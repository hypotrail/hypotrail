# CLI and study contract (`hypotrail`, v0.1, extended through v0.2)

Status: **frozen** at the end of Phase 1 (plan `docs/plans/V0.1-IMPLEMENTATION-PLAN.md` §4, §8, §9 bis). Implemented in `framework/mlkit/study/`. Frozen by `framework/tests/study/test_contract_freeze.py`.

Extended additively through v0.2 (no schema version changed): audience of engine messages (§3.3), the sealed final test (§4.1), confirmation modes and language (§5.2, §5.3), the data card, EDA governance, `preprocessing` and `success_criterion` (§11), cross-validation, `model_variant` and the `final_test` opening (§12), and model diagnostics (§13). A study created today has nine decisions; studies created under v0.1 (five) and v0.2a (seven) keep their set and load unchanged.

Phase 2 (activities) and Phase 3 (deliverables) are built in parallel on this contract. They may **add** what the extension points below allow. They must not rename, remove, or change the meaning of anything listed here. A change goes through the integrator: bump the schema version (`/1` to `/2`), update this document and the contract test in the same commit.

Consumers: the chat agent (Claude Code under directive A1), the HTML report, the generated notebook and workbench, and later a webview client (ADR 0002). All of them read the same JSON and write only through the same commands.

## 1. Invocation

```sh
uv run --project framework hypotrail <command> ... --study DIR
python -m mlkit.study.cli <command> ... --study DIR     # same program
```

| Rule | Detail |
|---|---|
| Study location | `--study DIR` is required by every command. The study is never taken from the current directory or from `OSML_ROOT`. A study is a directory with a `.hypotrail/` marker. |
| Output | Exactly one JSON document on stdout, then a newline. `--json` selects it explicitly; `--format text` prints a short human summary instead (not a contract); since v0.2a (WP-A1) `explain` and `evidence` print readable text there too, never JSON, and `hypotrail --help` lists every command, extensions included, with one line each. Nothing is written to stderr on a handled outcome. |
| Mutations | Every mutation is one request `{request_id, expected_revision, action, params}` applied by `mlkit.reliability.apply_command` under the writer lock. `--request-id` and `--expected-revision` are required on every mutating command. |
| Idempotency | Replaying a `request_id` with the same request returns the stored receipt with `replayed: true` and writes nothing. The same `request_id` with a different request is refused (`idempotency_conflict`). A replay is recognised before the revision check. |
| Revision | `expected_revision` must equal the current revision, otherwise `stale_revision` with `details.current_revision` and `details.changes_since` (the revision records the client has not seen). Every write's payload gives the study's revision after the write (v0.3, WP-A): the confirmation of `final_test` that opens the final test reports the revision after the opening's run, not the confirmation's own, so the next command's `--expected-revision` is the one the output gives. |

### Commands (v0.1)

```text
hypotrail init --case CASE --study DIR [--lang en|fr]
hypotrail status --study DIR [--since REV] [--json] [--summary]
hypotrail plan --study DIR
hypotrail decide propose DECISION (--value TEXT | --value-json JSON)
                 --restatement TEXT --rationale TEXT [--lang en|fr]
                 [--restatement-en TEXT] [--restatement-fr TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail decide confirm (PROPOSAL | --proposal PROPOSAL) --user-words TEXT
                 [--channel chat|cli|webview|choice] [--adoption-question] [--actor NAME]
                 [--basis explicit|delegated_default]
                 [--delegation-scope this_decision|standing] [--agent-concern TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail decide withdraw PROPOSAL [--reason TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail decide note (--about DECISION | --resolve NOTE_ID | --withdraw NOTE_ID) --text TEXT
                 [--kind hold|correction]
                 --request-id ID --expected-revision REV --study DIR
hypotrail mode set guided|training|express [--user-words TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail data --study DIR [--format json|text]
```

`--channel` defaults to `chat`, `--actor` to `user`, and `--basis` to `explicit` (§5). `--delegation-scope` has no default and goes with `--basis delegated_default` only (§5, R1). Reserved extension commands, absent in Phase 1 and refused with `unsupported_capability` until their module exists: `run`, `render`, `check`, `preview` (§8). Phase 3 adds `render` and `check` (§8.3). Post-v0.1 adds the read-only `session-report` (§8.6) and `decide note` (P2, §5.1); the post-v0.1 fixes add `decide note --withdraw` (D5, §5.1). v0.2a (ADR 0005, §5.2) adds `init --lang`, `decide propose --lang/--restatement-en/--restatement-fr`, `decide confirm --proposal` (the same as the positional `PROPOSAL`; giving both or neither is `invalid_arguments`) and `--agent-concern`, `decide note --kind correction` (`--user-words` is an alias of `--text`), and `mode set`. v0.2a (WP-A4, §11) adds the read-only `data` (the data card) and the decisions `success_criterion` and `preprocessing`. v0.3 (WP-B, ADR 0005 amendment of 2026-10-20, §5.4) adds `decide confirm --channel choice` and the switch `--adoption-question` (action parameter `adoption_question: true`, carried only when given).

## 2. Exit codes

| Code | Meaning |
|---|---|
| `0` | Success, or replay of a committed request |
| `1` | Internal error (unexpected exception); the payload is still `hypotrail.error/1` with code `internal_error` |
| `2` | Refusal without effect (any `hypotrail.error/1` with a stable code, including invalid arguments) |
| `3` | The command committed, but an artefact is `stale` or `failed` after rendering (WP3.4) |
| `4` | An execution has an unknown outcome (WP2.1, `run`) |

`status` and `plan` return `0` even when the study has interrupted executions or stale artefacts: they report them in the view.

## 3. Payload schemas

Every payload is a JSON object whose first keys are `schema` and `ok`. Keys are listed in their emitted order. Clients must ignore keys they do not know; producers must not remove listed keys within a schema version.

| Schema | Emitted by | Keys |
|---|---|---|
| `hypotrail.init/1` | `init` | `schema`, `ok`, `study`, `revision`, `case`, `dataset`, `structural_exposure`, `final_test`, `plan`, `next_action`, `agent_instructions`, `ignored_sources`, `note`, `notices`, `deliverables` |
| `hypotrail.status/1` | `status` | `schema`, `ok`, `study`, `revision`, `since`, `changed`, `changes_since`, `view` |
| `hypotrail.plan/1` | `plan` | `schema`, `ok`, `study`, `revision`, `steps`, `current_step`, `next_action` |
| `hypotrail.decide/1` | `decide …` | `schema`, `ok`, `study`, `action`, `request_id`, `replayed`, `revision`, `result`, `artifacts` |
| `hypotrail.error/1` | any refusal | `schema`, `ok` (`false`), `command`, `error` |
| `hypotrail.summary/1` | `status --summary` | `schema`, `ok`, `study`, `revision`, `since`, `changed`, `goal`, `current_step`, `plan`, `next_action`, `open_proposals`, `decisions`, `results`, `artifacts`, `executions`, `not_yet_defensible`, `notes`, `holds`, `final_test`, `criterion`, `eda_looks`, `recap`, `recap_audience`, `recap_junior`, `mode`, `deliverables` |
| `hypotrail.data/1` | `data` | `schema`, `ok`, `study`, `revision`, `observation_unit`, `development`, `target`, `final_test`, `groups`, `rows`, `note` (§11.1) |

* `status --summary` (D3, post-acceptance) prints a compact digest of the view (`view.summary`) for chat agents, a few kilobytes instead of the full view; `status --json` is unchanged and stays the client contract. `goal` is `{intended_use, decision, observation_unit, prediction_time}`: the first three are the case facts of those ids (`{value, status}` or `null`), `prediction_time` is `{value, source: decision|case, status}` (the decision value when there is one, else the case fact). `plan` lists the steps as `{id, title, status}`. `decisions` maps each decision to `{status, value, basis, delegation_scope, user_words, reason, open_proposals}` (a `feature_availability` value is grouped as `{status: [features]}`); `open_proposals` items are `{proposal_id, decision_id, value, restatement, revision}` (the restatement in the study language, `label`, is in `status --json` only, §5.2); `results` maps a slot to `{result_id, current, stale_reason, integrity}`; `artifacts` is `{status, items: {name: {status, revision, last_ok_revision, message}}}`; `executions` is `{active: [ids], interrupted: [{execution_id, activity, reason}], late: [{execution_id, activity, reason, result_id}], suspected_interrupted: [{execution_id, activity, liveness, reason}]}` (`active` lists only executions whose lease is held; see execution liveness, §3); `not_yet_defensible` is `{top: [{id, text}] (at most five, most urgent first), more: [ids]}`. `notes` (post-v0.1, P2; additive, before `recap`) lists every note of the study, oldest first, as `{note_id, decision_id, status, user_words, resolution_words}` (`view.SUMMARY_NOTE_KEYS`; `resolution_words` is `null` while the note is open, and holds the junior's resolving or withdrawing words otherwise). `holds` (post-v0.1 fixes, D5; additive, between `notes` and `recap`) groups the **open** holds by decision, in plan order: `[{decision_id, status, notes: [{note_id, user_words}]}]` (`view.SUMMARY_HOLD_KEYS`; `status` is the decision's status), so a restated hold is seen next to the one already recorded; `[]` when none is open. `final_test` (v0.2a, ADR 0006; additive, between `holds` and `recap`, so `recap` stays the last key before the digest keys) is `view.final_test` (§4.1).
* `summary.recap` (post-v0.1, acceptance T8 and F5; additive, the schema stays `/1`) is a list of exactly five strings, generated deterministically from the state by `view.recap`, that a new chat may quote to resume. Each starts with its label (`view.RECAP_LABELS`): `Goal` (the intended use and the prediction moment, the decision value or the case statement marked "from the case, not decided yet"), `Decided` (each confirmed decision in plan order, the feature availability with its excluded features by name and the doubtful ones kept, the split method and validation share (an ordinal cutoff names its column and cutoff), the policy rule of a binary study or the model choice of a regression study ("model choice: the linear model" or "the mean baseline"; M3), the conclusion verdict; "[delegated to the assistant]" or "[to confirm again]" when it applies; "nothing yet"), `Now` (the current step's title and the generated deliverables that are not up to date), `Next` (the next decision or action in words; an open proposal's restatement is quoted as recorded, so a stand-in figure keeps its caveat; an execution with an unknown outcome comes first), and `Limit` (the most urgent `not_yet_defensible` text other than `unconfirmed_decisions`). It holds no revision number, proposal, execution, or result id, with two exceptions. A binary study (post-v0.1 fixes, D10) whose `policy.evaluation` is current and verified cites the headline result of one evaluated rule: the adopted rule when it was evaluated, else the rule of the open policy proposal, else the first evaluated rule; the logistic model's precision and recall at that rule, in percent with one decimal as the report shows them, on the evaluation's `n` validation rows, with the first 8 characters of that result id: in `Decided` after an adopted policy ("policy capacity:100 (the logistic model at capacity:100 on the 90 validation rows: precision 31.0%, recall 54.5%, result 1a2b3c4d)"), otherwise in `Now` ("(latest policy evaluation: the logistic model at ...)"). And (P3) a regression study whose `evaluate.regression` is current and verified cites its validation MAE, as displayed with two decimals, in the target unit, with the first 8 characters of that result id: in `Decided` for a confirmed model choice ("model choice: the linear model (validation MAE 6.31 mpg, result 1a2b3c4d)"), otherwise in `Now` for both models. An open hold (P2, §5.1) is quoted in `Next` in the junior's words ("On hold in the junior's words: \"...\" (the policy); nothing on hold is confirmed until they resolve it."), the holds of one decision together ("\"a\"; \"b\" (the policy)", D5), so `open_holds` is not repeated as the `Limit`; nor is `conclusion_outdated` (D2), which `Decided` ("[to confirm again]") and `Next` already say. Each line is one flat line (whitespace collapsed, no line break). The deliverable messages hold no revision number either (P3, §8.3). A regression study's recap never uses the vocabulary of a decision rule (threshold, positive class, precision, recall, capacity): its texts come from the task-aware plan, next action, and limits.
* `summary.recap_audience`, `summary.recap_junior` (v0.2a, WP-A1; additive, after `recap`): `recap` is written for the agent (`recap_audience` is `agent`): it quotes the junior in the third person and cites result id prefixes. `recap_junior` is the same five labelled lines written for the junior (no result id, the junior variant of an agent instruction in `Next` and of the limit in `Limit`, holds in the second person). The `Now` line of both says "report and notebook not rendered yet" (or names the one not rendered) while a deliverable has never been rendered, never "up to date". `summary.decisions.*.feature_basis` (additive) is the availability's `feature_basis` grouped as `{basis: [features]}`, or `null`. `summary.artifacts.items.*` add `audience` and `junior_message`; `summary.not_yet_defensible.top` items are `{id, text, audience, junior_text}`, `junior_text` being `null` when `audience` is `junior` (the summary stays compact).
* `summary.mode` and `summary.deliverables` (v0.2a, WP-A7, the companion's requests; additive, after `recap_junior` and before the `--digest` keys): `mode` is `view.mode` (§5.2); `deliverables` is the view's `deliverables` (§3, R7) kept compact, `{launch: {notebook, workbench}}` with each launch `{mode, path, argv}` (`view.SUMMARY_DELIVERABLES_KEYS`, `view.SUMMARY_LAUNCH_KEYS`; the interpreter and the shell form stay in `status --json`), so a surface opens the notebooks without reading the full view. The `recap_junior` lines (WP-A7) say decision values in words, as the junior reads them elsewhere: the policy as "the decision policy: call the top 100 by score" (`audience.rule_words`), the verdict as "adopt the policy", "keep the baseline", or "inconclusive" (`audience.VERDICT_WORDS`), the decisions by `audience.decision_words`, and the headline figures without the rule's token; never a recorded token. Its `Now` line names the step that waits for the junior: the plan step of the decision of an `await_user_words` or `reconfirm` next action, with ", waiting for your answer" or ", waiting for you to confirm it again", or a run of an unknown outcome named in words (`audience.activity_words`), else the current step as in `recap`.
* `status.since` is the `--since` value or `null`; `changed` is `revision > since` (or `null`); `changes_since` lists the revision records after `since` (or `null`). A webview polls with `--since`.
* `decide.revision` is the revision created by the request (also on replay). `artifacts` is `null` until Phase 3 renders after commits (§8.3).
* `init.agent_instructions` is `{source, copied, skipped_existing, status, cli, agent_file, glossary}`; `glossary` is the study path of the glossary copy (§8.4); `status` is `copied`, `kept_existing`, or `no_templates_yet`; `cli` is the exact shell command that runs this CLI (§8.4) and `agent_file` is `.hypotrail/agent.json`. `copied` and `skipped_existing` list workspace paths. `ignored_sources` names the companion files found next to the case (`project.json`, `results.json`, `tutorial-results.json`, `answers.yaml`, `project.yaml`, `frame.yaml`); they are never read. `structural_exposure` is `{exposure_id, n_rows}`: the structural inspection of the **development rows** (v0.2a, ADR 0006; every row in a study created before it). `init.final_test` (v0.2a, additive) is the sealed final test, as `view.final_test` (§4.1).
* `init.notices` and `init.deliverables` (v0.2a, WP-A1, remark R7; additive). `init` writes `<study>/.vscode/settings.json` with `python.defaultInterpreterPath` set to the engine's Python (`framework/.venv/bin/python` when it exists, else the interpreter running the CLI; `mlkit.study.launch.interpreter`) **only when that file is absent**; when it exists and does not already name that Python, nothing is changed and `notices` holds `{code: "vscode_settings_kept", audience, message, junior_message, line}` (`launch.NOTICE_KEYS`), `line` being the JSON line to add. `notices` is `[]` otherwise. `init` also adds `__marimo__/` (Marimo's cache) to the study's `.gitignore`, creating it or appending the line once; `check` never reports `__marimo__/` or `.vscode/` as `untracked_files`. `deliverables` is `{interpreter, launch: {notebook, workbench}}` (`launch.DELIVERABLES_KEYS`); each launch is `{mode, path, argv, shell}` (`launch.LAUNCH_KEYS`): `mode` is `run` for the generated notebook (read-only, it is regenerated) and `edit` for the workbench, `path` the study-relative file, `argv` the argument list with absolute paths (`uv run --project <engine>/framework marimo run|edit <file>` when the CLI runs from the engine's uv project, as recorded in `.hypotrail/agent.json`; else the engine's Python with `-m marimo`), and `shell` the same quoted for a shell. The engine never starts these processes.
* `error` is `{code, message, details?, problems?}`. `problems` (case validation) is a list of `{path, problem}`.

### 3.1 Plan steps and next action

Each item of `plan.steps` and `view.plan` has the keys `id`, `title`, `question`, `expected_output`, `completion`, `pause`, `decision`, `activities`, `decide_first`, `missing_results`, `requires`, `status`, `current`. Step ids, in order: `prediction_time`, `feature_availability`, `split`, `train_eda`, `models`, `policy`, `conclusion`; for a regression study (§10) `prediction_time`, `feature_availability`, `split`, `train_eda`, `models`, `model_choice`, `conclusion`. Since v0.2a (WP-A4, §11) a study created by `init` has `discover_data`, `prediction_time`, `feature_availability`, `split`, `success_criterion`, `train_eda`, `preprocessing`, `models`, `policy` (or `model_choice`), `conclusion` (`state.FULL_STEP_IDS`, `state.FULL_REGRESSION_STEP_IDS`), the `models` step requiring `split`, `success_criterion` and `preprocessing`; a study created before has `discover_data` followed by its v0.1 steps (`state.steps(state)`). Step status is one of `done`, `needs_reconfirmation`, `awaiting_confirmation`, `ready`, `blocked`.

`next_action` always has `kind` and `message`, and since v0.2a (WP-A1, §3.3) `audience` and `junior_message`. Kinds and their extra keys:

| `kind` | Extra keys |
|---|---|
| `outcome_unknown` | `execution_id`, `activity` (closure fix F1: emitted by `status` only, first in priority, when an active execution's lease is not held). Its `junior_message` names the activity in words, "A run of the distribution of a column stopped ..." (WP-A7, `audience.activity_words`; "an analysis" for an activity it has no words for) |
| `acknowledge_interruption` | `execution_id` |
| `reconfirm` | `decision` |
| `await_user_words` | `proposal_id`, `decision` |
| `blocked` | `step`, `requires` |
| `show_data_card` | `step` (`discover_data`). v0.2a (WP-A4): while the study holds no proposal; informational, nothing to confirm (§11) |
| `propose` | `step`, `decision`; and `default_value` for `preprocessing` (WP-A4: the engine's default, §11.3) and, in a case with `scenario_defaults.capacity_share` (WP-A9, R6), for `policy` (`share:<p>`, the scenario's rule; also on the `run` action of the policy step), presented as the exercise's assumption |
| `run` | `step`, `activity` |
| `done` | — |

**Junior-ready keys (v0.3, WP-C; remarks R15, R18, R19, R36, R37; `mlkit.study.junior.enrich`).** In `status` (the view) and `status --summary`, and in `plan` (which now gives the view's next action), every `next_action` also carries, in this order after the keys above: `language` (the study language, `en` or `fr`: the language the agent records the restatement's label and the conclusion text in), `recommended` (`{value, why}`: the engine's default for the decision a `propose` asks for, with one sentence saying why, in the study language: the case's stated prediction moment, the availability drafted from the case, the cross-validation, the default preprocessing, the default variant, the scenario's share for the policy, the configuration the final test opens; `null` when the engine has no default, as for the success criterion's minimum, the model choice and the conclusion), `question` (the one question to ask the junior in the study language, `null` when nothing is asked: a `run`, `blocked` or `done`; at `await_user_words` "Do you adopt this decision?" in the guided and express modes, an own-words question in the training mode), and `junior_digest` (at most 200 words, `junior.MAX_DIGEST_WORDS`, in the study language: the statistical term first, with its canonical English term in parentheses in French, then this study's example: development and holdout rows, the folds, the target, the case's statement; no result id). At `feature_availability`, `default_value` is the availability drafted from the case (`junior.availability_draft`: `available_at_prediction` and `not_available` as the case states them, `uncertain` and `unknown` drafted `uncertain_excluded`, a doubt about the timing being a leakage risk). At `success_criterion` (`propose` and `await_user_words`), `criterion_options` (`criterion.options`, keys `criterion.OPTIONS_KEYS`): `task`, `action` (`share`, `capacity`, `threshold` from the adopted or proposed policy, else `share` when the case declares `scenario_defaults.capacity_share`, else `not_decided`; `model_choice` in a regression study), `default_metric`, `metrics` (`[{metric, value_key, unit, default, term, explanation}]`: `precision_gain` and `recall_gain`, or `mae_reduction`), `not_criteria` (`[{metric, available: false, why}]`: `expected_value`, which needs a cost and a value per action no case declares yet, and the ranking diagnostics `auc` and `average_precision`), `equivalence` (with a fixed number acted on, precision = TP/k and recall = TP/P rank configurations identically, and so does the lift; with a threshold they differ), `reference` (`{what: "base_rate", value, percent, n_rows, rows: development|training, result_id, text}` from the current split result, whose stratification read the target; `null` in a regression study or before the split is run), `candidates` (`[{value, per_1000, text}]`: +2, +5, +10 points with `per_1000: {reference, with_minimum, extra}` positives per 1,000 actions, or 5, 10, 20 % less error in the case's unit), `scale` (1000), `illustrative` (the sentence that labels the translation as illustrative, from the development rows) and `text` (the default metric explained for the action type). `check` accepts the numbers of these candidates as they are given (source `criterion_option`).

### 3.3 Audience of engine messages (v0.2a, WP-A1)

Every sentence the engine emits for a surface says who it is written for, with `audience`: `junior` (it may be shown to the junior as it is: second person or neutral, no command, flag, decision id, or field name) or `agent` (it instructs the assistant, such as "Show the restatement and record the user's own words", or speaks of the junior in the third person). A surface never shows an `agent` text to the junior; next to it the engine gives the junior variant. The keys are additive; no existing key changes meaning (`mlkit.study.audience`):

| Where | Audience key | Junior variant |
|---|---|---|

## 4. View model `hypotrail.view/1`

`mlkit.study.view.build(study_dir, *, leases=None) -> dict` is the **single** view of a study. `status` prints it under `view`, built with a read-only lease probe (`leases`, closure fix F1; see execution liveness below). ### 4.1 The sealed final test (v0.2a, ADR 0006)

`init` assigns a **final test** before any look at the data and seals it: by default 20 % of the rows (`partition.DEFAULT_FRACTION`), the same share of each target label in a binary study (`method: stratified`), of each of 5 target quantile bins in a regression study (`quantile_stratified`, `bins: 5`), or the last rows in the order the case declares (`temporal`, `CASE-CONTRACT.md` §Order). A stratified assignment draws a per-stratum permutation from `numpy.random.default_rng(seed)` with the recorded `seed` (`partition.DEFAULT_SEED`, 0) and keeps `floor(n × fraction + 0.5)` rows of each stratum. Every other row is a **development row**; every activity reads development rows only (`data.load_development`), and the `split` decision divides them into training and validation rows (its `n_rows` counts development rows).

The record is the optional state key `partition` (`state.TOP_OPTIONAL_KEYS`, `partition.RECORD_KEYS`): `{schema: "hypotrail.final-test/1", status, method, fraction, seed (null for temporal), stratified_on (the target or null), bins (null unless quantile_stratified), order (null, or {by, direction, ties_at_cut}), dataset_sha256, n_rows, development: {n_rows, row_keys}, final_test: {n_rows, row_keys}, schema_check, created, implementation}`. `row_keys` is the blob sha256 of the sorted row keys, one per line (the same canonical blob as exposure records), so a partition is identified by that digest and its count. `status` is `sealed` or, since v0.2b (WP-B1, §12), `opened` (`partition.STATUSES`), with the optional key `opening`. v0.2b (WP-B3): when the case declares `duplicates: {policy: group}` (`CASE-CONTRACT.md` §Duplicates), the assignment never divides a group of identical records (stratified: whole groups drawn per stratum, `partition.grouped_stratified`; temporal: a divided group moves to the side of its earliest record), `implementation` says so, and the record holds the optional key `groups: {policy, n_groups, n_rows, moved_rows}` (`partition.OPTIONAL_RECORD_KEYS`); the `split` then draws whole groups too (its inputs hold `duplicates: "group"`, its values `duplicates: {policy, n_groups, n_rows, divided_groups}`), and so do the folds of `eda.single_feature_signal` (`grouped_folds`). v0.2b (WP-B6a, review M2): when the case declares `prior_exposed_rows` (`CASE-CONTRACT.md` §Prior-exposed rows), those rows (with every copy of them under `duplicates: group`) are never sealed: a temporal final test is the declared tail less them (the cut stays at `fraction` of every row, so the final test holds fewer rows), a stratified one is drawn among the other rows; an unknown row key refuses `init` (`invalid_case`), a file whose bytes differ from its sha256 too (`dataset_changed`). The record holds the optional key `prior_exposed: {path, sha256, declared_rows, excluded_rows}` (`partition.PRIOR_EXPOSED_KEYS`; `excluded_rows`: those the rule would otherwise have sealed, temporal: the ones in the tail, stratified: every declared row) and `implementation` says so.

`schema_check` is the only reading of the final test's cells: `{status: pass|fail, n_rows, checks: [{check, column, failing_rows}], reveals}` with checks `numeric_cells` (one per numeric or integer variable), `target_missing`, and in a binary study `target_labels`. It holds counts, never a value, a label, or a row key. A failure refuses `init` with `invalid_case` (problems `{path, partition: "final_test", problem}`, `path` being the variable's `variables[i].type` or `target`, and `details.final_test_check`) or, when only target cells are missing, `unsupported_capability` (`missing target values (v0.2)`, reason with `partition: "final_test"` and `rows`). The development rows keep the detailed value refusals of `CASE-CONTRACT.md` §Dataset.

Every activity's `inputs` gains `development: {row_keys, n_rows}` (identity covers it); the split result's registry `partition` is `development`. Exposure: `init` records `structural_inspection` on partition `development` (activity `init.structure`) and the final-test rows under purpose `sealed`, partition `final_test` (activity `init.final_test`); `exposure.rows_exposed` does not count sealed rows (`records.SEALED_PURPOSES`), `by_purpose.sealed` does.

`view.final_test` and `summary.final_test` are `{status, rows, method, fraction, development_rows, schema_check}` (`schema_check` is the status word). A study created before v0.2a has no `partition` and is not migrated: `status` is `absent` and the other keys `null` ("no final test"); its activities read every row, its inputs have no `development` key (identities unchanged), and its exposure partitions stay `all`.

`decisions.*.confirmation` is `null` or `{user_words, channel, actor, restatement, proposal_id, revision, time, authenticated, basis, delegation_scope, agent_concern, mode, warnings, reason_given, adoption_question}` (`reason_given` and `adoption_question`, v0.3 WP-B, §5.4: `null` and `false` when not recorded; `mode`, v0.2b: the confirmation mode in force when the words were accepted, `null` for a confirmation recorded before v0.2b; `warnings`, WP-A9: the `words_contradict_value` warnings kept with the confirmation, `[]` when none). `authenticated` is always `false`: the engine records words, it cannot verify who typed them. `basis` is `endorsed`, `restated`, or `delegated_default` for a confirmation recorded since v0.2a (ADR 0005, §5.2), and `explicit` for one recorded before; a stored confirmation without it (written before the post-acceptance fixes) reads as `explicit`. `agent_concern` (ADR 0005, R3) is the point the agent raised before the junior confirmed, or `null` (also for a confirmation recorded before v0.2a). `delegation_scope` is `null`, `this_decision`, or `standing` (§5, R1); `null` for an explicit confirmation and for one recorded before R1. Decision status is one of `open`, `proposed`, `confirmed`, `reconfirm_required`, `superseded`.

A result item has the keys `slot`, `result_id`, `activity`, `current`, `stale_reason`, `partition`, `n_rows`, `values`, `blobs`, `params`, `inputs`, `code_fingerprint`, `environment`, `execution_id`, `exposure_id`, `started_revision`, `integrity`. Since review fix H2, `current` is derived (`read.Study.currency`): a result is current only if it is promoted and not stale in state, its activity's code is unchanged since it was computed (plan §3.7 row 11: every module of its code fingerprint still has the recorded sha256), and every result in its `inputs.results` (except the history role `previous_split`) is current too. A result that fails the derived rule has `stale_reason` `{reason, since: null, code_changed?: [modules], upstream_not_current?: [result ids]}`; `read.Study.is_current(slot)` and the artefact currency rule (§8.3) use the same rule. `integrity` is `ok` or the refusal code (`integrity_error`, `unknown_result`); a result that fails it has `current: false`, `values: null`, and adds a `result_integrity` item to `not_yet_defensible`. **Only a result item with `current: true` and `integrity: "ok"` may be cited.**

`not_yet_defensible` ids emitted in v0.1: `unconfirmed_decisions`, `validation_is_not_independent`, `public_data_already_explored`, `no_time_or_entity_identifier`, `uncertain_features_included`, `stale_results`, `interrupted_executions`, `no_causality`, `workbench_not_tracked`, `result_integrity`. Since v0.3 (WP-A, R34) `stale_results` also carries `cited_by` (`[{result_id, decision_id, proposal_id}]`: the stale results a decision value, confirmed, to confirm again or proposed, or an open proposal names, as `motivated_by` does; `state.cited_stale_results`) and `junior` (true when `cited_by` is not empty): with `junior: false` the item stays in the view and the summary for the agent (recompute before citing), but the junior's recap (`recap_junior`) and the report's "not yet defensible" section leave it out. Added by M3: `grouped_split_unsupported` (`column`, `capability`: the case declares a group column and this version has no grouped split; every split reports the group values its partitions share, `split.values.groups`, §10). Added by review fix L1: `sources_changed` (`changes`: `[{label, path, expected_sha256, actual_sha256}]`, the case or dataset file whose bytes differ from `state.case.sha256` / `state.dataset.sha256`; every result item is then `current: false` with `stale_reason.sources_changed`). Added by review fix H2: `code_changed` (`slots`: the current results whose activity code changed since they were computed). Added post-v0.1 (P2): `open_holds` (`notes`, `decisions`: the open holds, quoted verbatim in `text`). Added post-v0.1 (G.12), warnings computed by the view from current, verified results, never refusals: `small_validation_partition` (`slots: ["split"]`, `n_rows`, `min_rows`, and in a binary study `n_positive`, `min_positive`) when the current split's validation partition has at most `view.SMALL_VALIDATION_ROWS` (30) rows or, in a binary study, at most `view.SMALL_VALIDATION_POSITIVES` (5) positive rows (inclusive since the post-v0.1 fixes, D4: the boundary the plan calls small is small; before, "fewer than"), its `text` stating the counts (`view.small_partition_warning`); `capacity_exceeds_validation` (`rules`, `n_rows`) when the current policy evaluation holds a capacity at least as large as its validation rows, which "selects every row" (`view.capacity_warning`; `preview policy` returns both warnings for its rules, §8.1); `high_cardinality_grouping` (`slots`) when a current `eda.rate_by` or `eda.mean_by` folded values into `(other values)` (§8.5). Proposal rules:

* A proposal is first-class: `{proposal_id, decision_id, value, restatement, rationale, revision, status, created, request_id, basis}`; status ∈ `open`, `confirmed`, `withdrawn`, `superseded`. `basis` holds the confirmed values of the decisions it depends on.
* Proposing never changes a confirmed decision. A new proposal supersedes an older open one for the same decision.
* The restatement and rationale may only contain numbers that appear in the proposed value (a fraction may also appear as a percentage), or figures of a current, verified registry result, traced with the matcher of `hypotrail check` (`cmd_check.Pool`, current results only, at their displayed precision: "115 selected", "11.5%"); anything else is `literal_number_in_text`. **Since v0.3 (WP-A, one tracer):** `decide propose` traces its texts (restatement, rationale, labels, and the conclusion's `value.text`) with the same module and the same pool as `hypotrail check --text` (`mlkit.study.numtrace`: `study_pool`, `trace_text`), plus the proposed value as a literal (source `proposed_value`; never for the conclusion): a text `check` accepts is accepted here, and a number `check` reports (`untraceable_number`, `stale_number`, `final_test_figure_outdated`) is refused with `details.numbers` as written and `details.findings` as `check` reports them. The rules below remain, now shared by both commands. Since the post-acceptance fixes (D5) this check runs on the state the proposal is made against. Since review fixes L3 and L4: a percentage (`%`, `percent`, `pour cent` after the number) may come from a fraction of the value (`30%` for `validation_fraction` 0.3) or a current result, never from another number of the value (`capacity:100` does not allow `100% precision`; the refused number is reported as `100%`); digits glued to letters are numbers (`top250`), and identifiers are masked first (`commands.IDENTIFIER`: `p_5`, `r_1a2b`, `r-…`, a hexadecimal digest prefix of 8 or more characters with a letter and a digit). **Conclusion (review fix M1).** The conclusion's `value.text` is traced when proposed, with the matcher of `check` on the current results and the recorded literals (confirmed decisions other than the conclusion, the junior's recorded words, the rules of the current evaluation), never on the proposed value itself: an untraceable or stale number is `literal_number_in_text` with `details.field` `value.text`; then causal or forecast wording (`check`'s `causal_wording` and `forecast_wording` rules) in the text, restatement, or rationale is `causal_or_forecast_wording` with `details.findings`.

Confirmation rules (`ambiguous_confirmation`, with `details.reason`):

| `reason` | When |
|---|---|
| `missing_user_words` | `--user-words` is empty or blank |
| `negative_reply` | The words refuse, hesitate, or disagree (review fix H1, narrowed by P1 after the post-v0.1 acceptance: a negation is a refusal only when it targets the agreement or the proposal; `commands.is_negative`). In order: (1) a refusal of the agreement anywhere (`commands.REFUSES_AGREEMENT`: "disagree", "pas d'accord", "désaccord", "hold on", "not so fast", "I don't agree", "I can't confirm", an imperative "don't adopt ...", "je ne valide pas", "I'm not sure"); (2) a reply that opens with a refusal: its first word in `commands.NEGATIVE_LEADS` ("no", "non", "nope", "wait", "stop", "attends", "cancel", "never", "hold", ...) or an opening of `commands.REFUSAL_OPENINGS` ("not yet", "pas encore", "not now", "not that"), also right after an agreement word ("ok, not yet"); (3) a first clause that negates the proposal: a word of `commands.FIRST_CLAUSE_REFUSALS` ("wrong", "faux", "reject"), or, when the reply does not open with an agreement (`commands.AGREEMENT_LEAD`: "yes", "ok", "agreed", "right", "I confirm", "I adopt", "I choose", "I'll go with", "that matches", "oui", "d'accord", "je confirme", "j'adopte", ...) or a delegation, a negator ("not", "n't", "pas", "never") whose next word does not describe availability, a restart, or an inability to answer ("this feature is not available", "we don't know it before the call", "don't restart it", "for questions I can't answer" are statements); (4) a later clause that is a refusal on its own ("ok... no", "yes. No, wait.") or a reservation opening with "but" / "mais" followed by a negation ("Yes, but not before the first call", "d'accord, mais je ne veux pas de seuil"). After an agreement lead, a negated clause states a limit and is not a refusal ("Yes, and it's not a forecast", "agreed, never an input", "I confirm: its validation errors aren't evidence of future error"); the words are recorded verbatim, limits included |
| `bare_acknowledgement` | The words hold nothing beyond acknowledgements, filler words, and identifiers ("ok", "oui", "yes, that is right", "keep that", "garde ça", "d'accord", "sure, sounds good to me", "yes go with that", "ok p_5"); `commands.is_bare_acknowledgement`. Since ADR 0005 an explicit first-person endorsement is not bare (`confirm.ENDORSEMENT`: "I confirm", "I agree", "je confirme", "je valide", "je suis d'accord", "j'approuve"). Checked after `conditional_reply` |
| `question_reply` | ADR 0005 (guided): the words hold a question mark; a question is not an answer (`confirm.is_question`). Checked after `negative_reply` |
| `conditional_reply` | ADR 0005 (guided): the words set a condition or hesitate (`confirm.is_conditional`): anywhere "unless", "sauf si", "except if", "only if", "seulement si", "à condition", "provided that", "pourvu que", a hesitation ("réfléchir", "let me think", "think about it", "on verra"), and (WP-A9, B1) "pas pour", "not for", "but not", "mais pas"; or, right after an agreement or an endorsement (other agreement and filler words aside), "but", "mais", "however", "cependant", "toutefois", "sauf", "except", "though" ("oui mais je veux réfléchir", "d'accord sauf contact", "yes but"). Checked after `question_reply`. WP-A9 (B1), in every mode and after the proposal checks: a partial refusal of a `feature_availability`, `preprocessing`, `split`, `model_variant` or `final_test` proposal (`confirm.partial_refusal`, `details.partial: {negator, part}`): a negator ("pas", "not", "sans", "except", "sauf", "no", "non", "without"), or "non"/"no" after the part, applied to a part the value holds (a variable the value keeps; a preprocessing step the value applies, named by its concept terms, or one of its columns; a word of a split's value or restatement that the restatement does not negate itself); a negated description ("pas connu", "not available") is a statement; "all features except X" is accepted when the value excludes X |
| `unrelated_reply` | The words hold no explicit endorsement expression (`confirm.ENDORSEMENT`: "I confirm", "I agree", "agreed", "that works for me", "je confirme", "je valide", "je suis d'accord", "d'accord pour moi", "ça me va", "c'est bon pour moi") and are not about the proposal (review fix H1; ADR 0005; WP-A9, H1, `confirm.relates_to`): a reply relates when it agrees (an agreement opening or word, or a clause that states the decision: two or more content words, every one of them the proposal's) and one of its clauses is about the proposal: it states a number of the value or its texts or names a key of the value, or two of its content words (all of them when it has one) repeat a word of the proposal's value, restatement or labels (same word, a final "s" aside, or the same first five letters, accents folded), a concept term of the value (`content/concepts.yaml`), or a `reason_domain` word of the decision. A bare agreement word followed by unrelated content ("yes, I like pizza") and one shared common noun in an off-topic remark ("oui, la pizza du client est bonne") are refused. Also emitted by `decide note --resolve` (§5.1) and `run --acknowledge-interruption` (§8.1) |
| `proposal_not_found` | No such proposal |
| `proposal_withdrawn`, `proposal_superseded`, `proposal_confirmed` | The proposal is not open |
| `same_request` | The proposal was not created by an earlier request |
| `proposal_stale` | A decision the proposal rests on changed since it was made (`details.basis`, `details.current_basis`) |
| `not_a_delegation` | `--basis delegated_default`, but the words do not explicitly delegate to the assistant's recommended default |
| `delegation_needs_basis` | `--basis explicit`, but the words delegate the choice to the assistant: the confirmation must say so |
| `restatement_not_default` | `--basis delegated_default`, but the proposal's restatement does not say it is the assistant's recommended default |

| `delegation_not_given_at_this_pause` | `--basis delegated_default` for the `policy` or the `conclusion` without `--delegation-scope this_decision` (acceptance rerun, R1): a standing delegation covers `state.STANDING_DELEGATION_DECISIONS` only (`details.decision_id`, `details.delegation_scope`, `details.standing_covers`). Checked after `restatement_not_default` |

**Confirmation basis (D1, post-acceptance).** `explicit` (default): the user's own reply to the restatement decides. `delegated_default`: the user explicitly hands the choice to the assistant ("use your recommended default", "go with your recommendation", "je te laisse choisir", "prends ta recommandation"; `commands.is_delegation`), and the proposal's restatement states that it is the assistant's recommended default ("My recommended default: ..."; `commands.states_default`). A bare acknowledgement never delegates; silence is never a delegation. The basis is recorded in the confirmation, shown distinctly in the view, the HTML report and the notebook, and every delegated decision is listed in `not_yet_defensible` (`delegated_decisions`).

**Delegation scope (acceptance rerun, R1).** `--delegation-scope` (action parameter `delegation_scope`, `null` when absent) says which delegation a `delegated_default` confirmation rests on: `this_decision`, a delegation the junior gave at this very pause; or `standing`, an earlier delegation for every question they cannot answer ("for questions I can't answer, use your recommended default"). A standing delegation covers only `prediction_time`, `feature_availability`, and `split` (`state.STANDING_DELEGATION_DECISIONS`); in the `express` mode (v0.2b, §5.3) also `success_criterion` and `preprocessing` (`state.EXPRESS_STANDING_DELEGATION_DECISIONS`, `state.standing_delegation_decisions`). Since WP-B6c, in the `guided` mode it also covers a `preprocessing` proposal whose value is the engine's default (`commands.standing_covers_default_preprocessing`, ADR 0005 amendment); `details.standing_covers` is unchanged. The refusal's `details` then also carry `mode`. The `policy` and the `conclusion` need the junior's own words (`explicit`) or a delegation given at that pause: `--basis delegated_default` for them without `--delegation-scope this_decision` is `ambiguous_confirmation` with reason `delegation_not_given_at_this_pause`. For the other three decisions the scope is optional and recorded as given. A scope with `--basis explicit`, or a value outside `state.DELEGATION_SCOPES`, is `invalid_value` (`details.field` `delegation_scope`). The scope is recorded in the confirmation and shown in the view and in `status --summary`. Confirmations recorded before R1 (without a scope, including a delegated policy) stay valid.

Then, in order: the case and dataset bytes must still match (`dataset_changed`), the value must be valid (`invalid_value`), and the pause preconditions must hold (`precondition_missing`, `details.missing`). A confirmation records `{user_words (verbatim), proposal_id, restatement, authenticated: false, channel, actor, revision, time, basis, delegation_scope, agent_concern, mode, warnings, reason_given, adoption_question}` and applies §6. `channel` is one of `state.CONFIRMATION_CHANNELS` (`chat`, `cli`, `webview`, and, v0.3, `choice`). `basis`, `delegation_scope`, `agent_concern`, `mode` (v0.2b: the confirmation mode in force, one of `state.MODES`), `warnings` (WP-A9: written only when the words raised `words_contradict_value` warnings that were kept), `reason_given` (v0.3, WP-B: a boolean, written only for a trade-off confirmed in the junior's words) and `adoption_question` (v0.3, WP-B: `true`, written only when given) are optional in a stored record (`state.CONFIRMATION_OPTIONAL_KEYS`) so that earlier studies stay valid; `delegation_scope` is `null` unless the basis is `delegated_default`.

**Guided confirmation (ADR 0005, v0.2a).** The rules above are those of the `guided` mode (§5.2), the default (v0.2a); the `training` and `express` modes (v0.2b) are in §5.3. A reply bound to a proposal (`PROPOSAL` or `--proposal`) that is the single open proposal of its decision at the current revision (`--expected-revision`), that is neither negative, a question, conditional (a partial refusal included, WP-A9), nor bare, and that either holds an explicit endorsement expression or agrees and is about the proposal (`confirm.relates_to`, see `unrelated_reply`; else `unrelated_reply`), confirms it; with `--adoption-question` or `--channel choice`, a short affirmative confirms too (§5.4). No decision needs a reason in this mode since v0.3 (WP-B, R27; it replaces the R1 "hybrid" rule and the WP-B1 reason for the final test): for the decisions of `confirm.REASON_DECISIONS` (`policy`, `final_test` and `conclusion` in a binary study, `model_choice`, `final_test` and `conclusion` in a regression study) confirmed in the junior's own words, the record says whether the words give one reason (`reason_given`, `confirm.has_reason`, WP-A9 H1): a connector ("because", "since", "given", "as the ...", "parce que", "car", "puisque", "vu que", "étant donné"), or a clause that is neither a restatement of the value nor unrelated: it holds a content word that repeats neither the value, its texts, its numbers nor a concept term of the value, and the clause is about the proposal or the decision's `reason_domain` words (`content/concepts.yaml`: team, budget, capacity, evidence, ...). "ok, 10 %" restates and "je confirme, j'aime la pizza" is unrelated, so both record `reason_given: false`, which the report, the notebook, the handoff pack and the panel show as "no reason given". `reason_required` is a training refusal only (§5.3). The recorded `basis` is `restated` when the words repeat a word or a number of the proposal's value, restatement or labels (endorsement words left out, `confirm.restates`; since v0.3, WP-A, R25 note, generic references such as "choix", "décision", "cela", "this choice" are left out too, `confirm.GENERIC_REFERENCE_WORDS`, so "je confirme ce choix" is `endorsed`), else `endorsed`; the request's `--basis` stays `explicit` or `delegated_default` (`state.REQUEST_BASES`), and a delegation is recorded as `delegated_default` as before. `explicit`, `endorsed` and `restated` are all the junior's own words: a change between them never outdates a conclusion (§6, `state.basis_class`).

**Agent concern and contradiction warnings (ADR 0005, R3).** `--agent-concern TEXT` (action parameter `agent_concern`, carried only when given) records, on the confirmation, a point the agent raised about the junior's words before they confirmed and that the junior kept; it is non-blank (`invalid_value`, `details.field` `agent_concern`), shown in the view, `decisions`, the HTML report ("Point raised by the agent ... kept by the user") and the handoff pack. For `feature_availability`, the confirm result carries `warnings` (`confirm.availability_warnings`): the words are cut into clauses; a clause naming a candidate feature with exclusion words ("exclure", "écarter", "retirer", "sans", "exclude", "drop", "remove") while the value marks it `available_at_prediction` or `uncertain_included`, or with keep words ("garder", "conserver", "inclure", "keep", "include", "use") while the value marks it `not_available` or `uncertain_excluded`, gives `{code: "words_contradict_value", variable, said: "exclude"|"keep", value, message}`. A clause without such words continues the direction of the clause before it ("exclure duration, contact et pdays"); a clause with both kinds, or with a negation before them, says nothing. In the `express` mode it is a recorded warning. In the `guided` mode (WP-A9, H3) it is the refusal `words_contradict_value` (`details.warnings`, `mode`, `junior_message`) until the agent has raised the point: with `--agent-concern` the confirmation is recorded with the warning. In the `training` mode it is always the refusal (§5.3). A recorded warning is kept on the confirmation (`warnings`), shown in the view, `decisions`, and the report ("Words and value disagree"). A later correction of the reasoning is a note of kind `correction` (§5.1).

In a regression study (§10) the decisions are `prediction_time`, `feature_availability`, `split`, `model_choice`, `conclusion`; `policy` is not one of them (`unknown_decision`). `model_choice` is `"fit.linear"` or `"fit.baseline"` (`preconditions.MODEL_CHOICES`), confirmed only with a current `evaluate.regression` whose `params.models` lists it; the conclusion's verdict is one of `adopt_model`, `keep_baseline`, `inconclusive` (`preconditions.REGRESSION_CONCLUSION_VERDICTS`): `adopt_model` needs `model_choice` confirmed as `fit.linear`; `keep_baseline` and `inconclusive` need no model choice (D6; before the post-v0.1 fixes `inconclusive` needed a confirmed one). A standing delegation does not cover `model_choice` (it is not in `state.STANDING_DELEGATION_DECISIONS`).

**Split methods (M3).** `split` is one of `{"method": "stratified_random", "validation_fraction": f, "seed": n}` (binary study), `{"method": "random", "validation_fraction": f, "seed": n}` (regression study, not stratified), or `{"method": "ordinal_cutoff", "column": C, "cutoff": k}` (`commands.ORDINAL_SPLIT_KEYS`; `C` is the case's declared time column, of type `integer`; `k` an integer: rows with `C >= k` are validation rows). When the case declares a time column, `ordinal_cutoff` is the only method (`commands.split_methods`): a random split would mix earlier and later rows, so it is `invalid_value`, never a silent fallback. A method outside `commands.ALL_SPLIT_METHODS` is `unsupported_capability`. `run split` refuses a split the rows cannot support with `unsupported_capability` and a structured reason (`details.reasons[]: {code, capability, path, reason}`): `stratified split with fewer than two rows of each class` (with `counts` by label) before sampling, or `random split of these rows with these parameters` when the sampler refuses (for example a validation fraction that leaves a partition empty).

### 5.1 Notes: the junior's conditions and holds (post-v0.1, P2)

`hypotrail decide note --about DECISION --text TEXT` records a condition the junior stated at a pause, verbatim ("don't adopt anything until I bring my manager's figure"): a note `{note_id, decision_id, kind: "hold", user_words, status: "open", created, revision, request_id, resolution: null}` in `state.notes` (`state.NOTE_KEYS`). `--about` names a decision of the study (`unknown_decision` otherwise); the text must be non-blank and say more than an acknowledgement (`invalid_value`, `details.field` `user_words`). A refusal or a negation is allowed: a hold usually is one.

**A hold on a confirmed decision (post-v0.1 fixes, D1).** When the decision is already `confirmed`, the hold withdraws that agreement: the decision becomes `reconfirm_required` (its value and confirmation stay visible, `reason` names the note), and so does every confirmed decision that rests on it (`dependencies.dependents`: the decisions whose `depends_on` closure holds it; the conclusion rests on all of them). No result is invalidated, since no value changed. The invalidation is recorded with `mutation: hold_added`, `row: null`, `decision_id` the held decision (§6), and the `decide.note` result lists the decisions in `reconfirm_required`. A study therefore never shows a decision as confirmed while a hold on it is open; once the hold is resolved or withdrawn, the decision is proposed and confirmed again. A hold on an open or proposed decision changes no status. A state written before this rule may still hold a confirmed decision with an open hold; it is kept as recorded.

While a note on a decision is open, `decide confirm` of that decision is refused with `decision_on_hold` (`details.decision_id`, `proposal_id`, `notes: [{note_id, user_words}]`), whatever the basis, checked after the proposal is found open and created by an earlier request. Proposing is still allowed. `not_yet_defensible` lists `open_holds`; `status --summary` lists every note (`notes`) and the recap's `Next` line quotes the open ones; the HTML report shows each note, open or resolved, in its decision's card, in the junior's words.

`hypotrail decide note --resolve NOTE_ID --text TEXT` resolves an open note with the junior's own words, `resolution: {user_words, revision, time, request_id}` and `status: "resolved"`. The words follow the confirmation rules (`ambiguous_confirmation` with `details.reason` `missing_user_words`, `negative_reply` ("not yet"), `bare_acknowledgement`, or `unrelated_reply` when they share no word or number with the note's words, its decision's id, or that decision's open proposals); `same_request` when the request that recorded the note resolves it. A note id that does not exist is `unknown_note`; a resolved or withdrawn note is `note_not_open`. The words of a note and of its resolution are literals for `check` (`user_words`), like confirmation words.

`hypotrail decide note --withdraw NOTE_ID --text TEXT` (post-v0.1 fixes, D5) withdraws an open hold that no longer applies (a restatement of a hold already recorded, a condition the junior dropped), with the junior's own words: `status: "withdrawn"` and the same `resolution` record. The words may hold a negation ("no need to wait for that any more"); they must be non-blank (`ambiguous_confirmation`, `missing_user_words`) and say more than an acknowledgement (`bare_acknowledgement`); `same_request`, `unknown_note`, and `note_not_open` as for `--resolve`. A withdrawn note no longer blocks its decision; a decision a hold made `reconfirm_required` still needs the junior's words again. `state.NOTE_STATUSES` is `open`, `resolved`, `withdrawn`, `recorded`; the report shows a withdrawn note with the words that withdrew it.

**Corrections (ADR 0005, R3).** `hypotrail decide note --about DECISION --kind correction --user-words TEXT` (action parameter `kind`, carried only when it is not `hold`) records a later correction of a decision's reasoning in the junior's words, without asking for the decision again: a note `{kind: "correction", status: "recorded", resolution: null}`; no invalidation, no hold, nothing becomes `reconfirm_required`. The decision must have a confirmation (`confirmed` or `reconfirm_required`), otherwise `invalid_value` (`details.field` `kind`): before a confirmation the junior answers the proposal in the words they mean. A correction cannot be resolved or withdrawn (`note_not_open`). The report shows it in its decision's card ("Correction in your words"); the companion digest lists it with kind `other`.

### 5.2 Confirmation modes and language (ADR 0005)

`state.mode` is one of `state.MODES`: `guided` (the default, written by `init`), `training` and `express` (implemented in v0.2b, WP-B2, §5.3; `state.SUPPORTED_MODES` is all three, and `state.MODES_AVAILABLE_IN`, which in v0.2a refused `training` and `express` with `unsupported_capability` and `available_in` `v0.2b` in `details`, is now empty). `hypotrail mode set MODE [--user-words TEXT] --request-id ID --expected-revision REV --study DIR` (action `study.set_mode`, parameters `{mode, user_words}`, `user_words` `null` when the option is absent) records the mode: a mode outside `state.MODES` is `invalid_value`. The modes are ordered by strictness (`state.MODE_STRICTNESS`: `express` < `guided` < `training`). **Lowering** the strictness (training to guided, guided to express, training to express; `state.lowers_strictness`) needs the user's words, and they must name the mode asked for (`concepts.mode_named`, the `modes` lists of `content/concepts.yaml`: "express", "rapide", "guidé", ...), otherwise `ambiguous_confirmation` with reason `unrelated_reply`. **Raising** it (`state.raises_strictness`) needs no words: the agent may make confirmations stricter on its own. Keeping the same mode needs words. Missing words where they are needed are `ambiguous_confirmation` with reason `missing_user_words` (`details.previous`, `details.mode`). Words, when given, follow the guided reply rules (`ambiguous_confirmation`: `negative_reply`, `question_reply`, `conditional_reply`, `bare_acknowledgement`). Each accepted request appends `{mode, previous, user_words, revision, time, request_id}` (`state.MODE_CHANGE_KEYS`; `user_words` `null` only for a raise) to `state.mode_history`; the replay of a request is idempotent. A mode change never touches a decision or a proposal: past confirmations stay valid, each with the `mode` it was recorded in.

`state.language` is one of `state.LANGUAGES` (`en`, `fr`), set by `init --lang` (default `en`). A proposal keeps its structured `value` and its `restatement` (compatibility); `decide propose --restatement-en TEXT` and `--restatement-fr TEXT`, and `--lang L` (the language of `--restatement`), store `labels: {language: restatement}` on the proposal (action parameter `labels`, carried only when a language is given, so earlier requests keep their identity). Each label is non-blank, in a language of `state.LANGUAGES` (`invalid_value`, `details.field` `labels`), and checked for numbers like the restatement (`literal_number_in_text`, `details.field` `labels.<language>`). `status --json` shows `label`, the restatement in the study language, on each open proposal of the view (`status --summary` keeps its v0.1 shape); a French paraphrase can restate through the French label.

### 5.3 Training and express modes (v0.2b, WP-B2)

The checks of `guided` (§5) that do not depend on the proposal apply in every mode: `missing_user_words`, `negative_reply`, `question_reply`, `conditional_reply`, `bare_acknowledgement`, the delegation checks, and the binding, hold, and staleness checks. Then, for a confirmation in the junior's own words (`--basis explicit`):

| | `training` | `guided` | `express` |
|---|---|---|---|
| What confirms | A paraphrase on the proposal's **concepts** (`concepts.concept_map`, below); an endorsement alone ("oui je confirme cela") is `paraphrase_required` | An endorsement or a restatement (§5) | As `guided` |
| Reason (`confirm.REASON_DECISIONS`: `policy` or `model_choice`, `final_test`, and `conclusion`) | A reason connector ("because", "since", "given", "parce que", "car", "puisque", "vu que", "étant donné"; `concepts.has_reason_connector`), else `reason_required` | Optional since v0.3 (WP-B, R27): recorded as `reason_given` (`confirm.has_reason`) | As `guided` |
| Closed adoption question, `--channel choice` (v0.3, §5.4) | Lift nothing: an option label or a bare "oui" does not paraphrase | A short affirmative confirms | As `guided` |
| Words that contradict a `feature_availability` value (R3) | Refusal `words_contradict_value` (`details.warnings`) | Refusal `words_contradict_value` without `--agent-concern`; with it, a warning kept in `result.warnings` and the record (WP-A9) | Warning in `result.warnings` (recorded only) |
| Recorded `basis` | `restated` | `endorsed` or `restated` | `endorsed` or `restated` |
| Standing delegation covers | `state.STANDING_DELEGATION_DECISIONS` | the same, and (WP-B6c) the default `preprocessing` | `state.EXPRESS_STANDING_DELEGATION_DECISIONS`: also `success_criterion` and `preprocessing` |

The policy, the model choice, and the conclusion (and any decision that is not listed) are never covered by a standing delegation in any mode (R1 of v0.1): a delegation of them is given at their pause (`--delegation-scope this_decision`). Every delegated decision stays in `not_yet_defensible` (`delegated_decisions`), whatever the mode. Each confirmation records the mode in force (`confirmation.mode`, `result.mode`).

**Concepts (training).** `concepts.concept_map(state, proposal)` gives, for each decision, the small list of concepts a training confirmation must say. A concept is said when the reply, with endorsement words left out (`confirm.ENDORSEMENT_TOKENS`, so "je valide" never says "validation"), holds one of its terms, in English or French, from `content/concepts.yaml` (data, not code): a one-word term matches an equal word (a final "s" aside) or, when both have at least five letters, a word with the same first five letters; a term `stem*` matches every word that starts with `stem`; a term of several words matches them in a row. Accents and case are folded.

| Decision | Concepts (ids in `details.missing[].concept`) |
|---|---|
| `prediction_time` | each timing the value uses (`timing_before`, `timing_after`, `timing_at`: "before"/"avant", "after"/"après", "at the time"/"au moment"), and `event`: a word of the value or of a label, or a translation of it (`synonyms`: "call"/"appel", "first"/"premier", "campaign"/"campagne", ...), framing words ("predict", "score", "you", `framing`) left out |
| `feature_availability` | `exclude` ("exclure", "écarter", "retirer", "exclude", "drop", "not available", ...) and `variable:<name>` for every variable the value marks `not_available` or `uncertain_excluded`, named as it is (or with its `_` and `.` read as spaces); `keep_all` when nothing is excluded |
| `split` | `validation` (the rows held apart to validate), `random` ("random", "aléatoire", "au hasard", "stratifié"), `proportion` (the validation fraction as a fraction or a percentage, of the validation or the training rows: `0.3`, `30 %`, `70/30`, "trente"); an ordinal cutoff: `validation` (with the later-rows words) and `proportion` (the cutoff) |
| `success_criterion` | binary: `precision` and `min_gain` (the minimum points); regression: `error`, `reduction`, and `min_gain` (the share, as a fraction or a percentage) |
| `preprocessing` | one concept per parameter that differs from the default: `missing_indicator`, `rare_categories`, `caps`, `log_transform`; `no_preprocessing` for the default |
| `policy` | `capacity` ("the 100 best", "appeler les 100 meilleurs", "top", "capacité") or `threshold` ("seuil", "at least"), and `rule_number` (the capacity, or the threshold as a fraction or a percentage) |
| `model_choice` | `linear_model` or `baseline_model` |
| `conclusion` | the verdict: `adopt`, `keep_baseline`, or `inconclusive` |
| any other decision | `restatement`: a word or a number of the value or a label (`confirm.restates`) |

In order, after the checks of every mode: (1) for `feature_availability`, words that contradict the value (`confirm.availability_warnings`) are refused with `words_contradict_value` (`details.decision_id`, `proposal_id`, `user_words`, `mode`, `warnings`, `junior_message`); (2) a reply that holds no endorsement expression, no word or number of the proposal, and no concept is `ambiguous_confirmation` with reason `unrelated_reply` (the classifier is kept); (3) a concept left unsaid is `paraphrase_required` (`details.decision_id`, `proposal_id`, `user_words`, `mode`, `missing: [{concept, hint}]`, `said` (the concept ids said), `junior_message`: a sentence for the junior that names what the reply does not say yet, never words to type); (4) a trade-off without a reason connector is `reason_required`. `concepts.check(state, proposal, words)` returns `{concepts, said, missing}`. The matching is lexical: it misses paraphrases outside the lists and can accept a reply that names the concepts without understanding them; the agent instructions keep the R3 stop for a misattributed reason.

### 5.4 Adoption and interactive choices (v0.3, WP-B; ADR 0005 amendment of 2026-10-20)

**The closed adoption question (R14).** In the `guided` and `express` modes every pause ends with the restatement as a quoted block and one closed question, "Do you adopt this decision?" (in the study language). `decide confirm --adoption-question` (action parameter `adoption_question: true`, carried only when given; any other value is `invalid_value`, `details.field` `adoption_question`) states that the words answer that question about this open proposal; the engine cannot see the question, so the agent attests it. A short affirmative then confirms: an endorsement, a bare acknowledgement ("oui", "ok", "ok pour moi", "parfait", "vas-y", "allons-y"), or an agreement whose other words only point at the proposal ("d'accord avec ta recommandation", "oui, cette décision"); `confirm.closed_affirmative`. The checks of every mode still come first: `negative_reply`, `question_reply`, `conditional_reply` (a partial refusal included), and content unrelated to the proposal is `unrelated_reply` ("yes, I like pizza"). Without the flag, a bare acknowledgement is `bare_acknowledgement` as before; its message names the closed question. The record and the view carry `adoption_question: true`; the recorded basis is `endorsed` unless the words restate the proposal.

**The choice channel (R16).** `decide confirm --channel choice` records that the junior picked the adoption option of an interactive choice the agent offered in the chat (Claude Code's `AskUserQuestion`, or a client's equivalent). The options are: adopt (confirms), change something (the junior then writes what to change: the normal text path), explain first (no write). `--user-words` is the option label, verbatim, in the study language (for example "J'adopte cette décision", "I adopt this decision"); the channel implies the closed adoption question, and the recorded basis is always `endorsed`, since the label is the agent's wording. A label that does not adopt ("Je veux changer quelque chose", "Explain first") is refused like any reply that does not agree (`ambiguous_confirmation`). `choice` is a confirmation channel only (`state.CONFIRMATION_CHANNELS`): `decide propose --channel choice` is `invalid_value`, and `--channel choice` with `--basis delegated_default` is `invalid_value` (`details.field` `channel`). The text path stays complete and is the fallback for `claude -p`, clients without such a tool, and the acceptance harness.

**Reasons (R27).** In the `guided` and `express` modes no decision needs a reason; `reason_given` records whether the junior's words give one for a trade-off (§5). The `training` mode is unchanged (§5.3): concept matching and a reason connector; `--adoption-question` and `--channel choice` lift none of its refusals.

## 6. Invalidation (plan §3.7)

`mlkit.study.dependencies.MUTATIONS` is the table. `effects(old_state, decision_id, old, new)` returns at least `refit`, `re_eda`, `re_policy`, `re_chart`, `re_explain`, `reconfirm` (lists), plus `mutation`, `row`, `reason`, `recompute`, `blocked_until`, `scope`, `notes`.

| Row | `mutation` id | Classified from |
|---|---|---|

| 2 | `feature_availability.feature_set` | availability change that changes the usable feature set (`available_at_prediction` ∪ `uncertain_included`) |
| 3 | `feature_availability.wording` | availability change with the same feature set |
| 4 | `split` | any change of `split` |
| 5 | `policy.parameter` | same rule type, new `t` or `k` |

| 12 | `dataset` | `dataset` or `case`: refused with `dataset_changed` |
| 14 | `preprocessing` | v0.2a (WP-A4): a change of the preprocessing parameters: refit `fit.logistic` (`fit.linear`), re-evaluate, reconfirm `policy` (`model_choice`) and `conclusion`; the baseline and the EDA stay current |
| 15 | `preprocessing.motivation` | WP-A4: same parameters, other `motivated_by`: no effect |

| `*` | `unknown` | anything else, or an unparseable value: every current result stale, every other confirmed decision `reconfirm_required`, reason recorded |

A regression study uses `dependencies.REGRESSION_MUTATIONS` (`dependencies.mutations(state)`), with the same row numbers: rows 1–4 and 7 name `fit.linear`, `evaluate.regression` (under `re_policy`, the key of evaluations recomputed from stored predictions), and `model_choice` where the binary table names `fit.logistic`, `policy.evaluation`, and `policy`; rows 5 and 6 do not exist; row 13, `model_choice`, is new (no refit, no new evaluation; `conclusion` is reconfirmed). Result replacement uses `dependencies.REGRESSION_RESTS_ON` (`model_choice` and `conclusion` rest on `split`, `fit.baseline`, `fit.linear`).

A first confirmation (`mutation: first_confirmation`) and a confirmation with an unchanged value (`unchanged_value`) have `row: null` and no effect, with one exception. **The conclusion summarizes its decisions (post-v0.1 fixes, D2).** When the conclusion is `confirmed` and a decision it rests on (`state.depends_on(state, "conclusion")`) is then confirmed with a different status (it was not `confirmed`: a policy or model choice adopted after a `keep_baseline` conclusion, a decision confirmed again after a reconfirmation request), a different value, or a different basis class (a delegated default confirmed again in the junior's own words, or the reverse; since ADR 0005 `explicit`, `endorsed` and `restated` are one class, `state.basis_class`), the conclusion becomes `reconfirm_required` (`dependencies.outdates_conclusion`), and `not_yet_defensible` names `conclusion_outdated` until it is confirmed again. The record keeps the mutation id (`first_confirmation`, `unchanged_value`, or the table row) and states the reason. **A hold** on a confirmed decision is recorded with `mutation: hold_added` and `row: null` (§5.1, D1). **Result replacement (review fix H2).** When `run.promote` puts a new result in a slot that held another one, `dependencies.apply_replacement` records an invalidation with `mutation: result_replaced`, `decision_id` the slot, `row` 11 when the activity's code fingerprint changed (else `null`): every current result computed from the replaced one (registry lineage) becomes stale, and the decisions resting on the slot (`dependencies.RESTS_ON`: `policy` and `conclusion` for `split`, `fit.baseline`, `fit.logistic`) become `reconfirm_required`. Nothing is recorded when nothing is invalidated (an EDA or policy evaluation rerun). The `run` result then carries `invalidation` (`{mutation, row, reason, stale_results, stale_slots, reconfirm_required}`, or `null`). Rows 7 (`settings.bootstrap`) and 8 (`usage_label`) are classified by `effects` but no v0.1 command changes the bootstrap settings or a usage label, so they are not reachable; row 9 (`eda_added`) needs no action because an EDA result goes into its own slot (a new `eda.rate_by:<column>` slot adds, never replaces). Facts are never reconfirmed. A policy confirmation never marks its own evaluation stale (a current evaluation of the new rule is its precondition). Staleness propagates downstream through registry lineage.

An invalidation record in `state.invalidations` and `view.invalidations` has the keys `revision`, `decision_id`, `mutation`, `row`, `reason`, `stale_results`, `stale_slots`, `reconfirm_required`, `effects`, `previous` (`{value, confirmation, proposal_id}` of the replaced confirmation, or `null`). A reconfirmation request keeps the decision's previous `value` and `confirmation` visible and sets `reason`.

## 8. Extension points

### 8.1 Activities (Phase 2)

An activity is identified by its **slot** name, which is also its registry `activity`: `split`, `eda.target_rate`, `eda.special_values`, `fit.baseline`, `fit.logistic`, `policy.evaluation`. The plan's slots are `mlkit.study.state.ACTIVITY_SLOTS`. **Exception (Phase 4 integration):** `eda.rate_by` has one slot per column, `eda.rate_by:<column>` (`activities.slot_of`, `state.PER_COLUMN_SLOT_PREFIXES`); its registry entries keep `activity: "eda.rate_by"` and `params.column`, so exploring a second column never replaces the first. These slots are optional: they never block a step, are shown with the `train_eda` step, and a `code_fingerprint` change of `eda.rate_by` reaches every one of them. `run.result.slot` names the slot of a promoted result. A `{{slot:…}}` template may name a per-column slot (the longest known slot prefix wins).

1. **CLI command.** Create `framework/mlkit/study/cmd_run.py` (and `cmd_preview.py`) with
   ```python
   def configure(parser: argparse.ArgumentParser) -> None   # add arguments; --study and --format exist
   def main(args: argparse.Namespace) -> mlkit.study.commands.Outcome
   ```
   `cli.py` imports it only when `hypotrail run` (or `preview`) is invoked. Do not import pandas or scikit-learn at module level of `cmd_*` modules; import them inside the computation.
2. **State mutations.** Register `apply_command` actions:
   ```python
   commands.register_action(name: str, factory: Callable[[commands.Context], reliability.Handler]) -> None
   # Context(store: StudyStore, request_id: str); Handler(params: frozenset, run(state, params) -> result, check(params) -> None)
   commands.apply(study_dir, *, action: str, params: dict, request_id: str,
                  expected_revision: int, command: str = 'decide') -> Outcome
   ```
   Use dotted names, for example `run.reserve`, `run.promote`, `run.acknowledge`. `run` mutates state in memory only and raises `CommandRefused` to refuse.
3. **Preconditions.** Before reserving and again before promoting:
   ```python
   preconditions.require_activity(state, activity: str) -> None            # precondition_missing
   preconditions.missing_for_activity(state, activity: str) -> list[dict]
   preconditions.require_decision(state, decision_id, value=None, *, store=None) -> None
   ```
4. **Results.** Under the writer lock, after computing outside it:
   ```python
   code = registry.code_fingerprint(modules: Iterable[str]) -> {'fingerprint', 'modules'}
   eid = exposure.new_exposure_id() -> 'x_…'
   put = registry.put(store, *, activity, params, inputs, code, values, blobs=None,
                      partition=None, n_rows=None, exposure_id=None, execution_id=None,
                      started_revision=None, env=None)
         -> {'result_id', 'input_key', 'created', 'nondeterministic', 'same_input_results'}
   exposure.record(store, *, exposure_id, revision, activity, result_id, purpose, partition,
                   row_keys, dataset_sha256, columns, execution_id=None) -> dict
   ```
   * `inputs.results` maps a role to the upstream `result_id` (lineage); put decision values and `dataset_sha256` in `inputs` too, so `input_key` changes when they change.
   * `blobs` maps a name to bytes. Predictions use the name `predictions`: gzip CSV with header `row_key,y,score` (plan §3.4), read back by `read.Study.predictions`.
   * A policy evaluation records the evaluated rule(s) as `params.rule` or `params.rules`.
   * `put` never touches state. Promotion is a registered action that sets `state['current'][slot] = result_id` only if the `input_key` recomputed on current state is identical (plan WP2.1); otherwise record the execution under `state['executions']['late']`.
   * Record exposure for every read of rows, even for a result that is not promoted; use `result_id=None` when no result was stored (for example an interrupted execution).
   * Changing a split: compute `exposure.overlap(old_split, new_split, store=store)` and store it in the split result values.
   * A code change: `dependencies.effects(state, 'code_fingerprint', {'activity', 'fingerprint'}, {...})` then `dependencies.apply_effects(state, eff, revision=…, decision_id='code_fingerprint', store=store)` inside an action.
   * A replaced result (review fix H2): `run.promote` calls `dependencies.apply_replacement(state, slot, previous, new, *, revision, store, code_changed=False)`, which calls `apply_effects(..., seeds=[previous], keep=[new])`: `seeds` are results that no longer hold (their current descendants become stale), `keep` is never made stale. Staleness propagates through `inputs.results` without the history role `previous_split` (`records.HISTORY_ROLES`, `records.upstream(entry, history=False)`).
5. **Exit code 4** for an execution with an unknown outcome, including the `interrupted_execution_pending` refusal; `unknown_execution` refuses an acknowledgement of nothing (exit 2).
   **Acknowledgement words (D2, post-acceptance).** `hypotrail run --acknowledge-interruption E --user-words TEXT`: `--user-words` (the junior's verbatim reply after being told the outcome is unknown) is required and non-blank, otherwise `invalid_arguments`; it is refused with an activity. Since review fix L5 the words follow the confirmation rule (`commands.reply_problem`): a refusal, a bare acknowledgement, or words that name neither the interrupted activity nor its interruption (interrupted, unknown, outcome, restart, ...; `commands.ACKNOWLEDGEMENT_TOPIC`) are refused with `ambiguous_confirmation` and `details.reason` `negative_reply`, `bare_acknowledgement`, or `unrelated_reply`. The action `run.acknowledge` has the parameters `{execution_id, user_words}`; its result, and the execution history `.hypotrail/executions/<E>.json`, record `user_words`. An agent never acknowledges or reruns on its own.
6. **Payload schemas added in Phase 2** (additions; the five schemas of §3 are unchanged):

   | Schema | Emitted by | Keys |
   |---|---|---|
   | `hypotrail.run/1` | `run`, `run --acknowledge-interruption` | `schema`, `ok`, `study`, `action` (`run` or `run.acknowledge`), `request_id`, `replayed`, `revision`, `activity`, `execution_id`, `status`, `result_id`, `values`, `result`, `artifacts` |
   | `hypotrail.preview/1` | `preview policy` | `schema`, `ok`, `study`, `revision`, `kind`, `rules`, `models`, `evaluations`, `intervals`, `adopted`, `recorded` (`false`), `note`, `warnings` |

   `run.status` is one of `promoted`, `late_not_promoted`, `already_current`, `running`, `failed`, `interrupted_unknown`, `acknowledged`. An `acknowledged` result holds `execution_id`, `activity`, `status`, `restarted` (`false`), `started_revision`, `user_words`, `note`. `values` are the registry values of `result_id` (cite them only while the slot is current, §4); since review fix L6 a `late_not_promoted` payload has `values: null` and `result.citable: false` (the result is stored in the registry, but it describes a state that no longer holds). Since review fix L7, a `run` whose slot and `input_key` equal those of an active execution is refused with `execution_in_progress` (`details.execution_id`, `slot`, `activity`, `started_revision`) instead of computing twice. `preview` writes nothing and records no exposure; `validation_policy_selection` is recorded by `run policy.evaluate`. `preview.warnings` (post-v0.1 fixes, D4; additive) lists the G.12 warnings that bear on the previewed rules, as `not_yet_defensible` items words them (§4): `capacity_exceeds_validation` for the previewed capacities at least as large as the validation rows the fits scored, first, then `small_validation_partition` when the current split's validation partition is small; `[]` otherwise.

(the same for the generated notebook). * HTML numbers are `<data value data-result-id data-path title>` elements. Text shown as recorded rather than computed is wrapped in an element with `data-literal` ∈ `revision`, `ordinal`, `user_words`, `proposal`, `decision_value`, `case`, `identifier`, `parameter`, `environment`, `setting`, `message`, `category`, and since v0.2a (WP-A6) `structure` (a count recorded in the study state, such as the sealed final-test rows), `data_row` (a cell of the five example development rows), and `axis` (a chart tick); `check` ignores numbers there, except that an `axis` literal outside an `<svg>` element is `number_outside_result`. v0.2a (WP-A6, §11.5): a chart value label is an SVG `<text data-value data-result-id data-path>` element, verified like a `<data>` element; the format `pts0`–`pts2` shows a difference of fractions in percentage points and adds `data-scale="100"`, and `check` compares the shown text with the registry value times 100.
* v0.2a (WP-A4, §11.4): `verdict_contradicts_criterion` (warning), from the study check, when the conclusion adopts while `view.criterion.status` is `not_met` or `uncertain` (since WP-B6c, `view.criterion.judged_status`: the final-test status once opened).
* WP-B6c (§12, H2): `final_test_figure_outdated` (error) when a text cites a figure of `final_test.evaluation` or `diag.final_test` while `view.final_test.changed_after` names a decision of the choice (`cmd_check.CHOICE_CHANGES`: `policy`, `model_choice`, `model_variant`, `preprocessing`, `feature_availability`, `split`); a proposed conclusion with such a figure is refused (`literal_number_in_text`). Tracing binds the words of a number's sentence to the evidence (`cmd_check.scope_of`): "final test" / "test final" traces to `final_test.evaluation` and `diag.final_test` only, "out-of-fold", "cross-validated", "development", "validation" never to them; a percentage right after a rule word ("la règle des 20 %", "the top 20%") is a rule's share and matches only a `capacity_share` of that evidence; the bounds of a diagnostic's segments and intervals match only with interval words near.
* WP-B6c (§12, H4): `verdict_keeps_baseline_against_criterion` (warning) when the conclusion keeps the baseline while the criterion is met on the final test; the message explains the tension (a reason the criterion does not capture, or a verdict to reconsider). `value_mismatch` also reports (`details.reason: "double_scaled"`) a number shown with the points format (`data-scale="100"`) whose registry value is already in points: its mapping declares `unit: "percentage points"`, or its size is above 1.
* `check` always exits `0`; `clean` is false when a finding has severity `error`. A finding is `{code, severity, where, message, details?}`. Codes (severity): `number_outside_result`, `unknown_result_id`, `value_mismatch`, `stale_result_cited`, `feature_without_status`, `excluded_feature_used`, `untraceable_number`, `stale_number` (error); `causal_wording`, `forecast_wording`, `artifact_not_current`, `untracked_files` (warning); post-v0.1 (P7) `misattributed_delegation` (error): with `--text`, a recommended default credited to the analyst, junior, or user ("followed the analyst's recommended defaults", "defaults chosen by the junior"; `cmd_check.MISATTRIBUTED_DEFAULT`): a delegated decision is the assistant's recommended default, delegated by the analyst. Post-acceptance (D4): with `--text`, `--allow-user-text` (repeatable; a file, a pipe such as `<(printf ...)`, or `-` when `--text` is a file) gives text the junior wrote, whose numbers a draft may repeat (`traced` source `user_text`); the junior's recorded confirmation words and the rules of the current policy evaluation are literals too (`user_words`, `rule`); "percentage points" match a registered difference (`deltas`) times 100; U+2212 is a minus sign; rule identifiers (`capacity:100`) are never reported (`identifier`); numbers after "exit" and in a revision comparison ("revision 26 instead of 24") are exempt; since the acceptance rerun (R3), a result id prefix made only of digits is never reported either: a run of 6 or more digits (no sign, decimals, or percent) that follows "result", "result_id", "rid", "id", or "execution" ("(result 52659681)"), or that begins a `result_id` of the registry (`cmd_check.registry_ids`), is traced with source `identifier` and id `result_id` when it matches no figure; any other untraced number is still `untraceable_number`; the case and dataset files recorded in state are never `untracked_files`. WP-A9 (H2): the free-text pool (`--text`, the conclusion text, proposal texts) leaves out the paths of a result's internals (`cmd_check.INTERNAL_SEGMENTS`: null bands, bootstrap replicates and seeds, settings such as `max_groups`, coefficients and the intercept, tie-breaking details, fitted preprocessing, signal ranks and folds, `eda.quality`'s `ranges` and rare-category lists, and (WP-B1) per-fold metrics and fold sizes, the variant's penalty `C`, the final test's `refit` details and rule `parameter`s; the cross-validation spread and the final-test figures stay citable); and a number is bound to the results its nearby words name (`cmd_check.binding`): a metric word before it in its clause or in the three words after it ("précision", "recall", "AUC", "lift", "gain", "error", "missing", "distinct", a rate word) restricts the match to paths holding that metric; a count noun right after an integer ("50 clients", "90 validation rows") to count paths; an interval's `low`/`high` matches only near interval words or a range ("[21.2, 40.4]", "between", "32 to 53"); "model" without "baseline" leaves the baseline's values out. Recorded literals are not bound. The rendered deliverables cite by `data-result-id` and are unaffected. WP-B6b: in a diagnostic (`diag.*`, `cmd_check.DIAGNOSTIC_SLOTS`) the coefficients and their bootstrap bounds are citable (the agent reads them with the junior), while the refit check `point_check` and the drawn `scatter` points stay internal; a fit's raw coefficients stay internal. The success criterion as `status` shows it (`view.criterion`: `gain`, `low`, `high`, and the same of `final_test` once opened) is traced with `slot` `criterion` and `path` `criterion.<metric>.<key>` or `criterion.final_test.<metric>.<key>` (`cmd_check.criterion_items`; points for `precision_gain`, a share for `mae_reduction`), with the `result_id` of the evaluation it was read from; "gagne" (French) is a gain word. Both bounds of a range written with the numbers ("3.44 à 4.13", "40% to 54%") read as interval bounds (`cmd_check.RANGE_AFTER`, `RANGE_BEFORE`); "model year(s)" is not a model word; the numbers in a current result's group labels (`groups[].value` or `label`: "81 to 82 year (19xx)", "(2166.8, 2584.4]"; `cmd_check.group_labels`) are literals (source `group_label`); "calibration" and "Brier" bind to calibration paths, and a rate word admits a calibration bin's observed rate and bounds.
* Numbers written in words (post-v0.1, final acceptance F3; `mlkit/study/wordnum.py`). With `--text` and for the conclusion, `check` also reads common English and French word numbers **used quantitatively** and traces them like digits: cardinals 0–100 followed by a count noun ("the eleven kept columns", "quarante-trois clients", possibly one word between), "percent" / "pour cent" (a percentage), "percentage points" (a registered difference only), "dozen" / "douzaine" (12), ratios "k in N" / "k out of N" / "k sur N" ("one call in nine", "un client sur neuf"), and simple fractions followed by "of", "the", "de", "des", or a count noun ("half of the rows", "three quarters of", "la moitié des", "deux tiers des"). A ratio matches a registered rate `v` when `k / v` rounds to `N`; a fraction matches within `wordnum.FRACTION_TOLERANCE` (0.02); a cardinal matches as an integer. Such a number is `traced` (or reported) with `in_words: true` (and, in a finding, `kind` and `value`). Not read: "one" / "un" / "une" as a bare count ("one model"), "a single", ordinals ("first"), "the first half", cardinals above 100, vague quantities ("a few", "dozens", "most"), and a cardinal not followed by a listed count noun ("nine models"). In a regression study (M3) the target unit of the current results is a count noun too (`wordnum.unit_nouns`, a parenthesised note dropped): "about six mpg" is the count 6 and matches an error of 5.5 to 6.5 mpg. Like a digit, a word number traces to the first registered value it matches at its precision, so an unrelated value of the same size can trace it.
* Counts of the study's own structure (post-v0.1 fixes, D8). A count, in digits or in words, that matches no registered value but is followed (at most one word between) by a structural noun (`cmd_check.STRUCTURE_NOUNS`) is traced to the matching count of the view, with `source: "structure"` and an `id`: "columns", "features", "variables", "inputs", "predictors" (and "colonnes") to the length of a current, verified result's `values.features` list (`<slot>.features`) or a count of the feature availability decision or of an open proposal for it (`feature_availability.<decision|proposal id>.<all|usable|excluded|status>`); "groups" to the length of a current result's `values.groups` list; "steps", "pauses", "decisions" to the plan (`plan.steps`, `plan.pauses`) and the decisions (`decisions`). The same count before any other noun is not traced this way ("the seven columns we kept" is traced when the fit uses seven features; "seven calls" is not), and a structural count that matches none of these stays `untraceable_number`.
* v0.3 (WP-A, owner demo 2 R33; `mlkit.study.numtrace`, one tracer for `check --text`, the conclusion, and `decide propose`). **Rounding:** a number written with `d` decimals matches a registered value that rounds to it at `d` decimals, with its sign; a percentage matches a share times 100; a figure followed by "points" / "pts" (bare, as well as "percentage points", "pp", "points de pourcentage") matches a registered difference times 100 (`deltas`, a path with `difference`, or a last segment `gap`, `mean_absolute_gap`, `gain`), else a value already registered in points (`gain_points`, the criterion) or a recorded literal ("at least 5 points"), as written; a share is never a difference ("the base rate is 15.5 points" stays untraceable). Regression tests hold the exact R33 values. **Scope-bound matching:** a sentence that names a result (a slot with a dot such as `diag.binary` or `eda.rate_by:Month`, or a result id or a prefix of 6 or more hexadecimal characters) binds its numbers to that result only; `check --text ... --result RESULT` (repeatable: a result id, a prefix of 6 or more characters, or a slot; `invalid_arguments` when it names no result of the view or comes without `--text`) binds every sentence that names no result; a sentence that names a group label (`numtrace.LABEL_KEYS`: a segment's `column`, a group's `value` or `label`, a signal's `feature`; underscores may be spaces; labels of fewer than 2 characters, without a letter, or common words such as "yes", "other", "unknown", "may" are not names) matches that group's values first and never another group's. **Citable:** the single-feature signal's scores and median answer to their metric's words (a result's `metric`, `roc_auc` for "AUC"); a diagnostic's segment figures (`selected`, `n`, `precision`, `recall` of a group) are citable when the sentence names the group, and their bounds also need interval words; the per-fold figures of a policy evaluation (`by_fold`) are internal like a fit's. **Literals:** a decision's or an open proposal's fraction may also be written as its complement or as whole percents ("70/30" for a validation fraction of 0.3), never another of its numbers as a percentage ("capacity:100" does not allow "100%"); a figure bound to a metric word is never a setting (the bootstrap level 0.95), and a percentage bound to one is never a data-card cell or a final-test count ("100% precision"). In a regression study whose target unit is "points" (Diabetes), a bare "points" is that unit, not percentage points. Digits glued after a word of two or more letters ("the top250 clients") are a number (review fix L4, now in `check` too); identifiers are not (`p_5`, `r_1a2b`, a hexadecimal digest of 8 or more characters, `x2`).
* Retired proposals (post-v0.1, F3): figures of `withdrawn` or `superseded` proposals are never literals (only open proposals and current decisions are). A draft number that matches nothing else stays `untraceable_number`, and its `details.retired_proposal` and `details.proposal_status` name the proposal it repeats (`cmd_check.retired_proposals`).

* **Read-only**: it never writes (it runs in a read-only process too) and is never logged. Exit `0`; `--gap-minutes` below 1 is `invalid_arguments`. `--format text` prints the same report as Markdown (not a contract).
* Payload `hypotrail.session_report/1`, keys in order: `schema`, `ok`, `study`, `revision`, `since`, `sources`, `span`, `commands`, `refusals`, `decisions`, `pauses`, `runs`, `renders`, `checks`, `gaps`, `timeline`, `privacy`. `sources` is `{revisions, events, session_log: {enabled, entries, path, note}, artifacts_status}`; `span` is `{first, last, seconds, revisions}`; `commands` counts logged invocations by command and verb; `refusals` lists `{time, command, code, reason, revision, proposal_id, activity}`; `decisions` has one item per proposal `{proposal_id, decision_id, proposed_at, proposed_revision, outcome (open|confirmed|withdrawn|superseded), closed_at, seconds_open, basis, delegation_scope, refused_confirmations, refusal_reasons}`; `pauses` has one item per pause (1: `prediction_time`, `feature_availability`; 2: `split`; 3: `policy`, `conclusion` in a binary study, `model_choice`, `conclusion` in a regression study, M3) `{pause, decisions, opened_at, closed_at, seconds, proposals, confirmed, delegated, refused_confirmations}`, a pause closing when all its decisions are confirmed; `runs` lists executions `{execution_id, activity, rules, column, started_at, outcome, ended_at, seconds, slot, result_id}`; `renders` lists deliverable statuses after logged commands and `render_failed` events; `checks` lists logged `check` runs `{time, revision, target, clean, counts, codes, traced, in_words}`; `gaps` lists idle intervals longer than `--gap-minutes` (default 20) `{from, to, minutes}`, which usually separate chats or days; `timeline` merges revision records, operational events and session-log lines, each with `source` (`revision`, `event`, `session_log`) and `time`.
* `--since REV` keeps revisions after `REV`, and events and log lines from the time revision `REV` was committed.
* **Privacy**: the report copies no conversation content. From revision records it keeps identifiers only: action, revision, decision and proposal ids, `superseded`, basis, delegation scope, the invalidation's mutation and how many results it made stale, activity, execution id, rule identifiers, column, slot, status, and the first 8 characters of a result id. It never copies `user_words`, restatements, rationales, proposed values, reasons, or checked text.

**Session log** (`mlkit/study/sessionlog.py`): an opt-in, append-only file `.hypotrail/session-log.jsonl`, one `hypotrail.session_log/1` line per invocation of a mutating command, refusals included, and of a `status` or `check` read, written after the outcome is final (a write failure is ignored and never changes the outcome). Reads (owner decision at the companion integration, amending the review fix "reads write nothing"): of the read-only commands (`sessionlog.READ_COMMANDS`: `status`, `plan`, `preview`, `decisions`, `evidence`, `explain`, `check`), `status` and `check` (`sessionlog.LOGGED_READS`) append a line **when the log is on**, refused or not, because how often the junior checks is what an observation wants; with the log on they change the study tree by that line only. The other reads never append a line (a preview follows a slider); `HYPOTRAIL_SESSION_LOG=1` on one of them still creates the empty file, which is the opt-in. With the log off, every read leaves the study tree byte-identical. `export` and `session-report` never touch the file (`sessionlog.UNLOGGED`), so an export leaves the study tree byte-identical with the log on as well. The `preview` fields of a line below come only from lines written before the review fix. The companion panel runs its own reads with `HYPOTRAIL_SESSION_LOG=0`: its automatic re-reads are not the junior's checks (COMPANION-ADVANCED §5).

* Enabled by `HYPOTRAIL_SESSION_LOG=1` for that process, which creates the file; once the file exists, every later logged invocation (a mutating command, `status`, `check`) appends to it, in any chat, until the file is deleted. `HYPOTRAIL_SESSION_LOG=0` disables it for a process. A read-only process (`HYPOTRAIL_READ_ONLY=1`) never writes it, and `session-report` and `export` are never logged (`sessionlog.UNLOGGED`). Off by default: without the file and the variable, no command writes it, so `check` and `status` stay write-free.
* A line has `schema`, `time`, `command`, `verb`, `exit_code`, `ok`, `revision`, `options` (only `--basis`, `--delegation-scope`, `--proposal`, `--kind`, `--lang`, `--rule`, `--column`, `--channel`, `--acknowledge-interruption`, `--since`, `--about`, `--resolve`, `--max-groups`, the switches `--summary`, `--json`, `--intervals`, whether `--text` read a file or stdin, and how many `--allow-user-text` were given), and, as they apply: `decision_id`, `proposal_id`, `note_id`, `activity`, `refusal: {code, reason}` (the reason only when it is an identifier such as `bare_acknowledgement`), `replayed`, `status`, `basis`, `delegation_scope`, `invalidation: {mutation, stale_results}`, `artifacts` (name to status), `slot`, `result_id` (8 characters), `check: {target, clean, counts, codes, traced, in_words}`, `current_step`, `next_action` (its kind), `rules`. It never holds `--user-words`, a note's `--text`, `--restatement`, `--rationale`, `--value`/`--value-json`, `--reason`, request ids, checked or user text, or any message.

### 11.2 EDA governance

Every EDA result's `values` carry `question`, the question it answers. Additive value keys (§8.5):

* `eda.target_rate`: `interval` (Wilson 95 %, `{low, high, level, method}`); `eda.special_values` (binary): `interval` per special value; `eda.target_summary`: `mean_interval` (t, 95 %).
* `eda.rate_by:<column>`: per group `interval` (Wilson) and `null_band` (`{low, high}`: the range of that group's rate over the shuffles); per chart `null_band: {chart: {statistic, observed, null_min, null_max, outside}, shuffles: 19, seed: 20261019, note}`: the target is shuffled among the training rows `eda.NULL_SHUFFLES` times with `eda.NULL_SEED`; `chart.statistic` is the spread between the largest and the smallest group value among groups of at least `eda.MIN_GROUP_ROWS` rows (all groups when fewer than two qualify); `outside` is true when the observed spread exceeds every shuffled spread. `eda.mean_by:<column>`: the same with a t interval of each group mean.
* `eda.quality` (both tasks; new slot, optional, never blocks a step): the **development rows without the target**; no decision and no split needed (`preconditions.NO_REQUIREMENT_ACTIVITIES`). Values: `partition` (`development`, or `all` in a legacy study), `n_rows`, `n_columns`, `target_read` (`false`), `missing` (`[{column, n_missing, share}]`), `n_rows_with_missing`, `co_missing` (the ten most frequent patterns `[{columns, n_rows, share}]`), `duplicates` (`{n_rows, n_groups, definition}`: rows identical on every column but the target; v0.2b (WP-B3): when the case declares `duplicates: {policy: group}`, also `records`, the groups of identical records, target included, `data.duplicate_summary`, and the inputs hold `duplicates: "group"`), `cardinality` (non-numeric columns: `{column, type, n_distinct, rare: [{value, n_rows}], rare_rows}`, rare below `eda.RARE_CATEGORY_ROWS`), `ranges` (numeric columns, special values and missing cells apart: `{column, type, min, max, n_special, declared, n_below, n_above}`, compared with the case `range` when declared), `question`, `note`. Inputs: `columns` (every column but the target). Exposure: `structural_inspection`, partition `development` (`all` in a legacy study).
* `eda.correlation` (v0.3, WP-E2, R28; both tasks; new slot, optional, never blocks a step): the predictor-versus-predictor association matrix of the **development rows without the target**, like `eda.quality` (no decision and no split needed, `preconditions.NO_REQUIREMENT_ACTIVITIES`; structural, never a target look). Module `mlkit.study.correlation`. One measure per pair of candidate features: Spearman's rank correlation for two numeric features (signed; special values and missing cells left out, pairwise), Cramér's V with Bergsma's bias correction for two categorical features (a missing cell is its own category), the correlation ratio (eta) of the numeric feature's ranks across the categories for a mixed pair (both unsigned). Values: `partition`, `n_rows`, `target_read` (`false`), `columns` (`[{name, kind: numeric|categorical}]` in the case's order), `order` (the same names, an average-linkage clustering on 1 - |association|, leaves in dendrogram order), `pairs` (`[{a, b, measure: spearman|cramers_v|eta, value (null when fewer than 10 rows hold both or a column is constant), n_rows, flag}]`), `flagged` (the flagged pairs, strongest first), `n_flagged`, `level` (`correlation.COLLINEARITY_LEVEL`, 0.8: a pair is flagged when |value| >= level), `measures` (each measure in words), `question`, `note`. Inputs: `columns` (every feature), `special_values`. Exposure: `structural_inspection`, partition `development` (`all` in a legacy study). A target column (a counted look) is not offered in v0.3.
* v0.3 (WP-E2, R17): a numeric `eda.distribution` adds `numeric.zeros` (`{n_rows, share}` of the exact zeros, or `null` when a value is negative), `numeric.skewed`, and `numeric.log_bins` (`null` unless skewed): a column of non-negative values with at least 20 % exact zeros or a maximum at least ten times its third quartile gets bins of its positive values with edges 1, 3, 10, 30, ... between its smallest and largest positive value (`[{low, high, n_rows, share, closed}]`, closed on the left, the last on both sides). The ten fixed-width `bins` are unchanged.
* `eda.single_feature_signal` (both tasks; new slot): each candidate feature alone (the fits' design: special-value indicators, imputation, scaling or one-hot), scored out of fold on the training rows (5 folds, `StratifiedKFold`/`KFold`, seed `eda.SIGNAL_SEED`): `roc_auc` of a logistic model (binary) or out-of-fold `r2` of a linear model (regression). Values: `partition`, `n_rows`, `metric`, `folds`, `seed`, `signals: [{feature, availability (the study's decision), score, rank, flag}]`, `median`, `level`, `gap`, `questions: [{feature, score, availability, text}]`, `question`, `note`. A feature is flagged when its score reaches `level` (AUC 0.75, R² 0.8) or it is the top feature and exceeds the median by `gap` (0.15, 0.4). A flag only asks whether the value is known at the prediction moment: it never keeps or drops a feature. Inputs: `target`, `candidates`, `availability`, `special_values` (never `features`, which `check` reads as a fit's features). Exposure: `train_eda`.

**Ledger of target-involving looks.** `view.eda_looks` (`governance.ledger`) is `{target_looks, results, by_activity, note}`: every exposure record of purpose `train_eda` from an `eda.*` activity whose columns include the target, counted per run (a rerun is another look), with their result ids in order. `summary.eda_looks` is `{target_looks, results}`. It is a disclosure, not an alpha correction.

### 11.3 Decision `preprocessing`

Class b of the synthesis: proposed (the engine's default is `next_action.default_value` and `governance.DEFAULT_PREPROCESSING`), confirmed in the junior's words, parameters learnt on training rows only and applied unchanged to validation rows. Value: `missing` (`none`, `indicator`, or `{feature: none|indicator}`), `rare_category_min_rows` (training rows, integer `>= 0`; `0` keeps every category), `caps` (`{numeric feature: [q_low, q_high]}`, `0 <= q_low < q_high <= 1`), `log_transform` (distinct numeric features), optional `motivated_by` (result ids of this study's registry). Anything else is `invalid_value` (`details.field`, `default`). When proposed, the engine records `motivated_by` (`[]` when absent), `target_looks_before` (WP-A9, M1: the count of target-involving looks on training rows before the proposal, `governance.ledger`) and `data_contingent`: true when any motivating result read the target (`governance.uses_target`: the target-reading activities, `eda.distribution` of the target, a stratified `split`) or when `target_looks_before` is above 0, named or not; a given `data_contingent` or `target_looks_before` that differs is `invalid_value`; the report's decision card names the questions of the motivating results and says in words whether the preparation was chosen after looking at the outcome; an unknown result id is `invalid_value` (`details.unknown_results`).

The default (`{"missing": "none", "rare_category_min_rows": 0, "caps": {}, "log_transform": []}`) is what the models did before the decision existed: results stay comparable. In a study with the decision, the candidate fits (`fit.logistic`, `fit.linear`) record `inputs.preprocessing` (the confirmed parameters, without `motivated_by`) and `values.preprocessing: {value, fitted: {missing_indicators, rare_categories: {column: {kept, folded}}, caps: {column: [low, high]}, log_transform, ignored}, note}` (`fit.prepare`): a missing-value indicator `<column>=(missing)` is added for a used feature whose training cells hold a missing value (unless a special value read as missing already gives it one); categories with fewer training rows than that minimum, and validation categories unseen in training, become `(rare)`; caps clip at the training quantiles; the log transform is `sign(x) * log(1 + |x|)`, after the caps. The baseline fit and the EDA never apply it. Mutation rows 14 and 15 (§6). `not_yet_defensible` lists `data_contingent_preprocessing` while a confirmed preprocessing is data-contingent.

### 11.4 Decision `success_criterion`

Fixed after the split decision, before any model is fitted (the fits need it). Since v0.3 (WP-C, remarks R18, R19) it is a metric and a minimum: the agent offers the metric options of `next_action.criterion_options` (§3.1) with the reference value (the base rate of the development rows) and the illustrative translation per 1,000 actions, before asking for the minimum. Binary: the minimum precision gain (`precision_gain`, the default, tied to a capacity or share action) or recall gain (`recall_gain`, for a threshold action, where the two differ) over the baseline at the adopted rule, in percentage points; with a `recall_gain` value `gain`, `low`, `high` read `deltas.<model>.recall` (and the final-test criterion the recall deltas of `final_test.evaluation`), via `criterion.assess`; the fits' code is unchanged, so existing results stay current. Regression: the minimum relative reduction of the mean baseline's validation MAE. `view.criterion` (`governance.assess`) is `{decision_status, value, metric, status, result_id, rule, model, gain, low, high, minimum, unit, interval_includes_zero, verdict, contradicts_verdict}`: binary `gain` is `100 × deltas.[fit.logistic].precision.point` of the current `policy.evaluation` at the adopted rule (else the rule of the open policy proposal), `low`/`high` its paired interval in points; regression `gain` is `-deltas.[fit.linear].mae.point / models.[fit.baseline].mae` of the current `evaluate.regression`, with the interval mapped the same way. `status`: `met` (gain at least the minimum and an interval that excludes 0), `uncertain` (the point reaches it, the interval includes 0), `not_met`, or `not_assessed`. `contradicts_verdict` is true when the conclusion's verdict (confirmed, to confirm again, or proposed) is `adopt_policy` or `adopt_model` while the judged status (`judged_status`, below) is `not_met` or `uncertain`; `check` then warns `verdict_contradicts_criterion` and `not_yet_defensible` lists it. `summary.criterion` holds `decision_status, value, status, gain, low, high, minimum, unit, rule, result_id, contradicts_verdict`. **Cross-validation.** `run split` with a cross-validation value assigns each development row to a fold (`activities.compute_cv_split`): `StratifiedKFold` (shuffled, seeded) on the binary target or on `partition.QUANTILE_BINS` target quantile bins, or contiguous blocks in time order (one function builds the folds, `activities.assign_folds`, which also takes an optional `groups` array for grouped folds; `activities.time_order_column`: the time column, else the order's column, else `line`; ties broken by line; each block is predicted by a model fitted on the other blocks, later ones included: stability across periods, not a forecast). Each fold's out-of-fold scores come from a model fitted without that fold, so the scores of different folds are not on one scale (with temporal folds, each period is scored by a model of other periods). Under cross-validation the policy evaluation (`params.selection: "within_fold"`, `inputs.fold_split`: the split whose folds it reads) applies a `capacity:k` or `share:p` rule within each fold: the fold keeps the rule's share of its rows (`share_capacity(p, n_fold)`, `p = k / n` for a capacity; `policy.fold_capacities`) and selects that many of its best-scored rows by its own model; the counts are summed (`policy.evaluate(..., groups)`). The development diagnostics (`diag.binary`) and `preview policy` apply the rule the same way (`confusion.selection_scope`; the curve's points are the top share of each fold, the AUC pools the rows). The final test is scored by one model: its rule is applied to all its rows. ## 13. Model diagnostics (v0.2b, WP-B4, remark R9)

Additive: no schema version changes, nothing migrated. Three activities (`activities.DIAG_ACTIVITIES`: `diag.binary` and `diag.final_test` in a binary study, `diag.regression` and `diag.final_test` in a regression study; `activities.task_activities` lists them last). Running the activity of the other task is `invalid_arguments`; `diag.final_test` in a study created before WP-B1 is `invalid_arguments` (no final test). Each slot is the activity name. Until v0.3 none was a plan step; since v0.3 (WP-F1, R28, §14) the development diagnostics are an activity of the `models` step (before the variant decision) and of the choice step, so `next_action` runs them. A stale diagnostic never blocks the opening of the final test (`preconditions.final_test_missing` ignores `diag.` slots as it ignores `eda.` slots). The computation is `mlkit.study.diagnostics` (numpy, pandas and scikit-learn, imported lazily).

**Development diagnostics** (`diag.binary`, `diag.regression`; `activities.DEVELOPMENT_DIAGNOSTICS`). Preconditions as an evaluation (`preconditions.missing_for_activity`, prefix `diag.`): the activity decisions, the success criterion and the preprocessing, a current split and current fits, and in a WP-B1 study, once `model_variant` is confirmed, a current fit of every declared variant (v0.3, §14: before the variant decision, the candidate and the baseline only). They read back the stored predictions of the candidate and of the variant (`params.models`, the baseline excluded): out of fold under cross-validation (`params.evaluation: "out_of_fold"`, registry partition `development`), the validation predictions otherwise (`validation`). `inputs.results` holds `split` and each model's fit (lineage: a refit or a new split makes them stale). They read the rows those predictions describe (features and target) for the segments, the examples and the residuals by variable, and the rows the coefficients come from for the bootstrap. Exposure purpose `development_diagnostics` (`records.EXPOSURE_PURPOSES`), partition `development` (one record under cross-validation; `validation` and `train` otherwise); it reads the target, so `view.eda_looks` counts each run as one look (`governance.ledger`, by activity `diag.binary` or `diag.regression`; `governance.TARGET_ACTIVITIES` lists the three activities). `params`: `{models, evaluation, coefficients: {replicates, seed, level}, segments}` plus `{rule, rule_source}` (binary) or `residual_columns` (regression).

**The rule of the binary diagnostics** (`activities.diagnostic_rule`): the adopted policy rule (confirmed or awaiting reconfirmation, `rule_source: "adopted"`), else the rule of the latest open policy proposal (`proposed`), else `share:p` with the case's `scenario_defaults.capacity_share` (`scenario_default`), else `diagnostics.DEFAULT_RULE` `share:0.1` (`engine_default`); `diagnostics.RULE_SOURCES`. **Invalidation.** A `policy` confirmation whose rule differs from the rule the current `diag.binary` was computed at (its registry `params.rule`; v0.3, WP-A, R34) adds `diag.binary` to `recompute` (`dependencies.effects_at`, `dependencies._diagnostics_follow_the_rule`, `commands._diagnostic_rule`): its current result becomes stale with the confirmation's reason. Adopting the rule they were computed at, a first adoption included (the scenario's share, a proposed rule), keeps them current; before v0.3 a first adoption always made them stale. The report names the rule's source in words that stay true after an adoption ("the teaching scenario's share, before any rule was proposed"). Refits (rows 1, 2, 4, 14, 17), a replaced fit, and a code change reach the diagnostics through lineage and the code fingerprint (§6).

**Final diagnostics** (`diag.final_test`). Refused before the opening with `precondition_missing`, requirement `final_test_opened` (`preconditions.FINAL_DIAGNOSTICS`); then nothing is read and nothing recorded. After the opening (and with `final_test.evaluation` in `state.current`, else requirement `result_current`) it reads the predictions blob of the one final evaluation (`inputs.results: {final_test.evaluation}`), and the final-test rows through `data.load_final_test` (its second reader, after the opening only) for the segments, the examples and the residuals by variable. Exposure purpose `final_evaluation`, partition `final_test`. `params`: `{model, evaluation: "final_test", segments}` plus `rule` (the final evaluation's `rule_final`) or `residual_columns`. Like the final evaluation it stays current after later changes, and `partition.AFTER_SLOT_PREFIXES` does not list `diag.`: running diagnostics, before or after the opening, is never "a change after the final test".

**Values.** Top-level keys, in order: `diagnostics.BINARY_KEYS` (`question`, `evidence` (`development`), `purpose` (`development_diagnostics`), `partition`, `evaluation`, `n`, `n_positive`, `base_rate`, `rule`, `rule_source`, `segment_columns`, `segment_rule`, `models`, `coefficient_rows`, `note`), `diagnostics.REGRESSION_KEYS` (`question`, `evidence`, `purpose`, `partition`, `evaluation`, `n`, `target`, `unit`, `residual_columns`, `residual_definition`, `target_transform` (`null`: the engine has no target transform), `smearing` (`{applies: false, implemented: false, note}`: Duan's retransformation would be needed for a log target; not implemented), `normality_note` (normality is a post-fit question about residuals; Lumley et al. 2002), `models`, `coefficient_rows`, `note`), `diagnostics.FINAL_BINARY_KEYS` and `diagnostics.FINAL_REGRESSION_KEYS` (`evidence: "final"`, `purpose: "final_evaluation"`, `partition: "final_test"`, `evaluation: "final_test"`, plus `model` (the chosen configuration's model) and `final_evaluation` (its result id); no `rule_source`, no `coefficient_rows`). `evidence` is one of `diagnostics.EVIDENCE` (`development`, `final`). `models` maps each model slot (the candidate and the variant; for `diag.final_test` the chosen model only) to its diagnostics, keys `diagnostics.BINARY_MODEL_KEYS` or `diagnostics.REGRESSION_MODEL_KEYS` (`coefficients` in the development diagnostics only):

| Key | Binary content |
|---|---|

New logistic fits record `solver: newton-cholesky` and `tol: 1e-8` in their params (fits recorded earlier keep scikit-learn's default L-BFGS, which could stop before the optimum) |

**Report and notebook.** The report has a "Model diagnostics" section (`render_diagnostics.section`, `id="diagnostics"`) after the comparison: a "Development evidence" part (`id="diagnostics-development"`; after the opening a notice `data-opening="before"` or `"after"` says whether it was computed before or after the final test was opened) and a "Final evidence" part (`id="diagnostics-final"`: `data-final="sealed"` while sealed, `"pending"` when opened without diagnostics, else the chosen model's diagnostics, `data-evidence="final"`). Binary: the models side by side, the confusion matrix, the gain curve (`data-chart="diag_gain"`), the calibration plot (`diag_calibration`) and its bins, the segments, the coefficients and the examples; regression: the models side by side, residuals against the prediction (`diag_residuals`), predicted against observed (`diag_observed`), the quantile-quantile plot (`diag_qq`), the residual distribution, the heteroscedasticity indicator, residuals by variable, the coefficients, the largest errors and the target-transform note. Every number is cited; `check` stays clean. The annex leaves out `scatter` points (`render_html.ANNEX_SKIPPED`). The generated notebook's choice step gains `recompute_dev_diagnostics` and its final-test step `recompute_final_diagnostics` (`code_cells.diagnostics_cell`): from the stored predictions, the confusion matrix at the rule (counts, exactly) and the calibration bins and Brier score (to `TOLERANCE`), or the residuals by bin of prediction; not generated when the rule's cut splits a tie. `hypotrail evidence` gives the values like any result, with headlines (`content/evidence.yaml`); the companion's reading of them is CLI-CONTRACT-COMPANION §14.

## 14. Trial budget, nested tuning, and model families (v0.3, WP-F1, ADR 0007)

Additive: no schema version changes, nothing migrated. A study created before WP-B1 has no variant and is unchanged. A WP-B1 study keeps its `model_variant` value, read as one variant (the budget then has one variant used), and its first variant's identity. **Existing results stay current**: WP-F1 changes the fingerprinted modules `activities`, `fit`, `governance` and `diagnostics`, but every configuration a study could hold before computes the same values, so their pre-WP-F1 source digests are declared equivalent (`code_compat.EQUIVALENT`, read by `Study.code_changed` through `code_compat.equivalent`); an opened final test keeps its one evaluation citable. Such earlier results only lack the new additive keys (`model_selection`, `linear_checks`); the shortlist then says `rerun_diagnostics`. A run after WP-F1 records the new fingerprint (its input key differs, so asking for it computes a new result). The pure part is `mlkit.study.trials` (no pandas); the fits are `mlkit.study.families` (scikit-learn and `interpret-core`, imported lazily).

**Decision `model_variant`.** The value is `{"variants": [V, ...]}` (`trials.LIST_KEY`), one to three variants (`trials.MAX_VARIANTS`), each `{kind, ..., question}`; `question` (`trials.QUESTION_KEY`) is the question the variant answers, a non-empty sentence of at most `trials.MAX_QUESTION` characters. The kinds (`trials.KINDS`, `state.VARIANT_KINDS`; keys `trials.KIND_KEYS`): `regularisation` (`strength`: `weak` or `strong`, `trials.STRENGTHS`), `drop_group` (`group`), `tuned` (no parameter: the candidate's penalty chosen by nested cross-validation), `family` (`family`: `ebm` or `hgb`, `trials.VARIANT_FAMILIES`). A v0.2b value (`{"kind": "regularisation", ...}` or `{"kind": "drop_group", ...}`, no question) stays accepted and is read as a list of one (`trials.variants_of`); `tuned` and `family` exist in the list form only. `commands.validate_variant` refuses with `invalid_value` a value that `trials.check_value` rejects (details `kinds`, `strengths`, `groups`, `families`, `max`), and a value that would bring the number of distinct variant models the study ever confirmed above three (`details.budget: {max, used, would_use}`; `trials.used_specs` reads the confirmed `model_variant` proposals, the question left out, `trials.spec_of`, `trials.spec_key`). The engine's draft (`next_action.default_value`, `state.default_variant`, `trials.draft`) is `{"variants": [{"kind": "tuned", "question": ...}]}`, the question in the study language. `decide propose` returns `data_contingent: true` and a reason `{families, diagnostics, flags, text}` for a value with a `family` variant while the current development diagnostics flag a pattern (`trials.data_contingency`), `false` otherwise.

**Slots and runs.** Variant *i* is fitted into `trials.variant_slot(i)`: `fit.variant`, `fit.variant:2`, `fit.variant:3` (`trials.VARIANT_SLOTS`; `trials.declared_slots(state)` lists those the confirmed value names). `hypotrail run fit.variant:2` (`activities.VARIANT_SLOT_NAMES`, accepted by the CLI; `activities.resolve` maps it to the activity `fit.variant` with option `index`) runs the second. The registry entry keeps `activity: "fit.variant"`; variants 2 and 3 add `params.variant_index` (the first has none, so its identity is unchanged). `preconditions.missing_for_activity` refuses a variant the decision does not name (`precondition_missing`, requirement `variant_declared`); `activities.model_plan` refuses it too. The variant step of the plan lists the declared slots (`fit.variant` while none is named). `records.POLICY_MODELS` adds `fit.variant:2` and `fit.variant:3`: a policy may be `"<rule>@fit.variant:2"` (refused, `invalid_value`, when the decision does not name that variant). A regression `model_choice` may be any declared slot (`commands.model_choices`), and the conclusion `adopt_model` accepts a chosen variant. The evaluations compare every declared variant with the candidate (`activities.compared_models`, `activities.variant_pairs`: `comparisons` has one entry per variant); a policy evaluation adds `gain_points_variants` (`{slot: {model, ...}}`) for variants 2 and 3 next to `gain_points_variant`. `policy.evaluation`, `evaluate.regression`, and the diagnostics once the decision is confirmed, need every declared variant fit current. The opening of the final test needs the declared variant fits current (`preconditions.final_test_missing`); a stale result of a variant the decision no longer names does not block it.

**Nested tuning** (`tuned` and `family` variants). `params.tuning` is `trials.grid(family, task)`: `{parameter, values, meaning, inner_folds, seed, metric, tie, method}`, the grids of `trials.GRIDS` (logistic `C`: 0.01, 0.1, 1, 10, 100; ridge `alpha`: 100, 10, 1, 0.1, 0.01; EBM `interactions`: 0, 3; boosting `max_depth`: 2, 4; simplest first), `trials.INNER_FOLDS` (3) shuffled folds seeded `trials.INNER_SEED` (stratified on a binary target when each class has three rows), metric `roc_auc` (binary) or `mae` (`trials.INNER_METRIC`), a tie keeping the first value. Within each outer fold, `families.choose` fits every grid value on the inner training rows (the preparation learnt there) and scores the inner held-out rows; the outer model is refitted with the best value. A `tuned` regression variant is a ridge (`params.model: "ridge"`). The inner folds are not temporal and do not keep the case's duplicate groups together: this affects the choice of the value only, never the out-of-fold figures, which keep the outer folds. Values gain `tuning`: the grid, `per_fold: [{fold, value, inner_scores: [{value, mean}]}]`, `development: {value, inner_scores}` (the value chosen on every development row, the fit whose terms are shown), and `note`. Under a train/validation split the value is chosen on the training rows (`tuning.per_fold` empty). `final_test.evaluation` of a tuned or family configuration chooses its value by an inner cross-validation of the development rows and records `tuning` (and `family`) in its values. Diagnostics reuse `tuning.development.value` for the coefficient bootstrap.

**Model families** (`trials.CATALOGUE`, `trials.FAMILIES`: `linear`, `ebm`, `hgb`; `trials.NONLINEAR_FAMILIES`). A `family` variant's `params` are `{model, family, implementation, preprocessing, special_values, settings, tuning, seed}` (plus `variant_index`): `ebm` is `interpret.glassbox.ExplainableBoosting{Classifier,Regressor}` with `trials.EBM_SETTINGS` (`outer_bags` 1, `inner_bags` 0, `max_rounds` 500, `learning_rate` 0.05, `n_jobs` 1), `random_state` the seed; `hgb` is `sklearn.ensemble.HistGradientBoosting{Classifier,Regressor}` with `trials.HGB_SETTINGS` (`max_iter` 100, `learning_rate` 0.1, `early_stopping` false), categorical inputs ordinal-encoded as native categories (at most 250 per column), fitted and scored with one OpenMP thread (`families.one_thread`). The inputs are the candidate's (features, special-value indicators, the confirmed preprocessing). `interpret-core` is pinned (`0.7.3`); the modules `interpret._version` and `sklearn` are in the code fingerprint of `fit.variant` and `final_test.evaluation` (`activities.MODULES`), and the values record `versions` (`families.versions`). Values of a family fit: `{model, family, features, special_value_indicators, n_train, versions, settings, n_train_positive (binary) or target and unit (regression), validation, predictions, tuning, family_diagnostics, preprocessing, variant, variant_index?, evaluation, cross_validation}`, no `coefficients`. `family_diagnostics` (the family's own diagnostics, registered with the fit): for `ebm`, `{kind: "ebm_terms", terms: [{term, kind: main or interaction, importance, shape}], n_terms, interactions, score_scale, importance, note}` (`families.ebm_terms`; a main term's `shape` is `{type: continuous, points: [{from, to, score}]}` with at most `families.MAX_SHAPE_POINTS` points, or `{type: nominal, points: [{value, score}]}` with the `families.MAX_CATEGORY_POINTS` largest; at most `families.MAX_TERMS` terms), from the fit on every development row; for `hgb`, `{kind: "permutation_importance", columns: [{column, importance, per_fold}], metric, repeats, definition, note}` (`families.permutation_importance`, `families.combine_importance`: the drop in ROC AUC or the rise in MAE when a column is shuffled, `families.PERMUTATION_REPEATS` repeats, on each outer fold's held-out rows, weighted by rows). In the development diagnostics a family model's entry has `coefficients: null` and gains `family_diagnostics` (copied from its fit); a tuned model's entry gains `tuning`.

**Linear checks** (`diagnostics.linear_checks`). `diag.binary` and `diag.regression` add, last, `linear_checks` (`diagnostics.LINEAR_CHECK_KEYS`: `{model, nonlinearity, interaction, calibration_slope, flags, alpha, method, note}`) for the candidate: `nonlinearity` `[{feature, bins: [{bin, n, low, high, gap, se}], statistic, df, p_value, level, flagged}]` for each numeric feature the model uses with more than `diagnostics.CHECK_BINS` values (the observed rate minus the mean score, or the mean residual, in five quantile bins; `sum((gap/se)^2)` against a chi-square; `level` `diagnostics.CHECK_ALPHA` 0.01 divided by the features tested); `interaction` `[{feature, groups: [{value, n, slope, se}], q, df, p_value, level, flagged}]` for the segment columns (`diagnostics.segment_columns`; groups of at least `diagnostics.MIN_SEGMENT_ROWS` rows and, binary, `diagnostics.MIN_SEGMENT_POSITIVES` rows of each class; Cochran's Q of the calibration slopes); `calibration_slope` `{slope, se, low, high, band, flagged, definition}` (`diagnostics.SLOPE_BAND` [0.8, 1.2], flagged outside it when the 95 % interval excludes 1); `flags` `[{check, feature, p_value, slope?}]`.

**Shortlist** (`view.model_families`, `trials.shortlist`, keys `trials.SHORTLIST_KEYS`): `{constraints: {interpretability, declared}, evidence: {source, checked, flags, checks}, families: [{family, model, interpretability, implementation, diagnostics, default, allowed, excluded_reason, motivated, words}], shortlist, recommendation, text, texts, data_contingent, catalogue}`. `constraints` reads the case's optional `constraints.interpretability` (`trials.INTERPRETABILITY`: `required`, `preferred`, `none`; absent is `none`; CASE-CONTRACT §Constraints); `required` excludes `hgb` (a black box). `evidence.source` is the current development diagnostics' result id. `recommendation` is `run_diagnostics` (no diagnostics yet; shortlist `[linear]`), `rerun_diagnostics` (diagnostics computed before WP-F1, without `linear_checks`), `stay_linear` (no flag), or `compare_nonlinear` (a flag: `[linear, ebm, hgb]`, the glass box first, `hgb` only when allowed). `text` is in the study language, `texts` is `{en, fr}`.

**Selection** (`trials.select`, keys `trials.SELECTION_KEYS`; one configuration `trials.CONFIGURATION_KEYS`). `policy.evaluation` and `evaluate.regression` that compare variants record `inputs.variants` (the declared variants without their questions) and `inputs.trial_budget`, and add `model_selection` to their values (the B6c key `selection`, the scope of a within-fold rule, is unchanged): `{available, metric (roc_auc or mae), direction, folds, configurations: [{slot, kind, family, question (null when stored), words, per_fold, mean, sd, se, difference: {against, mean, sd, se, low, high, within_fold_noise, definition} or null, within_one_se, complexity}], best, one_se: {pick, best, bound, se_of_best, source, text, texts, simplicity}, optimism: {estimate, metric, configurations, per_fold, method, source, text, texts, note}, advice: {code, stop, noise, largest_difference, text, texts}, budget: {max, declared, used, remaining, legacy}, trials, note}`. The per-fold metric is each fit's `cross_validation.per_fold` ROC AUC or MAE; `se` is the standard deviation over folds divided by the square root of the folds; `difference` is the paired per-fold difference with the candidate, ± one standard error; the one-standard-error rule (`trials.ONE_SE_SOURCE`) keeps the simplest configuration whose mean is within one standard error of the best (simpler: the linear family, then fewer features, then a stronger penalty; a tie keeps the candidate); the optimism (`trials.OPTIMISM_SOURCE`, Tibshirani & Tibshirani 2009) is the mean over folds of the gap between the fold's best configuration and the configuration best on the mean; `advice.code` is `budget_exhausted` (three variants used) or `fold_noise` (every variant's difference within one standard error of zero), both with `stop: true`, `may_continue`, `no_variant` (`noise`: the candidate's standard error), or `not_available` (no cross-validation). `view.model_selection` (`trials.selection`) is the same reading of the current fits with the study's budget, `null` in a study without the variant decision.

**Diagnostics in the plan (R28).** In a WP-B1 study the plan lists the development diagnostics (`state.DIAG_SLOT`): in the `models` step after the fits while the variant decision is not confirmed, and in the choice step (`policy` or `model_choice`) after the evaluation (`state._wp_f1_steps`); `next_action` is `{kind: run, activity: "diag.binary"}` (or `diag.regression`) when they are missing or stale. Before the variant decision the diagnostics need the candidate and the baseline only; the variant decision confirmed with other variants (its first confirmation included) makes them stale (`dependencies._diagnostics_follow_the_variants`), and a policy adopted at another rule than theirs too (§13). Dependency row 17 now refits only the variants whose model changed or that the decision no longer names (`trials.changed_slots`); restating the same variants (a question reworded, a v0.2b value written as a list) has no effect (`unchanged_value`). The rows that refit the candidate refit every variant fitted.

**Report and notebook.** The report has a "Variants and model families" section (`render_trials.section`, `id="variants"`, in the study language) after the comparison: the budget (recorded literals), the shortlist with the flags of the linear fit (cited from the diagnostics), the configurations compared fold by fold with the one-standard-error pick, the optimism and the advice (cited from the evaluation's `model_selection`), the value chosen per fold, and each family's diagnostics (cited from the variant fits). With several variants, the comparison table names each row's model. The generated notebook's variant step gains `recompute_selection` (`code_cells.selection_cell`): a pandas table of the per-fold metrics from the fits, the means, standard errors, best mean and optimism recomputed and asserted equal to the stored `model_selection`.
