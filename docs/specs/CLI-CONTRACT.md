# CLI and study contract (`hypotrail`, v0.1)

Status: **frozen** at the end of Phase 1 (plan `docs/plans/V0.1-IMPLEMENTATION-PLAN.md` §4, §8, §9 bis). Implemented in `framework/mlkit/study/`. Frozen by `framework/tests/study/test_contract_freeze.py`.

Phase 2 (activities) and Phase 3 (deliverables) are built in parallel on this contract. They may **add** what the extension points below allow. They must not rename, remove, or change the meaning of anything listed here. A change goes through the integrator: bump the schema version (`/1` to `/2`), update this document and the contract test in the same commit.

Consumers: the chat agent (Claude Code under directive A1), the HTML report, the generated notebook and workbench, and later a webview client (ADR 0002). All of them read the same JSON and write only through the same commands.

## 1. Invocation

```sh
uv run --project framework hypotrail <command> ... --study DIR
python -m mlkit.study.cli <command> ... --study DIR     # same program
```

| Rule | Detail |
|---|---|
| Study location | `--study DIR` is required by every command. The study is never taken from the current directory or from `OSML_ROOT`. A study is a directory with a `.hypotrail/` marker. |
| Output | Exactly one JSON document on stdout, then a newline. `--json` selects it explicitly; `--format text` prints a short human summary instead (not a contract); since v0.2a (WP-A1) `explain` and `evidence` print readable text there too, never JSON, and `hypotrail --help` lists every command, extensions included, with one line each. Nothing is written to stderr on a handled outcome. |
| Mutations | Every mutation is one request `{request_id, expected_revision, action, params}` applied by `mlkit.reliability.apply_command` under the writer lock. `--request-id` and `--expected-revision` are required on every mutating command. |
| Idempotency | Replaying a `request_id` with the same request returns the stored receipt with `replayed: true` and writes nothing. The same `request_id` with a different request is refused (`idempotency_conflict`). A replay is recognised before the revision check. |
| Revision | `expected_revision` must equal the current revision, otherwise `stale_revision` with `details.current_revision` and `details.changes_since` (the revision records the client has not seen). |

### Commands (v0.1)

```text
hypotrail init --case CASE --study DIR [--lang en|fr]
hypotrail status --study DIR [--since REV] [--json] [--summary]
hypotrail plan --study DIR
hypotrail decide propose DECISION (--value TEXT | --value-json JSON)
                 --restatement TEXT --rationale TEXT [--lang en|fr]
                 [--restatement-en TEXT] [--restatement-fr TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail decide confirm (PROPOSAL | --proposal PROPOSAL) --user-words TEXT
                 [--channel chat|cli|webview] [--actor NAME]
                 [--basis explicit|delegated_default]
                 [--delegation-scope this_decision|standing] [--agent-concern TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail decide withdraw PROPOSAL [--reason TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail decide note (--about DECISION | --resolve NOTE_ID | --withdraw NOTE_ID) --text TEXT
                 [--kind hold|correction]
                 --request-id ID --expected-revision REV --study DIR
hypotrail mode set guided|training|express [--user-words TEXT]
                 --request-id ID --expected-revision REV --study DIR
hypotrail data --study DIR [--format json|text]
```

`--channel` defaults to `chat`, `--actor` to `user`, and `--basis` to `explicit` (§5). `--delegation-scope` has no default and goes with `--basis delegated_default` only (§5, R1). Reserved extension commands, absent in Phase 1 and refused with `unsupported_capability` until their module exists: `run`, `render`, `check`, `preview` (§8). Phase 3 adds `render` and `check` (§8.3). Post-v0.1 adds the read-only `session-report` (§8.6) and `decide note` (P2, §5.1); the post-v0.1 fixes add `decide note --withdraw` (D5, §5.1). v0.2a (ADR 0005, §5.2) adds `init --lang`, `decide propose --lang/--restatement-en/--restatement-fr`, `decide confirm --proposal` (the same as the positional `PROPOSAL`; giving both or neither is `invalid_arguments`) and `--agent-concern`, `decide note --kind correction` (`--user-words` is an alias of `--text`), and `mode set`. v0.2a (WP-A4, §11) adds the read-only `data` (the data card) and the decisions `success_criterion` and `preprocessing`.

## 2. Exit codes

| Code | Meaning |
|---|---|
| `0` | Success, or replay of a committed request |
| `1` | Internal error (unexpected exception); the payload is still `hypotrail.error/1` with code `internal_error` |
| `2` | Refusal without effect (any `hypotrail.error/1` with a stable code, including invalid arguments) |
| `3` | The command committed, but an artefact is `stale` or `failed` after rendering (WP3.4) |
| `4` | An execution has an unknown outcome (WP2.1, `run`) |

`status` and `plan` return `0` even when the study has interrupted executions or stale artefacts: they report them in the view.

## 3. Payload schemas

Every payload is a JSON object whose first keys are `schema` and `ok`. Keys are listed in their emitted order. Clients must ignore keys they do not know; producers must not remove listed keys within a schema version.

| Schema | Emitted by | Keys |
|---|---|---|
| `hypotrail.init/1` | `init` | `schema`, `ok`, `study`, `revision`, `case`, `dataset`, `structural_exposure`, `final_test`, `plan`, `next_action`, `agent_instructions`, `ignored_sources`, `note`, `notices`, `deliverables` |
| `hypotrail.status/1` | `status` | `schema`, `ok`, `study`, `revision`, `since`, `changed`, `changes_since`, `view` |
| `hypotrail.plan/1` | `plan` | `schema`, `ok`, `study`, `revision`, `steps`, `current_step`, `next_action` |
| `hypotrail.decide/1` | `decide …` | `schema`, `ok`, `study`, `action`, `request_id`, `replayed`, `revision`, `result`, `artifacts` |
| `hypotrail.error/1` | any refusal | `schema`, `ok` (`false`), `command`, `error` |
| `hypotrail.summary/1` | `status --summary` | `schema`, `ok`, `study`, `revision`, `since`, `changed`, `goal`, `current_step`, `plan`, `next_action`, `open_proposals`, `decisions`, `results`, `artifacts`, `executions`, `not_yet_defensible`, `notes`, `holds`, `final_test`, `criterion`, `eda_looks`, `recap`, `recap_audience`, `recap_junior`, `mode`, `deliverables` |
| `hypotrail.data/1` | `data` | `schema`, `ok`, `study`, `revision`, `observation_unit`, `development`, `target`, `final_test`, `groups`, `rows`, `note` (§11.1) |

* `status --summary` (D3, post-acceptance) prints a compact digest of the view (`view.summary`) for chat agents, a few kilobytes instead of the full view; `status --json` is unchanged and stays the client contract. `goal` is `{intended_use, decision, observation_unit, prediction_time}`: the first three are the case facts of those ids (`{value, status}` or `null`), `prediction_time` is `{value, source: decision|case, status}` (the decision value when there is one, else the case fact). `plan` lists the steps as `{id, title, status}`. `decisions` maps each decision to `{status, value, basis, delegation_scope, user_words, reason, open_proposals}` (a `feature_availability` value is grouped as `{status: [features]}`); `open_proposals` items are `{proposal_id, decision_id, value, restatement, revision}` (the restatement in the study language, `label`, is in `status --json` only, §5.2); `results` maps a slot to `{result_id, current, stale_reason, integrity}`; `artifacts` is `{status, items: {name: {status, revision, last_ok_revision, message}}}`; `executions` is `{active: [ids], interrupted: [{execution_id, activity, reason}], late: [{execution_id, activity, reason, result_id}], suspected_interrupted: [{execution_id, activity, liveness, reason}]}` (`active` lists only executions whose lease is held; see execution liveness, §3); `not_yet_defensible` is `{top: [{id, text}] (at most five, most urgent first), more: [ids]}`. `notes` (post-v0.1, P2; additive, before `recap`) lists every note of the study, oldest first, as `{note_id, decision_id, status, user_words, resolution_words}` (`view.SUMMARY_NOTE_KEYS`; `resolution_words` is `null` while the note is open, and holds the junior's resolving or withdrawing words otherwise). `holds` (post-v0.1 fixes, D5; additive, between `notes` and `recap`) groups the **open** holds by decision, in plan order: `[{decision_id, status, notes: [{note_id, user_words}]}]` (`view.SUMMARY_HOLD_KEYS`; `status` is the decision's status), so a restated hold is seen next to the one already recorded; `[]` when none is open. `final_test` (v0.2a, ADR 0006; additive, between `holds` and `recap`, so `recap` stays the last key before the digest keys) is `view.final_test` (§4.1).
* `summary.recap` (post-v0.1, acceptance T8 and F5; additive, the schema stays `/1`) is a list of exactly five strings, generated deterministically from the state by `view.recap`, that a new chat may quote to resume. Each starts with its label (`view.RECAP_LABELS`): `Goal` (the intended use and the prediction moment, the decision value or the case statement marked "from the case, not decided yet"), `Decided` (each confirmed decision in plan order, the feature availability with its excluded features by name and the doubtful ones kept, the split method and validation share (an ordinal cutoff names its column and cutoff), the policy rule of a binary study or the model choice of a regression study ("model choice: the linear model" or "the mean baseline"; M3), the conclusion verdict; "[delegated to the assistant]" or "[to confirm again]" when it applies; "nothing yet"), `Now` (the current step's title and the generated deliverables that are not up to date), `Next` (the next decision or action in words; an open proposal's restatement is quoted as recorded, so a stand-in figure keeps its caveat; an execution with an unknown outcome comes first), and `Limit` (the most urgent `not_yet_defensible` text other than `unconfirmed_decisions`). It holds no revision number, proposal, execution, or result id, with two exceptions. A binary study (post-v0.1 fixes, D10) whose `policy.evaluation` is current and verified cites the headline result of one evaluated rule: the adopted rule when it was evaluated, else the rule of the open policy proposal, else the first evaluated rule; the logistic model's precision and recall at that rule, in percent with one decimal as the report shows them, on the evaluation's `n` validation rows, with the first 8 characters of that result id: in `Decided` after an adopted policy ("policy capacity:100 (the logistic model at capacity:100 on the 90 validation rows: precision 31.0%, recall 54.5%, result 1a2b3c4d)"), otherwise in `Now` ("(latest policy evaluation: the logistic model at ...)"). And (P3) a regression study whose `evaluate.regression` is current and verified cites its validation MAE, as displayed with two decimals, in the target unit, with the first 8 characters of that result id: in `Decided` for a confirmed model choice ("model choice: the linear model (validation MAE 6.31 mpg, result 1a2b3c4d)"), otherwise in `Now` for both models. An open hold (P2, §5.1) is quoted in `Next` in the junior's words ("On hold in the junior's words: \"...\" (the policy); nothing on hold is confirmed until they resolve it."), the holds of one decision together ("\"a\"; \"b\" (the policy)", D5), so `open_holds` is not repeated as the `Limit`; nor is `conclusion_outdated` (D2), which `Decided` ("[to confirm again]") and `Next` already say. Each line is one flat line (whitespace collapsed, no line break). The deliverable messages hold no revision number either (P3, §8.3). A regression study's recap never uses the vocabulary of a decision rule (threshold, positive class, precision, recall, capacity): its texts come from the task-aware plan, next action, and limits.
* `summary.recap_audience`, `summary.recap_junior` (v0.2a, WP-A1; additive, after `recap`): `recap` is written for the agent (`recap_audience` is `agent`): it quotes the junior in the third person and cites result id prefixes. `recap_junior` is the same five labelled lines written for the junior (no result id, the junior variant of an agent instruction in `Next` and of the limit in `Limit`, holds in the second person). The `Now` line of both says "report and notebook not rendered yet" (or names the one not rendered) while a deliverable has never been rendered, never "up to date". `summary.decisions.*.feature_basis` (additive) is the availability's `feature_basis` grouped as `{basis: [features]}`, or `null`. `summary.artifacts.items.*` add `audience` and `junior_message`; `summary.not_yet_defensible.top` items are `{id, text, audience, junior_text}`, `junior_text` being `null` when `audience` is `junior` (the summary stays compact).
* `summary.mode` and `summary.deliverables` (v0.2a, WP-A7, the companion's requests; additive, after `recap_junior` and before the `--digest` keys): `mode` is `view.mode` (§5.2); `deliverables` is the view's `deliverables` (§3, R7) kept compact, `{launch: {notebook, workbench}}` with each launch `{mode, path, argv}` (`view.SUMMARY_DELIVERABLES_KEYS`, `view.SUMMARY_LAUNCH_KEYS`; the interpreter and the shell form stay in `status --json`), so a surface opens the notebooks without reading the full view. The `recap_junior` lines (WP-A7) say decision values in words, as the junior reads them elsewhere: the policy as "the decision policy: call the top 100 by score" (`audience.rule_words`), the verdict as "adopt the policy", "keep the baseline", or "inconclusive" (`audience.VERDICT_WORDS`), the decisions by `audience.decision_words`, and the headline figures without the rule's token; never a recorded token. Its `Now` line names the step that waits for the junior: the plan step of the decision of an `await_user_words` or `reconfirm` next action, with ", waiting for your answer" or ", waiting for you to confirm it again", or a run of an unknown outcome named in words (`audience.activity_words`), else the current step as in `recap`.
* `status.since` is the `--since` value or `null`; `changed` is `revision > since` (or `null`); `changes_since` lists the revision records after `since` (or `null`). A webview polls with `--since`.
* `decide.revision` is the revision created by the request (also on replay). `artifacts` is `null` until Phase 3 renders after commits (§8.3).
* `init.agent_instructions` is `{source, copied, skipped_existing, status, cli, agent_file, glossary}`; `glossary` is the study path of the glossary copy (§8.4); `status` is `copied`, `kept_existing`, or `no_templates_yet`; `cli` is the exact shell command that runs this CLI (§8.4) and `agent_file` is `.hypotrail/agent.json`. `copied` and `skipped_existing` list workspace paths. `ignored_sources` names the companion files found next to the case (`project.json`, `results.json`, `tutorial-results.json`, `answers.yaml`, `project.yaml`, `frame.yaml`); they are never read. `structural_exposure` is `{exposure_id, n_rows}`: the structural inspection of the **development rows** (v0.2a, ADR 0006; every row in a study created before it). `init.final_test` (v0.2a, additive) is the sealed final test, as `view.final_test` (§4.1).
* `init.notices` and `init.deliverables` (v0.2a, WP-A1, remark R7; additive). `init` writes `<study>/.vscode/settings.json` with `python.defaultInterpreterPath` set to the engine's Python (`framework/.venv/bin/python` when it exists, else the interpreter running the CLI; `mlkit.study.launch.interpreter`) **only when that file is absent**; when it exists and does not already name that Python, nothing is changed and `notices` holds `{code: "vscode_settings_kept", audience, message, junior_message, line}` (`launch.NOTICE_KEYS`), `line` being the JSON line to add. `notices` is `[]` otherwise. `init` also adds `__marimo__/` (Marimo's cache) to the study's `.gitignore`, creating it or appending the line once; `check` never reports `__marimo__/` or `.vscode/` as `untracked_files`. `deliverables` is `{interpreter, launch: {notebook, workbench}}` (`launch.DELIVERABLES_KEYS`); each launch is `{mode, path, argv, shell}` (`launch.LAUNCH_KEYS`): `mode` is `run` for the generated notebook (read-only, it is regenerated) and `edit` for the workbench, `path` the study-relative file, `argv` the argument list with absolute paths (`uv run --project <engine>/framework marimo run|edit <file>` when the CLI runs from the engine's uv project, as recorded in `.hypotrail/agent.json`; else the engine's Python with `-m marimo`), and `shell` the same quoted for a shell. The engine never starts these processes.
* `error` is `{code, message, details?, problems?}`. `problems` (case validation) is a list of `{path, problem}`.

### 3.1 Plan steps and next action

Each item of `plan.steps` and `view.plan` has the keys `id`, `title`, `question`, `expected_output`, `completion`, `pause`, `decision`, `activities`, `decide_first`, `missing_results`, `requires`, `status`, `current`. Step ids, in order: `prediction_time`, `feature_availability`, `split`, `train_eda`, `models`, `policy`, `conclusion`; for a regression study (§10) `prediction_time`, `feature_availability`, `split`, `train_eda`, `models`, `model_choice`, `conclusion`. Since v0.2a (WP-A4, §11) a study created by `init` has `discover_data`, `prediction_time`, `feature_availability`, `split`, `success_criterion`, `train_eda`, `preprocessing`, `models`, `policy` (or `model_choice`), `conclusion` (`state.FULL_STEP_IDS`, `state.FULL_REGRESSION_STEP_IDS`), the `models` step requiring `split`, `success_criterion` and `preprocessing`; a study created before has `discover_data` followed by its v0.1 steps (`state.steps(state)`). Step status is one of `done`, `needs_reconfirmation`, `awaiting_confirmation`, `ready`, `blocked`.

`next_action` always has `kind` and `message`, and since v0.2a (WP-A1, §3.3) `audience` and `junior_message`. Kinds and their extra keys:

| `kind` | Extra keys |
|---|---|
| `outcome_unknown` | `execution_id`, `activity` (closure fix F1: emitted by `status` only, first in priority, when an active execution's lease is not held). Its `junior_message` names the activity in words, "A run of the distribution of a column stopped ..." (WP-A7, `audience.activity_words`; "an analysis" for an activity it has no words for) |
| `acknowledge_interruption` | `execution_id` |
| `reconfirm` | `decision` |
| `await_user_words` | `proposal_id`, `decision` |
| `blocked` | `step`, `requires` |
| `show_data_card` | `step` (`discover_data`). v0.2a (WP-A4): while the study holds no proposal; informational, nothing to confirm (§11) |
| `propose` | `step`, `decision`; and `default_value` for `preprocessing` (WP-A4: the engine's default, §11.3) |
| `run` | `step`, `activity` |
| `done` | — |

### 3.3 Audience of engine messages (v0.2a, WP-A1)

Every sentence the engine emits for a surface says who it is written for, with `audience`: `junior` (it may be shown to the junior as it is: second person or neutral, no command, flag, decision id, or field name) or `agent` (it instructs the assistant, such as "Show the restatement and record the user's own words", or speaks of the junior in the third person). A surface never shows an `agent` text to the junior; next to it the engine gives the junior variant. The keys are additive; no existing key changes meaning (`mlkit.study.audience`):

| Where | Audience key | Junior variant |
|---|---|---|
| `next_action` (`init`, `plan`, `status`, `status --summary`) | `audience` (of `message`) | `junior_message`, always present (equal to `message` when `audience` is `junior`: the step question of `propose` and `run`) |
| `view.not_yet_defensible[]`, `summary.not_yet_defensible.top[]` | `audience` (of `text`) | `junior_text`: in the view always present (equal to `text` when `audience` is `junior`), in the summary `null` when `audience` is `junior`; written for the junior for `unconfirmed_decisions`, `open_holds`, `conclusion_outdated`, `delegated_decisions`, `stale_results`) |
| `view.artifacts.items.*`, `summary.artifacts.items.*` | `audience` (of `message`: `agent`, it names paths and asks for a render) | `junior_message` |
| `summary.recap` | `recap_audience` (`agent`) | `recap_junior` |
| `summary.digest.items[]` (`--digest`, CLI-CONTRACT-COMPANION §1.4) | `audience` (of `text`; v0.2a, WP-A7) | `junior_text`, `null` when `audience` is `junior` |
| `init.notices[]` | `audience` (of `message`) | `junior_message` |

The HTML report shows the junior variants (the next action and the limits). Agent instructions keep their wording and stay where they were.

## 4. View model `hypotrail.view/1`

`mlkit.study.view.build(study_dir, *, leases=None) -> dict` is the **single** view of a study. `status` prints it under `view`, built with a read-only lease probe (`leases`, closure fix F1; see execution liveness below). The HTML report, the generated notebook, and a future webview consume it; renderers do not read raw state. It holds no clock reading, so two builds of one study content are equal.

| Key | Content |
|---|---|
| `schema` | `hypotrail.view/1` |
| `study` | Absolute study directory |
| `revision`, `updated` | Current revision and its commit time |
| `case` | `{id, path, sha256}` |
| `dataset` | `{path, sha256, rows, row_key}` |
| `plan` | Steps (§3.1) |
| `current_step` | Id of the first step not done, or `null` |
| `next_action` | §3.1 |
| `open_proposals` | List of `{proposal_id, decision_id, value, restatement, rationale, revision, created, labels, label, origin}`, oldest first. `origin` (advanced companion, C9; additive, last: decision CI.6) is the stored `{channel}` of the proposal, or `null` for one recorded before C9. `labels` (ADR 0005; additive, before `origin`) is the stored `{language: restatement}` or `null`; `label` is the restatement in the study language (`state.label_of`: `labels[language]`, else `restatement`) |
| `decisions` | `{decision_id: {decision_id, status, value, proposal_id, depends_on, revision, reason, confirmation, open_proposals, feature_basis}}` for the five decisions. `feature_basis` (v0.2a, WP-A1; additive) is `null` except for a `feature_availability` with a value and a confirmation: `{feature: discussed \| default_from_case}`, `discussed` when the feature is named (as a word, case-insensitive, an underscore read as a space or a hyphen) in the confirmation's `user_words` or in the `restatement` they answered, `default_from_case` otherwise. It is derived at view time, so an earlier study reads the same way; surfaces never present a `default_from_case` feature as the junior's own decision (the report says "From the case, not discussed") |
| `facts` | `{by_status: {documented_fact: [...], scenario_assumption: [...], observed: [...], unknown: [...]}, count}`; items are `{id, value, source}` |
| `structure` | The case structure statements (`row_unit`, `group_column`, `time_column`, `duplicates`) |
| `results` | `{slot: result item}` for every promoted slot (below) |
| `stale` | `{result_id: {reason, since}}` |
| `invalidations` | The invalidation records (§6), oldest first |
| `executions` | `{active, interrupted, late, suspected_interrupted}` (filled by Phase 2; `suspected_interrupted` added by closure fix F1, see below) |
| `artifacts` | `{manifest, status, items}`; before any render `{manifest: null, status: "not_rendered", items: {}}` |
| `exposure` | `{records, rows_exposed, by_purpose, by_partition, validation_rows_used_for_selection, prior_exposure}` |
| `not_yet_defensible` | List of `{id, text, ...}` (plan §6) |

**Execution liveness (closure fix F1).** `status` stays read-only and takes no writer lock, but before reading the state it probes every execution lease with a read-only check (`lock.probe_leases`, built on `lock.lease_is_held`: the lease file is opened read-only and a non-blocking shared lock is tried). Each record of `view.executions.active` carries `liveness`: `running` (the lease is held, or the execution was reserved after the probe) or `not_checked` (a view built without a probe: the renderers, which stay deterministic per revision). ### 4.1 The sealed final test (v0.2a, ADR 0006)

`init` assigns a **final test** before any look at the data and seals it: by default 20 % of the rows (`partition.DEFAULT_FRACTION`), the same share of each target label in a binary study (`method: stratified`), of each of 5 target quantile bins in a regression study (`quantile_stratified`, `bins: 5`), or the last rows in the order the case declares (`temporal`, `CASE-CONTRACT.md` §Order). A stratified assignment draws a per-stratum permutation from `numpy.random.default_rng(seed)` with the recorded `seed` (`partition.DEFAULT_SEED`, 0) and keeps `floor(n × fraction + 0.5)` rows of each stratum. Every other row is a **development row**; every activity reads development rows only (`data.load_development`), and the `split` decision divides them into training and validation rows (its `n_rows` counts development rows).

The record is the optional state key `partition` (`state.TOP_OPTIONAL_KEYS`, `partition.RECORD_KEYS`): `{schema: "hypotrail.final-test/1", status, method, fraction, seed (null for temporal), stratified_on (the target or null), bins (null unless quantile_stratified), order (null, or {by, direction, ties_at_cut}), dataset_sha256, n_rows, development: {n_rows, row_keys}, final_test: {n_rows, row_keys}, schema_check, created, implementation}`. `row_keys` is the blob sha256 of the sorted row keys, one per line (the same canonical blob as exposure records), so a partition is identified by that digest and its count. `status` is `sealed` (`partition.STATUSES`); v0.2b adds `opened`.

`schema_check` is the only reading of the final test's cells: `{status: pass|fail, n_rows, checks: [{check, column, failing_rows}], reveals}` with checks `numeric_cells` (one per numeric or integer variable), `target_missing`, and in a binary study `target_labels`. It holds counts, never a value, a label, or a row key. A failure refuses `init` with `invalid_case` (problems `{path, partition: "final_test", problem}`, `path` being the variable's `variables[i].type` or `target`, and `details.final_test_check`) or, when only target cells are missing, `unsupported_capability` (`missing target values (v0.2)`, reason with `partition: "final_test"` and `rows`). The development rows keep the detailed value refusals of `CASE-CONTRACT.md` §Dataset.

Every activity's `inputs` gains `development: {row_keys, n_rows}` (identity covers it); the split result's registry `partition` is `development`. Exposure: `init` records `structural_inspection` on partition `development` (activity `init.structure`) and the final-test rows under purpose `sealed`, partition `final_test` (activity `init.final_test`); `exposure.rows_exposed` does not count sealed rows (`records.SEALED_PURPOSES`), `by_purpose.sealed` does.

`view.final_test` and `summary.final_test` are `{status, rows, method, fraction, development_rows, schema_check}` (`schema_check` is the status word). A study created before v0.2a has no `partition` and is not migrated: `status` is `absent` and the other keys `null` ("no final test"); its activities read every row, its inputs have no `development` key (identities unchanged), and its exposure partitions stay `all`.

`decisions.*.confirmation` is `null` or `{user_words, channel, actor, restatement, proposal_id, revision, time, authenticated, basis, delegation_scope, agent_concern, mode}` (`mode`, v0.2b: the confirmation mode in force when the words were accepted, `null` for a confirmation recorded before v0.2b). `authenticated` is always `false`: the engine records words, it cannot verify who typed them. `basis` is `endorsed`, `restated`, or `delegated_default` for a confirmation recorded since v0.2a (ADR 0005, §5.2), and `explicit` for one recorded before; a stored confirmation without it (written before the post-acceptance fixes) reads as `explicit`. `agent_concern` (ADR 0005, R3) is the point the agent raised before the junior confirmed, or `null` (also for a confirmation recorded before v0.2a). `delegation_scope` is `null`, `this_decision`, or `standing` (§5, R1); `null` for an explicit confirmation and for one recorded before R1. Decision status is one of `open`, `proposed`, `confirmed`, `reconfirm_required`, `superseded`.

A result item has the keys `slot`, `result_id`, `activity`, `current`, `stale_reason`, `partition`, `n_rows`, `values`, `blobs`, `params`, `inputs`, `code_fingerprint`, `environment`, `execution_id`, `exposure_id`, `started_revision`, `integrity`. Since review fix H2, `current` is derived (`read.Study.currency`): a result is current only if it is promoted and not stale in state, its activity's code is unchanged since it was computed (plan §3.7 row 11: every module of its code fingerprint still has the recorded sha256), and every result in its `inputs.results` (except the history role `previous_split`) is current too. A result that fails the derived rule has `stale_reason` `{reason, since: null, code_changed?: [modules], upstream_not_current?: [result ids]}`; `read.Study.is_current(slot)` and the artefact currency rule (§8.3) use the same rule. `integrity` is `ok` or the refusal code (`integrity_error`, `unknown_result`); a result that fails it has `current: false`, `values: null`, and adds a `result_integrity` item to `not_yet_defensible`. **Only a result item with `current: true` and `integrity: "ok"` may be cited.**

`not_yet_defensible` ids emitted in v0.1: `unconfirmed_decisions`, `validation_is_not_independent`, `public_data_already_explored`, `no_time_or_entity_identifier`, `uncertain_features_included`, `stale_results`, `interrupted_executions`, `no_causality`, `workbench_not_tracked`, `result_integrity`. Added by M3: `grouped_split_unsupported` (`column`, `capability`: the case declares a group column and this version has no grouped split; every split reports the group values its partitions share, `split.values.groups`, §10). Added by review fix L1: `sources_changed` (`changes`: `[{label, path, expected_sha256, actual_sha256}]`, the case or dataset file whose bytes differ from `state.case.sha256` / `state.dataset.sha256`; every result item is then `current: false` with `stale_reason.sources_changed`). Added by review fix H2: `code_changed` (`slots`: the current results whose activity code changed since they were computed). Added post-v0.1 (P2): `open_holds` (`notes`, `decisions`: the open holds, quoted verbatim in `text`). Added post-v0.1 (G.12), warnings computed by the view from current, verified results, never refusals: `small_validation_partition` (`slots: ["split"]`, `n_rows`, `min_rows`, and in a binary study `n_positive`, `min_positive`) when the current split's validation partition has at most `view.SMALL_VALIDATION_ROWS` (30) rows or, in a binary study, at most `view.SMALL_VALIDATION_POSITIVES` (5) positive rows (inclusive since the post-v0.1 fixes, D4: the boundary the plan calls small is small; before, "fewer than"), its `text` stating the counts (`view.small_partition_warning`); `capacity_exceeds_validation` (`rules`, `n_rows`) when the current policy evaluation holds a capacity at least as large as its validation rows, which "selects every row" (`view.capacity_warning`; `preview policy` returns both warnings for its rules, §8.1); `high_cardinality_grouping` (`slots`) when a current `eda.rate_by` or `eda.mean_by` folded values into `(other values)` (§8.5). Added by the post-v0.1 fixes: `conclusion_outdated` (D2; `decisions: ["conclusion"]`, `reason`: the conclusion's reconfirmation reason) while the conclusion is `reconfirm_required`, so its text may no longer describe the study; `inconclusive_without_choice` (D6; `decisions`: the policy or the model choice) when a confirmed (or to-reconfirm) conclusion is `inconclusive` and that decision is not confirmed. Added after the Claude Code acceptance run: `delegated_decisions` (`decisions`: every decision whose current confirmation has basis `delegated_default`, "decided by delegation to the assistant's default, not by the junior's own judgment") and `adopted_rule_not_evaluated` (`rules`: the adopted policy rule, confirmed or awaiting reconfirmation, when no current, verified `policy.evaluation` lists it in `params.rules`). Added by v0.2a (WP-A4, §11): `verdict_contradicts_criterion` (`decisions: ["conclusion"]`, `status`) and `data_contingent_preprocessing` (`decisions: ["preprocessing"]`, `results`: its `motivated_by`).

Proposal rules:

* A proposal is first-class: `{proposal_id, decision_id, value, restatement, rationale, revision, status, created, request_id, basis}`; status ∈ `open`, `confirmed`, `withdrawn`, `superseded`. `basis` holds the confirmed values of the decisions it depends on.
* Proposing never changes a confirmed decision. A new proposal supersedes an older open one for the same decision.
* The restatement and rationale may only contain numbers that appear in the proposed value (a fraction may also appear as a percentage), or figures of a current, verified registry result, traced with the matcher of `hypotrail check` (`cmd_check.Pool`, current results only, at their displayed precision: "115 selected", "11.5%"); anything else is `literal_number_in_text`. Since the post-acceptance fixes (D5) this check runs on the state the proposal is made against. Since review fixes L3 and L4: a percentage (`%`, `percent`, `pour cent` after the number) may come from a fraction of the value (`30%` for `validation_fraction` 0.3) or a current result, never from another number of the value (`capacity:100` does not allow `100% precision`; the refused number is reported as `100%`); digits glued to letters are numbers (`top250`), and identifiers are masked first (`commands.IDENTIFIER`: `p_5`, `r_1a2b`, `r-…`, a hexadecimal digest prefix of 8 or more characters with a letter and a digit). **Conclusion (review fix M1).** The conclusion's `value.text` is traced when proposed, with the matcher of `check` on the current results and the recorded literals (confirmed decisions other than the conclusion, the junior's recorded words, the rules of the current evaluation), never on the proposed value itself: an untraceable or stale number is `literal_number_in_text` with `details.field` `value.text`; then causal or forecast wording (`check`'s `causal_wording` and `forecast_wording` rules) in the text, restatement, or rationale is `causal_or_forecast_wording` with `details.findings`.

**Confirmation basis (D1, post-acceptance).** `explicit` (default): the user's own reply to the restatement decides. `delegated_default`: the user explicitly hands the choice to the assistant ("use your recommended default", "go with your recommendation", "je te laisse choisir", "prends ta recommandation"; `commands.is_delegation`), and the proposal's restatement states that it is the assistant's recommended default ("My recommended default: ..."; `commands.states_default`). A bare acknowledgement never delegates; silence is never a delegation. The basis is recorded in the confirmation, shown distinctly in the view, the HTML report and the notebook, and every delegated decision is listed in `not_yet_defensible` (`delegated_decisions`).

**Delegation scope (acceptance rerun, R1).** `--delegation-scope` (action parameter `delegation_scope`, `null` when absent) says which delegation a `delegated_default` confirmation rests on: `this_decision`, a delegation the junior gave at this very pause; or `standing`, an earlier delegation for every question they cannot answer ("for questions I can't answer, use your recommended default"). A standing delegation covers only `prediction_time`, `feature_availability`, and `split` (`state.STANDING_DELEGATION_DECISIONS`); in the `express` mode (v0.2b, §5.3) also `success_criterion` and `preprocessing` (`state.EXPRESS_STANDING_DELEGATION_DECISIONS`, `state.standing_delegation_decisions`). The refusal's `details` then also carry `mode`. The `policy` and the `conclusion` need the junior's own words (`explicit`) or a delegation given at that pause: `--basis delegated_default` for them without `--delegation-scope this_decision` is `ambiguous_confirmation` with reason `delegation_not_given_at_this_pause`. For the other three decisions the scope is optional and recorded as given. A scope with `--basis explicit`, or a value outside `state.DELEGATION_SCOPES`, is `invalid_value` (`details.field` `delegation_scope`). The scope is recorded in the confirmation and shown in the view and in `status --summary`. Confirmations recorded before R1 (without a scope, including a delegated policy) stay valid.

Then, in order: the case and dataset bytes must still match (`dataset_changed`), the value must be valid (`invalid_value`), and the pause preconditions must hold (`precondition_missing`, `details.missing`). A confirmation records `{user_words (verbatim), proposal_id, restatement, authenticated: false, channel, actor, revision, time, basis, delegation_scope, agent_concern, mode}` and applies §6. `basis`, `delegation_scope`, `agent_concern` and `mode` (v0.2b: the confirmation mode in force, one of `state.MODES`) are optional in a stored record (`state.CONFIRMATION_OPTIONAL_KEYS`) so that earlier studies stay valid; `delegation_scope` is `null` unless the basis is `delegated_default`.

**Guided confirmation (ADR 0005, v0.2a).** The rules above are those of the `guided` mode (§5.2), the default (v0.2a); the `training` and `express` modes (v0.2b) are in §5.3. A reply bound to a proposal (`PROPOSAL` or `--proposal`) that is the single open proposal of its decision at the current revision (`--expected-revision`), that is neither negative, a question, conditional, nor bare, and that either holds an explicit endorsement expression or repeats a word or a number of the proposal (else `unrelated_reply`), confirms it. Then, after `proposal_stale` and for a confirmation in the junior's own words only (not a delegation): the decisions of `confirm.REASON_DECISIONS` (`policy` and `conclusion` in a binary study, `model_choice` and `conclusion` in a regression study) need one reason, a clause beyond the endorsement (`confirm.has_reason`: a connector, "because", "since", "given", "parce que", "car", "puisque", "vu que", "étant donné", or any content word that is not an endorsement word or an intensifier); otherwise the refusal is `reason_required` (`details.decision_id`, `proposal_id`, `user_words`, `mode`), not `ambiguous_confirmation`. The recorded `basis` is `restated` when the words repeat a word or a number of the proposal's value, restatement or labels (endorsement words left out, `confirm.restates`), else `endorsed`; the request's `--basis` stays `explicit` or `delegated_default` (`state.REQUEST_BASES`), and a delegation is recorded as `delegated_default` as before. `explicit`, `endorsed` and `restated` are all the junior's own words: a change between them never outdates a conclusion (§6, `state.basis_class`).

**Agent concern and contradiction warnings (ADR 0005, R3).** `--agent-concern TEXT` (action parameter `agent_concern`, carried only when given) records, on the confirmation, a point the agent raised about the junior's words before they confirmed and that the junior kept; it is non-blank (`invalid_value`, `details.field` `agent_concern`), shown in the view, `decisions`, the HTML report ("Point raised by the agent ... kept by the user") and the handoff pack. For `feature_availability`, the confirm result carries `warnings` (`confirm.availability_warnings`): the words are cut into clauses; a clause naming a candidate feature with exclusion words ("exclure", "écarter", "retirer", "sans", "exclude", "drop", "remove") while the value marks it `available_at_prediction` or `uncertain_included`, or with keep words ("garder", "conserver", "inclure", "keep", "include", "use") while the value marks it `not_available` or `uncertain_excluded`, gives `{code: "words_contradict_value", variable, said: "exclude"|"keep", value, message}`. A clause without such words continues the direction of the clause before it ("exclure duration, contact et pdays"); a clause with both kinds, or with a negation before them, says nothing. In the `guided` and `express` modes it is a warning, never a refusal: the confirmation is recorded; in the `training` mode it is the refusal `words_contradict_value` (§5.3). A later correction of the reasoning is a note of kind `correction` (§5.1).

In a regression study (§10) the decisions are `prediction_time`, `feature_availability`, `split`, `model_choice`, `conclusion`; `policy` is not one of them (`unknown_decision`). `model_choice` is `"fit.linear"` or `"fit.baseline"` (`preconditions.MODEL_CHOICES`), confirmed only with a current `evaluate.regression` whose `params.models` lists it; the conclusion's verdict is one of `adopt_model`, `keep_baseline`, `inconclusive` (`preconditions.REGRESSION_CONCLUSION_VERDICTS`): `adopt_model` needs `model_choice` confirmed as `fit.linear`; `keep_baseline` and `inconclusive` need no model choice (D6; before the post-v0.1 fixes `inconclusive` needed a confirmed one). A standing delegation does not cover `model_choice` (it is not in `state.STANDING_DELEGATION_DECISIONS`).

**Split methods (M3).** `split` is one of `{"method": "stratified_random", "validation_fraction": f, "seed": n}` (binary study), `{"method": "random", "validation_fraction": f, "seed": n}` (regression study, not stratified), or `{"method": "ordinal_cutoff", "column": C, "cutoff": k}` (`commands.ORDINAL_SPLIT_KEYS`; `C` is the case's declared time column, of type `integer`; `k` an integer: rows with `C >= k` are validation rows). When the case declares a time column, `ordinal_cutoff` is the only method (`commands.split_methods`): a random split would mix earlier and later rows, so it is `invalid_value`, never a silent fallback. A method outside `commands.ALL_SPLIT_METHODS` is `unsupported_capability`. `run split` refuses a split the rows cannot support with `unsupported_capability` and a structured reason (`details.reasons[]: {code, capability, path, reason}`): `stratified split with fewer than two rows of each class` (with `counts` by label) before sampling, or `random split of these rows with these parameters` when the sampler refuses (for example a validation fraction that leaves a partition empty).

### 5.1 Notes: the junior's conditions and holds (post-v0.1, P2)

`hypotrail decide note --about DECISION --text TEXT` records a condition the junior stated at a pause, verbatim ("don't adopt anything until I bring my manager's figure"): a note `{note_id, decision_id, kind: "hold", user_words, status: "open", created, revision, request_id, resolution: null}` in `state.notes` (`state.NOTE_KEYS`). `--about` names a decision of the study (`unknown_decision` otherwise); the text must be non-blank and say more than an acknowledgement (`invalid_value`, `details.field` `user_words`). A refusal or a negation is allowed: a hold usually is one.

**A hold on a confirmed decision (post-v0.1 fixes, D1).** When the decision is already `confirmed`, the hold withdraws that agreement: the decision becomes `reconfirm_required` (its value and confirmation stay visible, `reason` names the note), and so does every confirmed decision that rests on it (`dependencies.dependents`: the decisions whose `depends_on` closure holds it; the conclusion rests on all of them). No result is invalidated, since no value changed. The invalidation is recorded with `mutation: hold_added`, `row: null`, `decision_id` the held decision (§6), and the `decide.note` result lists the decisions in `reconfirm_required`. A study therefore never shows a decision as confirmed while a hold on it is open; once the hold is resolved or withdrawn, the decision is proposed and confirmed again. A hold on an open or proposed decision changes no status. A state written before this rule may still hold a confirmed decision with an open hold; it is kept as recorded.

While a note on a decision is open, `decide confirm` of that decision is refused with `decision_on_hold` (`details.decision_id`, `proposal_id`, `notes: [{note_id, user_words}]`), whatever the basis, checked after the proposal is found open and created by an earlier request. Proposing is still allowed. `not_yet_defensible` lists `open_holds`; `status --summary` lists every note (`notes`) and the recap's `Next` line quotes the open ones; the HTML report shows each note, open or resolved, in its decision's card, in the junior's words.

`hypotrail decide note --resolve NOTE_ID --text TEXT` resolves an open note with the junior's own words, `resolution: {user_words, revision, time, request_id}` and `status: "resolved"`. The words follow the confirmation rules (`ambiguous_confirmation` with `details.reason` `missing_user_words`, `negative_reply` ("not yet"), `bare_acknowledgement`, or `unrelated_reply` when they share no word or number with the note's words, its decision's id, or that decision's open proposals); `same_request` when the request that recorded the note resolves it. A note id that does not exist is `unknown_note`; a resolved or withdrawn note is `note_not_open`. The words of a note and of its resolution are literals for `check` (`user_words`), like confirmation words.

`hypotrail decide note --withdraw NOTE_ID --text TEXT` (post-v0.1 fixes, D5) withdraws an open hold that no longer applies (a restatement of a hold already recorded, a condition the junior dropped), with the junior's own words: `status: "withdrawn"` and the same `resolution` record. The words may hold a negation ("no need to wait for that any more"); they must be non-blank (`ambiguous_confirmation`, `missing_user_words`) and say more than an acknowledgement (`bare_acknowledgement`); `same_request`, `unknown_note`, and `note_not_open` as for `--resolve`. A withdrawn note no longer blocks its decision; a decision a hold made `reconfirm_required` still needs the junior's words again. `state.NOTE_STATUSES` is `open`, `resolved`, `withdrawn`, `recorded`; the report shows a withdrawn note with the words that withdrew it.

**Corrections (ADR 0005, R3).** `hypotrail decide note --about DECISION --kind correction --user-words TEXT` (action parameter `kind`, carried only when it is not `hold`) records a later correction of a decision's reasoning in the junior's words, without asking for the decision again: a note `{kind: "correction", status: "recorded", resolution: null}`; no invalidation, no hold, nothing becomes `reconfirm_required`. The decision must have a confirmation (`confirmed` or `reconfirm_required`), otherwise `invalid_value` (`details.field` `kind`): before a confirmation the junior answers the proposal in the words they mean. A correction cannot be resolved or withdrawn (`note_not_open`). The report shows it in its decision's card ("Correction in your words"); the companion digest lists it with kind `other`.

### 5.2 Confirmation modes and language (ADR 0005)

`state.mode` is one of `state.MODES`: `guided` (the default, written by `init`), `training` and `express` (implemented in v0.2b, WP-B2, §5.3; `state.SUPPORTED_MODES` is all three, and `state.MODES_AVAILABLE_IN`, which in v0.2a refused `training` and `express` with `unsupported_capability` and `available_in` `v0.2b` in `details`, is now empty). `hypotrail mode set MODE [--user-words TEXT] --request-id ID --expected-revision REV --study DIR` (action `study.set_mode`, parameters `{mode, user_words}`, `user_words` `null` when the option is absent) records the mode: a mode outside `state.MODES` is `invalid_value`. The modes are ordered by strictness (`state.MODE_STRICTNESS`: `express` < `guided` < `training`). **Lowering** the strictness (training to guided, guided to express, training to express; `state.lowers_strictness`) needs the user's words, and they must name the mode asked for (`concepts.mode_named`, the `modes` lists of `content/concepts.yaml`: "express", "rapide", "guidé", ...), otherwise `ambiguous_confirmation` with reason `unrelated_reply`. **Raising** it (`state.raises_strictness`) needs no words: the agent may make confirmations stricter on its own. Keeping the same mode needs words. Missing words where they are needed are `ambiguous_confirmation` with reason `missing_user_words` (`details.previous`, `details.mode`). Words, when given, follow the guided reply rules (`ambiguous_confirmation`: `negative_reply`, `question_reply`, `conditional_reply`, `bare_acknowledgement`). Each accepted request appends `{mode, previous, user_words, revision, time, request_id}` (`state.MODE_CHANGE_KEYS`; `user_words` `null` only for a raise) to `state.mode_history`; the replay of a request is idempotent. A mode change never touches a decision or a proposal: past confirmations stay valid, each with the `mode` it was recorded in.

`state.language` is one of `state.LANGUAGES` (`en`, `fr`), set by `init --lang` (default `en`). A proposal keeps its structured `value` and its `restatement` (compatibility); `decide propose --restatement-en TEXT` and `--restatement-fr TEXT`, and `--lang L` (the language of `--restatement`), store `labels: {language: restatement}` on the proposal (action parameter `labels`, carried only when a language is given, so earlier requests keep their identity). Each label is non-blank, in a language of `state.LANGUAGES` (`invalid_value`, `details.field` `labels`), and checked for numbers like the restatement (`literal_number_in_text`, `details.field` `labels.<language>`). `status --json` shows `label`, the restatement in the study language, on each open proposal of the view (`status --summary` keeps its v0.1 shape); a French paraphrase can restate through the French label.

### 5.3 Training and express modes (v0.2b, WP-B2)

The checks of `guided` (§5) that do not depend on the proposal apply in every mode: `missing_user_words`, `negative_reply`, `question_reply`, `conditional_reply`, `bare_acknowledgement`, the delegation checks, and the binding, hold, and staleness checks. Then, for a confirmation in the junior's own words (`--basis explicit`):

| | `training` | `guided` | `express` |
|---|---|---|---|
| What confirms | A paraphrase on the proposal's **concepts** (`concepts.concept_map`, below); an endorsement alone ("oui je confirme cela") is `paraphrase_required` | An endorsement or a restatement (§5) | As `guided` |
| Reason (`confirm.REASON_DECISIONS`: `policy` or `model_choice`, and `conclusion`) | A reason connector ("because", "since", "given", "parce que", "car", "puisque", "vu que", "étant donné"; `concepts.has_reason_connector`), else `reason_required` | One reason (`confirm.has_reason`), else `reason_required` | As `guided` |
| Words that contradict a `feature_availability` value (R3) | Refusal `words_contradict_value` (`details.warnings`) | Warning in `result.warnings` | Warning in `result.warnings` (recorded only) |
| Recorded `basis` | `restated` | `endorsed` or `restated` | `endorsed` or `restated` |
| Standing delegation covers | `state.STANDING_DELEGATION_DECISIONS` | the same | `state.EXPRESS_STANDING_DELEGATION_DECISIONS`: also `success_criterion` and `preprocessing` |

The policy, the model choice, and the conclusion (and any decision that is not listed) are never covered by a standing delegation in any mode (R1 of v0.1): a delegation of them is given at their pause (`--delegation-scope this_decision`). Every delegated decision stays in `not_yet_defensible` (`delegated_decisions`), whatever the mode. Each confirmation records the mode in force (`confirmation.mode`, `result.mode`).

**Concepts (training).** `concepts.concept_map(state, proposal)` gives, for each decision, the small list of concepts a training confirmation must say. A concept is said when the reply, with endorsement words left out (`confirm.ENDORSEMENT_TOKENS`, so "je valide" never says "validation"), holds one of its terms, in English or French, from `content/concepts.yaml` (data, not code): a one-word term matches an equal word (a final "s" aside) or, when both have at least five letters, a word with the same first five letters; a term `stem*` matches every word that starts with `stem`; a term of several words matches them in a row. Accents and case are folded.

| Decision | Concepts (ids in `details.missing[].concept`) |
|---|---|
| `prediction_time` | each timing the value uses (`timing_before`, `timing_after`, `timing_at`: "before"/"avant", "after"/"après", "at the time"/"au moment"), and `event`: a word of the value or of a label, or a translation of it (`synonyms`: "call"/"appel", "first"/"premier", "campaign"/"campagne", ...), framing words ("predict", "score", "you", `framing`) left out |
| `feature_availability` | `exclude` ("exclure", "écarter", "retirer", "exclude", "drop", "not available", ...) and `variable:<name>` for every variable the value marks `not_available` or `uncertain_excluded`, named as it is (or with its `_` and `.` read as spaces); `keep_all` when nothing is excluded |
| `split` | `validation` (the rows held apart to validate), `random` ("random", "aléatoire", "au hasard", "stratifié"), `proportion` (the validation fraction as a fraction or a percentage, of the validation or the training rows: `0.3`, `30 %`, `70/30`, "trente"); an ordinal cutoff: `validation` (with the later-rows words) and `proportion` (the cutoff) |
| `success_criterion` | binary: `precision` and `min_gain` (the minimum points); regression: `error`, `reduction`, and `min_gain` (the share, as a fraction or a percentage) |
| `preprocessing` | one concept per parameter that differs from the default: `missing_indicator`, `rare_categories`, `caps`, `log_transform`; `no_preprocessing` for the default |
| `policy` | `capacity` ("the 100 best", "appeler les 100 meilleurs", "top", "capacité") or `threshold` ("seuil", "at least"), and `rule_number` (the capacity, or the threshold as a fraction or a percentage) |
| `model_choice` | `linear_model` or `baseline_model` |
| `conclusion` | the verdict: `adopt`, `keep_baseline`, or `inconclusive` |
| any other decision | `restatement`: a word or a number of the value or a label (`confirm.restates`) |

In order, after the checks of every mode: (1) for `feature_availability`, words that contradict the value (`confirm.availability_warnings`) are refused with `words_contradict_value` (`details.decision_id`, `proposal_id`, `user_words`, `mode`, `warnings`, `junior_message`); (2) a reply that holds no endorsement expression, no word or number of the proposal, and no concept is `ambiguous_confirmation` with reason `unrelated_reply` (the classifier is kept); (3) a concept left unsaid is `paraphrase_required` (`details.decision_id`, `proposal_id`, `user_words`, `mode`, `missing: [{concept, hint}]`, `said` (the concept ids said), `junior_message`: a sentence for the junior that names what the reply does not say yet, never words to type); (4) a trade-off without a reason connector is `reason_required`. `concepts.check(state, proposal, words)` returns `{concepts, said, missing}`. The matching is lexical: it misses paraphrases outside the lists and can accept a reply that names the concepts without understanding them; the agent instructions keep the R3 stop for a misattributed reason.

## 6. Invalidation (plan §3.7)

`mlkit.study.dependencies.MUTATIONS` is the table. `effects(old_state, decision_id, old, new)` returns at least `refit`, `re_eda`, `re_policy`, `re_chart`, `re_explain`, `reconfirm` (lists), plus `mutation`, `row`, `reason`, `recompute`, `blocked_until`, `scope`, `notes`.

| Row | `mutation` id | Classified from |
|---|---|---|
| 1 | `prediction_time` | any change of `prediction_time` |
| 2 | `feature_availability.feature_set` | availability change that changes the usable feature set (`available_at_prediction` ∪ `uncertain_included`) |
| 3 | `feature_availability.wording` | availability change with the same feature set |
| 4 | `split` | any change of `split` |
| 5 | `policy.parameter` | same rule type, new `t` or `k` |
| 6 | `policy.rule_type` | threshold ↔ capacity |
| 7 | `settings.bootstrap` | bootstrap settings |
| 8 | `usage_label` | usage label |
| 9 | `eda_added` | an EDA result added |
| 10 | `conclusion` | conclusion text or verdict |
| 11 | `code_fingerprint` | `old`/`new` = `{activity, fingerprint}` |
| 12 | `dataset` | `dataset` or `case`: refused with `dataset_changed` |
| 14 | `preprocessing` | v0.2a (WP-A4): a change of the preprocessing parameters: refit `fit.logistic` (`fit.linear`), re-evaluate, reconfirm `policy` (`model_choice`) and `conclusion`; the baseline and the EDA stay current |
| 15 | `preprocessing.motivation` | WP-A4: same parameters, other `motivated_by`: no effect |
| 16 | `success_criterion` | WP-A4: reconfirm `conclusion`; no result changes |
| `*` | `unknown` | anything else, or an unparseable value: every current result stale, every other confirmed decision `reconfirm_required`, reason recorded |

A regression study uses `dependencies.REGRESSION_MUTATIONS` (`dependencies.mutations(state)`), with the same row numbers: rows 1–4 and 7 name `fit.linear`, `evaluate.regression` (under `re_policy`, the key of evaluations recomputed from stored predictions), and `model_choice` where the binary table names `fit.logistic`, `policy.evaluation`, and `policy`; rows 5 and 6 do not exist; row 13, `model_choice`, is new (no refit, no new evaluation; `conclusion` is reconfirmed). Result replacement uses `dependencies.REGRESSION_RESTS_ON` (`model_choice` and `conclusion` rest on `split`, `fit.baseline`, `fit.linear`).

A first confirmation (`mutation: first_confirmation`) and a confirmation with an unchanged value (`unchanged_value`) have `row: null` and no effect, with one exception. **The conclusion summarizes its decisions (post-v0.1 fixes, D2).** When the conclusion is `confirmed` and a decision it rests on (`state.depends_on(state, "conclusion")`) is then confirmed with a different status (it was not `confirmed`: a policy or model choice adopted after a `keep_baseline` conclusion, a decision confirmed again after a reconfirmation request), a different value, or a different basis class (a delegated default confirmed again in the junior's own words, or the reverse; since ADR 0005 `explicit`, `endorsed` and `restated` are one class, `state.basis_class`), the conclusion becomes `reconfirm_required` (`dependencies.outdates_conclusion`), and `not_yet_defensible` names `conclusion_outdated` until it is confirmed again. The record keeps the mutation id (`first_confirmation`, `unchanged_value`, or the table row) and states the reason. **A hold** on a confirmed decision is recorded with `mutation: hold_added` and `row: null` (§5.1, D1). **Result replacement (review fix H2).** When `run.promote` puts a new result in a slot that held another one, `dependencies.apply_replacement` records an invalidation with `mutation: result_replaced`, `decision_id` the slot, `row` 11 when the activity's code fingerprint changed (else `null`): every current result computed from the replaced one (registry lineage) becomes stale, and the decisions resting on the slot (`dependencies.RESTS_ON`: `policy` and `conclusion` for `split`, `fit.baseline`, `fit.logistic`) become `reconfirm_required`. Nothing is recorded when nothing is invalidated (an EDA or policy evaluation rerun). The `run` result then carries `invalidation` (`{mutation, row, reason, stale_results, stale_slots, reconfirm_required}`, or `null`). Rows 7 (`settings.bootstrap`) and 8 (`usage_label`) are classified by `effects` but no v0.1 command changes the bootstrap settings or a usage label, so they are not reachable; row 9 (`eda_added`) needs no action because an EDA result goes into its own slot (a new `eda.rate_by:<column>` slot adds, never replaces). Facts are never reconfirmed. A policy confirmation never marks its own evaluation stale (a current evaluation of the new rule is its precondition). Staleness propagates downstream through registry lineage.

An invalidation record in `state.invalidations` and `view.invalidations` has the keys `revision`, `decision_id`, `mutation`, `row`, `reason`, `stale_results`, `stale_slots`, `reconfirm_required`, `effects`, `previous` (`{value, confirmation, proposal_id}` of the replaced confirmation, or `null`). A reconfirmation request keeps the decision's previous `value` and `confirmation` visible and sets `reason`.

## 8. Extension points

### 8.1 Activities (Phase 2)

An activity is identified by its **slot** name, which is also its registry `activity`: `split`, `eda.target_rate`, `eda.special_values`, `fit.baseline`, `fit.logistic`, `policy.evaluation`. The plan's slots are `mlkit.study.state.ACTIVITY_SLOTS`. **Exception (Phase 4 integration):** `eda.rate_by` has one slot per column, `eda.rate_by:<column>` (`activities.slot_of`, `state.PER_COLUMN_SLOT_PREFIXES`); its registry entries keep `activity: "eda.rate_by"` and `params.column`, so exploring a second column never replaces the first. These slots are optional: they never block a step, are shown with the `train_eda` step, and a `code_fingerprint` change of `eda.rate_by` reaches every one of them. `run.result.slot` names the slot of a promoted result. A `{{slot:…}}` template may name a per-column slot (the longest known slot prefix wins).

1. **CLI command.** Create `framework/mlkit/study/cmd_run.py` (and `cmd_preview.py`) with
   ```python
   def configure(parser: argparse.ArgumentParser) -> None   # add arguments; --study and --format exist
   def main(args: argparse.Namespace) -> mlkit.study.commands.Outcome
   ```
   `cli.py` imports it only when `hypotrail run` (or `preview`) is invoked. Do not import pandas or scikit-learn at module level of `cmd_*` modules; import them inside the computation.
2. **State mutations.** Register `apply_command` actions:
   ```python
   commands.register_action(name: str, factory: Callable[[commands.Context], reliability.Handler]) -> None
   # Context(store: StudyStore, request_id: str); Handler(params: frozenset, run(state, params) -> result, check(params) -> None)
   commands.apply(study_dir, *, action: str, params: dict, request_id: str,
                  expected_revision: int, command: str = 'decide') -> Outcome
   ```
   Use dotted names, for example `run.reserve`, `run.promote`, `run.acknowledge`. `run` mutates state in memory only and raises `CommandRefused` to refuse.
3. **Preconditions.** Before reserving and again before promoting:
   ```python
   preconditions.require_activity(state, activity: str) -> None            # precondition_missing
   preconditions.missing_for_activity(state, activity: str) -> list[dict]
   preconditions.require_decision(state, decision_id, value=None, *, store=None) -> None
   ```
4. **Results.** Under the writer lock, after computing outside it:
   ```python
   code = registry.code_fingerprint(modules: Iterable[str]) -> {'fingerprint', 'modules'}
   eid = exposure.new_exposure_id() -> 'x_…'
   put = registry.put(store, *, activity, params, inputs, code, values, blobs=None,
                      partition=None, n_rows=None, exposure_id=None, execution_id=None,
                      started_revision=None, env=None)
         -> {'result_id', 'input_key', 'created', 'nondeterministic', 'same_input_results'}
   exposure.record(store, *, exposure_id, revision, activity, result_id, purpose, partition,
                   row_keys, dataset_sha256, columns, execution_id=None) -> dict
   ```
   * `inputs.results` maps a role to the upstream `result_id` (lineage); put decision values and `dataset_sha256` in `inputs` too, so `input_key` changes when they change.
   * `blobs` maps a name to bytes. Predictions use the name `predictions`: gzip CSV with header `row_key,y,score` (plan §3.4), read back by `read.Study.predictions`.
   * A policy evaluation records the evaluated rule(s) as `params.rule` or `params.rules`.
   * `put` never touches state. Promotion is a registered action that sets `state['current'][slot] = result_id` only if the `input_key` recomputed on current state is identical (plan WP2.1); otherwise record the execution under `state['executions']['late']`.
   * Record exposure for every read of rows, even for a result that is not promoted; use `result_id=None` when no result was stored (for example an interrupted execution).
   * Changing a split: compute `exposure.overlap(old_split, new_split, store=store)` and store it in the split result values.
   * A code change: `dependencies.effects(state, 'code_fingerprint', {'activity', 'fingerprint'}, {...})` then `dependencies.apply_effects(state, eff, revision=…, decision_id='code_fingerprint', store=store)` inside an action.
   * A replaced result (review fix H2): `run.promote` calls `dependencies.apply_replacement(state, slot, previous, new, *, revision, store, code_changed=False)`, which calls `apply_effects(..., seeds=[previous], keep=[new])`: `seeds` are results that no longer hold (their current descendants become stale), `keep` is never made stale. Staleness propagates through `inputs.results` without the history role `previous_split` (`records.HISTORY_ROLES`, `records.upstream(entry, history=False)`).
5. **Exit code 4** for an execution with an unknown outcome, including the `interrupted_execution_pending` refusal; `unknown_execution` refuses an acknowledgement of nothing (exit 2).
   **Acknowledgement words (D2, post-acceptance).** `hypotrail run --acknowledge-interruption E --user-words TEXT`: `--user-words` (the junior's verbatim reply after being told the outcome is unknown) is required and non-blank, otherwise `invalid_arguments`; it is refused with an activity. Since review fix L5 the words follow the confirmation rule (`commands.reply_problem`): a refusal, a bare acknowledgement, or words that name neither the interrupted activity nor its interruption (interrupted, unknown, outcome, restart, ...; `commands.ACKNOWLEDGEMENT_TOPIC`) are refused with `ambiguous_confirmation` and `details.reason` `negative_reply`, `bare_acknowledgement`, or `unrelated_reply`. The action `run.acknowledge` has the parameters `{execution_id, user_words}`; its result, and the execution history `.hypotrail/executions/<E>.json`, record `user_words`. An agent never acknowledges or reruns on its own.
6. **Payload schemas added in Phase 2** (additions; the five schemas of §3 are unchanged):

   | Schema | Emitted by | Keys |
   |---|---|---|
   | `hypotrail.run/1` | `run`, `run --acknowledge-interruption` | `schema`, `ok`, `study`, `action` (`run` or `run.acknowledge`), `request_id`, `replayed`, `revision`, `activity`, `execution_id`, `status`, `result_id`, `values`, `result`, `artifacts` |
   | `hypotrail.preview/1` | `preview policy` | `schema`, `ok`, `study`, `revision`, `kind`, `rules`, `models`, `evaluations`, `intervals`, `adopted`, `recorded` (`false`), `note`, `warnings` |

   `run.status` is one of `promoted`, `late_not_promoted`, `already_current`, `running`, `failed`, `interrupted_unknown`, `acknowledged`. An `acknowledged` result holds `execution_id`, `activity`, `status`, `restarted` (`false`), `started_revision`, `user_words`, `note`. `values` are the registry values of `result_id` (cite them only while the slot is current, §4); since review fix L6 a `late_not_promoted` payload has `values: null` and `result.citable: false` (the result is stored in the registry, but it describes a state that no longer holds). Since review fix L7, a `run` whose slot and `input_key` equal those of an active execution is refused with `execution_in_progress` (`details.execution_id`, `slot`, `activity`, `started_revision`) instead of computing twice. `preview` writes nothing and records no exposure; `validation_policy_selection` is recorded by `run policy.evaluate`. `preview.warnings` (post-v0.1 fixes, D4; additive) lists the G.12 warnings that bear on the previewed rules, as `not_yet_defensible` items words them (§4): `capacity_exceeds_validation` for the previewed capacities at least as large as the validation rows the fits scored, first, then `small_validation_partition` when the current split's validation partition is small; `[]` otherwise.

(the same for the generated notebook). * v0.2a (WP-A4, §11.4): `verdict_contradicts_criterion` (warning), from the study check, when the conclusion adopts while `view.criterion.status` is `not_met` or `uncertain`.
* `check` always exits `0`; `clean` is false when a finding has severity `error`. A finding is `{code, severity, where, message, details?}`. Codes (severity): `number_outside_result`, `unknown_result_id`, `value_mismatch`, `stale_result_cited`, `feature_without_status`, `excluded_feature_used`, `untraceable_number`, `stale_number` (error); `causal_wording`, `forecast_wording`, `artifact_not_current`, `untracked_files` (warning); post-v0.1 (P7) `misattributed_delegation` (error): with `--text`, a recommended default credited to the analyst, junior, or user ("followed the analyst's recommended defaults", "defaults chosen by the junior"; `cmd_check.MISATTRIBUTED_DEFAULT`): a delegated decision is the assistant's recommended default, delegated by the analyst. The HTML report's conclusion card lists who decided what: the delegated decisions as "the assistant's recommended default, delegated by the analyst (not the analyst's own choice)", the others as confirmed in the analyst's own words. `traced` lists each number of the checked text with the `result_id` and `path` (or the decision, setting, or case statement) it matched. Post-acceptance (D4): with `--text`, `--allow-user-text` (repeatable; a file, a pipe such as `<(printf ...)`, or `-` when `--text` is a file) gives text the junior wrote, whose numbers a draft may repeat (`traced` source `user_text`); the junior's recorded confirmation words and the rules of the current policy evaluation are literals too (`user_words`, `rule`); "percentage points" match a registered difference (`deltas`) times 100; U+2212 is a minus sign; rule identifiers (`capacity:100`) are never reported (`identifier`); numbers after "exit" and in a revision comparison ("revision 26 instead of 24") are exempt; since the acceptance rerun (R3), a result id prefix made only of digits is never reported either: a run of 6 or more digits (no sign, decimals, or percent) that follows "result", "result_id", "rid", "id", or "execution" ("(result 52659681)"), or that begins a `result_id` of the registry (`cmd_check.registry_ids`), is traced with source `identifier` and id `result_id` when it matches no figure; any other untraced number is still `untraceable_number`; the case and dataset files recorded in state are never `untracked_files`.
* Numbers written in words (post-v0.1, final acceptance F3; `mlkit/study/wordnum.py`). With `--text` and for the conclusion, `check` also reads common English and French word numbers **used quantitatively** and traces them like digits: cardinals 0–100 followed by a count noun ("the eleven kept columns", "quarante-trois clients", possibly one word between), "percent" / "pour cent" (a percentage), "percentage points" (a registered difference only), "dozen" / "douzaine" (12), ratios "k in N" / "k out of N" / "k sur N" ("one call in nine", "un client sur neuf"), and simple fractions followed by "of", "the", "de", "des", or a count noun ("half of the rows", "three quarters of", "la moitié des", "deux tiers des"). A ratio matches a registered rate `v` when `k / v` rounds to `N`; a fraction matches within `wordnum.FRACTION_TOLERANCE` (0.02); a cardinal matches as an integer. Such a number is `traced` (or reported) with `in_words: true` (and, in a finding, `kind` and `value`). Not read: "one" / "un" / "une" as a bare count ("one model"), "a single", ordinals ("first"), "the first half", cardinals above 100, vague quantities ("a few", "dozens", "most"), and a cardinal not followed by a listed count noun ("nine models"). In a regression study (M3) the target unit of the current results is a count noun too (`wordnum.unit_nouns`, a parenthesised note dropped): "about six mpg" is the count 6 and matches an error of 5.5 to 6.5 mpg. Like a digit, a word number traces to the first registered value it matches at its precision, so an unrelated value of the same size can trace it.
* Counts of the study's own structure (post-v0.1 fixes, D8). A count, in digits or in words, that matches no registered value but is followed (at most one word between) by a structural noun (`cmd_check.STRUCTURE_NOUNS`) is traced to the matching count of the view, with `source: "structure"` and an `id`: "columns", "features", "variables", "inputs", "predictors" (and "colonnes") to the length of a current, verified result's `values.features` list (`<slot>.features`) or a count of the feature availability decision or of an open proposal for it (`feature_availability.<decision|proposal id>.<all|usable|excluded|status>`); "groups" to the length of a current result's `values.groups` list; "steps", "pauses", "decisions" to the plan (`plan.steps`, `plan.pauses`) and the decisions (`decisions`). The same count before any other noun is not traced this way ("the seven columns we kept" is traced when the fit uses seven features; "seven calls" is not), and a structural count that matches none of these stays `untraceable_number`.
* Retired proposals (post-v0.1, F3): figures of `withdrawn` or `superseded` proposals are never literals (only open proposals and current decisions are). A draft number that matches nothing else stays `untraceable_number`, and its `details.retired_proposal` and `details.proposal_status` name the proposal it repeats (`cmd_check.retired_proposals`).

A regression `predictions` blob is gzip CSV `row_key,y,prediction` (`y` and `prediction` in the target unit). A residual is `y - prediction` (observed minus predicted); the mean residual is the bias.

`cmd_check` reads the features a fit used from `values.features` and `inputs.features`. A number written with a minus sign glued to its digits (`-1`) is read as negative by `cite.parse_numbers`; `10-18` is still two numbers.

### 11.2 EDA governance

Every EDA result's `values` carry `question`, the question it answers. Additive value keys (§8.5):

* `eda.target_rate`: `interval` (Wilson 95 %, `{low, high, level, method}`); `eda.special_values` (binary): `interval` per special value; `eda.target_summary`: `mean_interval` (t, 95 %).
* `eda.rate_by:<column>`: per group `interval` (Wilson) and `null_band` (`{low, high}`: the range of that group's rate over the shuffles); per chart `null_band: {chart: {statistic, observed, null_min, null_max, outside}, shuffles: 19, seed: 20261019, note}`: the target is shuffled among the training rows `eda.NULL_SHUFFLES` times with `eda.NULL_SEED`; `chart.statistic` is the spread between the largest and the smallest group value among groups of at least `eda.MIN_GROUP_ROWS` rows (all groups when fewer than two qualify); `outside` is true when the observed spread exceeds every shuffled spread. `eda.mean_by:<column>`: the same with a t interval of each group mean.
* `eda.quality` (both tasks; new slot, optional, never blocks a step): the **development rows without the target**; no decision and no split needed (`preconditions.NO_REQUIREMENT_ACTIVITIES`). Values: `partition` (`development`, or `all` in a legacy study), `n_rows`, `n_columns`, `target_read` (`false`), `missing` (`[{column, n_missing, share}]`), `n_rows_with_missing`, `co_missing` (the ten most frequent patterns `[{columns, n_rows, share}]`), `duplicates` (`{n_rows, n_groups, definition}`: rows identical on every column but the target), `cardinality` (non-numeric columns: `{column, type, n_distinct, rare: [{value, n_rows}], rare_rows}`, rare below `eda.RARE_CATEGORY_ROWS`), `ranges` (numeric columns, special values and missing cells apart: `{column, type, min, max, n_special, declared, n_below, n_above}`, compared with the case `range` when declared), `question`, `note`. Inputs: `columns` (every column but the target). Exposure: `structural_inspection`, partition `development` (`all` in a legacy study).
* `eda.single_feature_signal` (both tasks; new slot): each candidate feature alone (the fits' design: special-value indicators, imputation, scaling or one-hot), scored out of fold on the training rows (5 folds, `StratifiedKFold`/`KFold`, seed `eda.SIGNAL_SEED`): `roc_auc` of a logistic model (binary) or out-of-fold `r2` of a linear model (regression). Values: `partition`, `n_rows`, `metric`, `folds`, `seed`, `signals: [{feature, availability (the study's decision), score, rank, flag}]`, `median`, `level`, `gap`, `questions: [{feature, score, availability, text}]`, `question`, `note`. A feature is flagged when its score reaches `level` (AUC 0.75, R² 0.8) or it is the top feature and exceeds the median by `gap` (0.15, 0.4). A flag only asks whether the value is known at the prediction moment: it never keeps or drops a feature. Inputs: `target`, `candidates`, `availability`, `special_values` (never `features`, which `check` reads as a fit's features). Exposure: `train_eda`.

**Ledger of target-involving looks.** `view.eda_looks` (`governance.ledger`) is `{target_looks, results, by_activity, note}`: every exposure record of purpose `train_eda` from an `eda.*` activity whose columns include the target, counted per run (a rerun is another look), with their result ids in order. `summary.eda_looks` is `{target_looks, results}`. It is a disclosure, not an alpha correction.

### 11.3 Decision `preprocessing`

Class b of the synthesis: proposed (the engine's default is `next_action.default_value` and `governance.DEFAULT_PREPROCESSING`), confirmed in the junior's words, parameters learnt on training rows only and applied unchanged to validation rows. Value: `missing` (`none`, `indicator`, or `{feature: none|indicator}`), `rare_category_min_rows` (training rows, integer `>= 0`; `0` keeps every category), `caps` (`{numeric feature: [q_low, q_high]}`, `0 <= q_low < q_high <= 1`), `log_transform` (distinct numeric features), optional `motivated_by` (result ids of this study's registry). Anything else is `invalid_value` (`details.field`, `default`). When proposed, the engine records `motivated_by` (`[]` when absent) and `data_contingent`: true when any motivating result read the target (`governance.uses_target`: the target-reading activities, `eda.distribution` of the target, a stratified `split`); a given `data_contingent` that differs is `invalid_value`; an unknown result id is `invalid_value` (`details.unknown_results`).

The default (`{"missing": "none", "rare_category_min_rows": 0, "caps": {}, "log_transform": []}`) is what the models did before the decision existed: results stay comparable. In a study with the decision, the candidate fits (`fit.logistic`, `fit.linear`) record `inputs.preprocessing` (the confirmed parameters, without `motivated_by`) and `values.preprocessing: {value, fitted: {missing_indicators, rare_categories: {column: {kept, folded}}, caps: {column: [low, high]}, log_transform, ignored}, note}` (`fit.prepare`): a missing-value indicator `<column>=(missing)` is added for a used feature whose training cells hold a missing value (unless a special value read as missing already gives it one); categories with fewer training rows than that minimum, and validation categories unseen in training, become `(rare)`; caps clip at the training quantiles; the log transform is `sign(x) * log(1 + |x|)`, after the caps. The baseline fit and the EDA never apply it. Mutation rows 14 and 15 (§6). `not_yet_defensible` lists `data_contingent_preprocessing` while a confirmed preprocessing is data-contingent.

### 11.4 Decision `success_criterion`

Fixed after the split decision, before any model is fitted (the fits need it). Binary: the minimum precision gain over the baseline at the adopted rule, in percentage points; regression: the minimum relative reduction of the mean baseline's validation MAE. `view.criterion` (`governance.assess`) is `{decision_status, value, metric, status, result_id, rule, model, gain, low, high, minimum, unit, interval_includes_zero, verdict, contradicts_verdict}`: binary `gain` is `100 × deltas.[fit.logistic].precision.point` of the current `policy.evaluation` at the adopted rule (else the rule of the open policy proposal), `low`/`high` its paired interval in points; regression `gain` is `-deltas.[fit.linear].mae.point / models.[fit.baseline].mae` of the current `evaluate.regression`, with the interval mapped the same way. `status`: `met` (gain at least the minimum and an interval that excludes 0), `uncertain` (the point reaches it, the interval includes 0), `not_met`, or `not_assessed`. `contradicts_verdict` is true when the conclusion's verdict (confirmed, to confirm again, or proposed) is `adopt_policy` or `adopt_model` while the status is `not_met` or `uncertain`; `check` then warns `verdict_contradicts_criterion` and `not_yet_defensible` lists it. `summary.criterion` holds `decision_status, value, status, gain, low, high, minimum, unit, rule, result_id, contradicts_verdict`. Mutation row 16 (§6).
