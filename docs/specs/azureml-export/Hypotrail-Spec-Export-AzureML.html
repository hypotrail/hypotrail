01 / Spécification proposée

La décision proposée

Ajouter un export Azure ML qui transforme une étude en projet conforme à votre template, avec une configuration explicite et des vérifications de fidélité.

À la fin de l’atelier, le participant demande : « Prépare cette étude pour Azure ML avec le template de l’équipe. » Hypotrail crée un dossier indépendant, explique les fichiers essentiels et indique ce qui a été vérifié. Avec un profil Azure prérempli par le formateur, le participant n’a pas à reconstituer les variables, les transformations ou les paramètres du modèle.

La valeur pédagogique : passer d’une conclusion documentée à un objet exécutable, en conservant la trace de ce qui a réellement été évalué.

La génération de ce dossier est le périmètre de la première livraison. L’exécution d’une pipeline d’entraînement sur Azure et la mise à disposition d’un endpoint sont des actions distinctes. Votre archive couvre surtout la première ; elle ne contient pas de définition d’endpoint. Cette distinction doit être visible dans le produit, sans compliquer le parcours du participant.

Recommandation : garder vos chemins src/conf/, src/pipeline/, aml/components/, aml/pipelines/training/ et .ci/. Adapter le contenu à l’étude par un générateur déterministe. Hydra est conservé dans le projet exporté ; son adoption générale dans le moteur Hypotrail n’est pas un préalable.

Statut de ce document : spécification proposée, pas fonctionnalité livrée. Les commandes nouvelles, schémas et noms de modules ci-dessous sont des contrats à implémenter. Aucun job Azure n’a été soumis et aucun endpoint n’a été créé pour cette analyse.

04 / Spécification proposée

Le parcours de fin d’atelier

Un seul cas de bout en bout : Auto MPG, si c’est le jeu retenu pour l’atelier. La démonstration Azure réutilise exactement l’étude qui vient d’être menée. Elle n’introduit ni les navettes du template ni un second problème métier.

MomentCe que voit le participantCe qu’il comprend
1 · La demande« Prépare cette étude pour Azure ML avec le profil atelier. »L’export part de la décision enregistrée, pas du dernier notebook modifié.
2 · La réponse courteModèle sélectionné, révision, dossier créé, contrôles réussis, informations éventuellement manquantes.Un dossier généré n’est pas encore une exécution cloud réussie.
3 · Trois fichiers à ouvrirsrc/conf/config.yaml, aml/pipelines/training/pipeline-job.yml, docs/pages/deployment.md.Les choix ML, la destination Azure et le mode opératoire sont distincts.

Cible pédagogique proposée : 10 à 15 minutes pour génération, lecture de fichiers et inférence locale. La durée de construction d’image et d’allocation du compute Azure est exclue ; ne pas promettre qu’elle tient dans ce créneau. Préparer l’environnement, le profil et les ressources avant l’atelier.

Si l’étude ne satisfait pas son critère de succès, le dossier peut quand même être produit en démonstration technique. Son README le dit, et la promotion de production reste désactivée. L’atelier doit montrer qu’une pipeline exécutable ne transforme pas un résultat insuffisant en bon modèle.

05 / Spécification proposée

Contrat de commande et comportement de l’agent

Étendre le groupe export, actuellement limité à handoff. Les commandes suivantes sont proposées ; elles n’existent pas dans le dépôt inspecté.

hypotrail export azureml --study ./study \
  --template team-azureml-v1 \
  --profile ./azure/atelier.yaml \
  --expected-revision 42 \
  --out ./delivery/auto-mpg-azureml --json

# Analyser sans créer le dossier ni lancer de calcul ML
hypotrail export azureml --study ./study \
  --template team-azureml-v1 --profile ./azure/atelier.yaml \
  --expected-revision 42 --plan --json

Le numéro 42 est illustratif : l’agent lit la révision courante avant l’export. Le générateur n’entraîne pas, ne réévalue pas et ne contacte pas Azure. --plan affiche la liste des fichiers, les capacités reconnues et les champs manquants. Sans profil complet, l’export produit un projet draft clairement marqué ; une demande --require-configured échoue sans écrire si les champs nécessaires manquent.

Le profil du formateur est réutilisable pour tous les participants. L’agent demande uniquement une information absente qui empêche réellement la suite : le workspace n’est pas redemandé s’il est déjà dans ce profil. Il ne choisit pas un autre modèle pour contourner une incompatibilité.

Le retour JSON versionné hypotrail.azureml_export/1 contient : ok, study_revision, snapshot_id, export_id, out, files[], configuration_status, artifact_status, checks[], missing_fields[], warnings[] et next_commands[]. Chaque commande indique si elle est locale, nécessite le réseau ou écrit dans Azure.

Conserver les codes d’erreur existants pour révision périmée, cible occupée et lecture seule. Ajouter des codes métier nommés sans réutiliser arbitrairement les codes de sortie numériques existants : template_unsupported, model_not_captured, unsupported_export_capability, data_identity_mismatch, environment_unqualified et scientific_config_changed. Un résultat draft réussi n’est pas présenté comme prêt à soumettre.

L’agent restitue un message court construit à partir du retour structuré. Aucun changement du panneau VS Code n’est nécessaire au MVP : le chat ouvre le dossier. Ajouter un bouton d’export Azure au panneau demanderait un élargissement explicite de son contrat et de l’ADR associé.

06 / Spécification proposée

Architecture : un exporteur, un runtime, un adaptateur

Le moteur reste responsable des choix et de la validité des preuves. L’exporteur traduit un instantané figé vers un template reconnu. Le projet généré possède ses points d’entrée opérationnels ; Azure reste l’orchestrateur distant.

templates/team-azureml-v1/Squelette nettoyé, manifeste des chemins, schéma de paramètres, tests de conformité.Version explicite ; le ZIP original est une source de migration, pas un programme arbitraire exécuté.

Le runtime partagé est un travail de factorisation, pas une copie du moteur dans chaque cas d’usage. Le projet reçoit une distribution versionnée avec empreinte, ou une référence immuable à cette distribution. Il peut fonctionner sans le répertoire d’origine de l’étude, sans connexion à GitHub et sans session d’agent.

Le contrat du template doit distinguer trois types de fichier : conservé (convention de l’équipe), rendu (contenu déterminé par le snapshot), ajouté (provenance, tests et outils nouveaux). Un nouveau ZIP inconnu est inspectable, mais n’est pas accepté automatiquement comme template exécutable.

07 / Spécification proposée

Le changement essentiel : conserver le prédicteur complet

Dans fit.py, design() prépare les types et valeurs spéciales ; prepare() applique notamment catégories rares, bornes et transformations logarithmiques ; puis une pipeline ou une famille de modèles est ajustée. Enregistrer seulement l’objet scikit-learn renvoyé à la fin ne conserve donc pas nécessairement tout le calcul de prédiction.

Exemple Auto MPG : origin, codé numériquement, est traité comme catégorie ; les valeurs manquantes et l’ordre des variables ont une sémantique. Une API qui traite soudain origin comme une grandeur continue ne sert plus le même prédicteur, même si le fichier du régresseur a été copié correctement.

Exigences sur l’artefact

  1. M-01. Capturer une interface complète predict(raw_features) : sélection et ordre des colonnes, conversion des types, valeurs spéciales, état appris de prétraitement, estimateur et adaptation de sortie.
  2. M-02. Distinguer la recette d’apprentissage et l’état ajusté. Une recette « regrouper les catégories rares » ne suffit pas : conserver la liste des catégories retenues, le traitement des catégories inconnues et les bornes numériques apprises. Les métadonnées de résumé actuelles ne remplacent pas cet état.
  3. M-03. Conserver les paramètres effectivement utilisés après tuning. L’export du modèle évalué ne relance pas une recherche ; une valeur réglée sur le développement final peut différer de celle de chaque fold.
  4. M-04. En CV, distinguer les modèles des folds et le prédicteur réajusté sur le développement avant test final. L’un des modèles de fold ne devient jamais, par défaut, « le modèle final ».
  5. M-05. Pour les futurs tests finaux, sérialiser et vérifier le rechargement du prédicteur avant de lire les labels du test final. Lier ensuite les résultats finaux à l’empreinte de cet artefact dans la transaction d’activité. Une panne ne doit ni créer une fausse preuve ni permettre de rouvrir un test déjà exposé.
  6. M-06. Enregistrer format, version, environnement, code, contrat d’entrée, recette, scope d’entraînement, empreintes des appartenances et des fichiers. Les octets d’un modèle ne sont pas supposés identiques après réentraînement ; leur empreinte identifie l’objet sauvegardé.
  7. M-07. Produire le package MLflow sans réajuster. Tester les deux chargements : runtime natif et mlflow.pyfunc. Le wrapper doit conserver les transformations et dépendances personnalisées. Pour la première version atelier, activer cette capture avec les dépendances de packaging installées : le package est créé une fois pendant l’activité autorisée, avant l’évaluation finale, puis copié par l’export. L’export ne régénère pas des métadonnées MLflow datées à chaque appel.

Pour une ancienne étude sans artefact capturé, ne pas reconstruire le prédicteur à partir des seuls coefficients affichés. Autoriser un export de recette, avec artifact_status=missing. Un réentraînement explicite sur le développement crée un nouvel artefact ; les résultats historiques ne sont pas réattribués à cet objet. Aucun « repair » ne réouvre le test final.

La sérialisation native peut s’appuyer sur joblib pour les objets internes de confiance ; elle doit être entourée d’un manifeste vérifié avant chargement et d’un environnement compatible. Une empreinte protège contre une altération détectable, elle n’authentifie pas la provenance d’un fichier reçu d’un tiers. La documentation scikit-learn ne garantit pas la compatibilité de chargement entre versions différentes. [S6]

Identité déterministe : snapshot_id résume le contenu scientifique canonique ; export_id ajoute le template, la version du générateur et les paramètres non secrets de destination. Les timestamps de runs, chemins absolus locaux et tokens n’entrent pas dans ces identités. Des références à des secrets peuvent être décrites par nom de mécanisme, jamais par leur valeur.

Appartenances : exporter des clés de ligne et les rôles train/validation/folds/exclusion, avec le lien à l’empreinte de la source. Si les clés actuelles dépendent des numéros de ligne, une permutation du fichier change son identité et doit être refusée ; ne pas prétendre que ces clés résistent à une réorganisation des données.

Données : le mode par défaut référence un asset Azure versionné. Un asset versionné pointant vers un stockage mutable ne suffit pas : vérifier aussi l’empreinte du contenu attendu. Si les données ne sont pas déjà disponibles, générer la définition d’asset et une étape explicite de transfert. Les labels et lignes du test final ne sont jamais nécessaires à l’inférence ni au replay de développement.

Si l’asset contient uniquement le développement extrait d’une source plus large, distinguer source_sha256 et materialization_sha256. Le manifeste de matérialisation conserve les clés de ligne originales dans une colonne réservée et le mapping de colonnes ; il ne renumérote pas les lignes après extraction. La clé technique est exclue des variables du modèle. Vérifier la filiation de la projection plutôt que d’exiger à tort l’égalité des empreintes de deux fichiers différents.

Le générateur ne copie pas le dossier d’étude complet. Les jeux de parité proviennent de données de développement déjà accessibles ou de cas synthétiques ; leurs tailles et éventuelles données sensibles sont déclarées. Les données brutes ne sont pas envoyées avec code: : ce répertoire n’inclut que le code, les configurations nécessaires et les contrats publics au run.

10 / Spécification proposée

Hydra : conserver votre convention, figer les choix ML

Hydra sert à composer les paramètres d’exécution et à garder vos groupes de configuration. Le manifeste d’Hypotrail reste la référence de ce qui a été décidé et évalué. Ces deux rôles sont complémentaires.

11 / Spécification proposée

Sémantique des quatre étapes Azure ML

Conserver les quatre noms familiers, mais préciser leur sens. L’ordre préparation → découpage est acceptable si la préparation ne fait que lire, typer et valider. Tout traitement apprenant des paramètres appartient au prédicteur et s’ajuste sur les lignes d’entraînement autorisées.

ÉtapeEntrées et sortiesInvariant
data_preparationDonnée source versionnée + contrat → table canonique avec clés de ligne, rapport de validation.Pas de médiane, normalisation, catégories rares apprises ni dropna implicite. Écart de contenu ou de population : arrêt.
data_splittingTable + plan figé → partitions de développement et manifeste des appartenances.Matérialiser les rôles et folds existants ; ne jamais appeler train_test_split pour inventer un nouveau protocole.
trainingDonnées autorisées + recette résolue → nouveau prédicteur complet MLflow + manifeste de run.Pas de recherche d’hyperparamètres en mode replay ; pas de labels de test final ; pas de registration automatique.
evaluationModèle de ce run + fixture/parité + contrats → contrôles techniques et rapport de filiation.Vérifier chargement et prédiction. Ne pas produire une nouvelle preuve finale en relisant le test historique.

Deux modes de replay explicitement distincts : development_evaluation réexécute le protocole train/validation ou les folds existants et produit des résultats de développement déjà exposé ; rebuild_final_candidate ajuste la recette finale sur le développement autorisé et fait des contrôles techniques. Dans ce deuxième mode, aucune métrique de généralisation n’est fabriquée à partir des données d’entraînement.

Pour le MVP atelier, recommander rebuild_final_candidate avec paramètres finaux figés, et conserver séparément model/evaluated/. Le modèle réentraîné par Azure est marqué rebuilt_candidate. Même si un petit jeu de parité donne des prédictions proches, cela ne suffit pas à lui attribuer exactement le verdict d’un autre objet.

Le fichier du modèle évalué peut être enregistré sur Azure sans réentraîner, après contrôles de packaging et d’environnement. C’est le chemin qui permet de montrer « le modèle évalué devient transportable ». La pipeline d’entraînement reste fournie pour montrer le chemin de reconstruction et préparer les évolutions.

Un réentraînement sur de nouvelles données constitue un nouveau run scientifique : nouvelle identité de dataset et nouvelle évaluation. Les YAML sont réutilisables ; le verdict de l’étude ne l’est pas automatiquement.

13 / Spécification proposée

Environnements, MLflow et autonomie

Décision proposée : conserver Python 3.13 pour la première qualification, parce que c’est la contrainte du moteur actuel. Ne pas abaisser la version juste pour conserver l’ancien fichier du template. La compatibilité Azure d’une image précise doit être démontrée par un run de recette ; elle n’est pas établie par cette revue.

Le lock doit couvrir au minimum Python, numpy, scipy, pandas, scikit-learn, le runtime partagé, Hydra/OmegaConf et MLflow ; ajouter interpret-core seulement pour une famille EBM supportée. Déclarer explicitement MLflow, actuellement importé dans les scripts du template via un environnement qui ne le fixe pas directement. Ne pas embarquer openpyxl, pandera ou un launcher Hydra uniquement parce qu’ils figuraient dans l’exemple : conserver ceux réellement appelés.

Deux variantes d’environnement sont supportables : référence à une image/environnement déjà qualifié, ou construction à partir d’un contexte minimal aml/environments/runtime/ contenant le Dockerfile, les locks et la distribution du runtime. L’environnement Azure doit choisir l’une de ces variantes sans combiner des champs incompatibles. Le manifeste enregistre le digest de l’image effectivement exécutée lorsque celui-ci est disponible.

Les dépendances nécessaires au chargement du modèle sont aussi déclarées dans le package MLflow, et testées dans un environnement propre. Une signature décrit les colonnes d’entrée et la sortie ; elle ne prouve ni la qualité métier, ni l’absence de dérive. L’environnement de serving peut ajouter ses propres dépendances : une qualification du training ne qualifie donc pas automatiquement un endpoint. [S3]

Éviter un autolog global qui enregistrerait des échantillons ou des modèles hors contrat. Les scripts loggent explicitement paramètres, identités et résultats autorisés. Pour les essais locaux, le tracking peut être désactivé sans désactiver la sauvegarde du modèle ; aucun appel Azure caché n’est effectué lors d’une simple prédiction.

15 / Spécification proposée

Exécution locale, CI et déploiement ultérieur

Le projet généré expose un petit nombre de commandes stables. Elles réutilisent les mêmes fonctions que les composants ; la CI ne doit pas tester une implémentation différente de celle exécutée dans Azure.

# Commandes proposées à exécuter depuis le dossier exporté
python scripts/project.py validate --offline
python scripts/project.py predict --model model/evaluated \
  --input tests/fixtures/parity/input.json --output outputs/predictions.json
python scripts/project.py run-local --mode rebuild_final_candidate

# Accès Azure en lecture, puis soumission séparée
python scripts/project.py preflight --profile azure/target.yaml
python scripts/project.py submit --profile azure/target.yaml

validate --offline contrôle schémas, imports disponibles, intégrité, expressions, chemins et parité si l’artefact et l’environnement sont présents. Une dépendance absente est un contrôle non exécuté, pas un succès. run-local entraîne : il n’est jamais appelé par export ou par une simple validation de structure.

submit vérifie le manifeste, annonce les écritures prévues, enregistre les assets manquants autorisés puis crée le job. Il écrit un outputs/submission.json avec les IDs, retourne l’URL Studio et attend l’état terminal si --wait est demandé. Un délai d’attente dépassé laisse le statut « soumis, résultat non observé » ; il ne relance pas un second job.

La CI de qualité s’exécute sans credential sur un jeu synthétique, puis sur une fixture du cas autorisée. La CI cloud utilise une service connection de l’organisation, un scope et des permissions définis par l’équipe. Dans le template exporté pour l’atelier, elle est manuelle par défaut. Toute publication automatique ultérieure doit être explicite dans le profil de livraison.

Si une création d’asset réussit et que la suivante échoue, le journal permet une reprise idempotente : même nom+version+empreinte → réutilisation ; même nom+version mais contenu différent → erreur. Une soumission de job déjà confirmée n’est jamais répétée automatiquement. Les sorties des runs sont isolées et les erreurs ne déclenchent pas de suppression récursive générique.

Option endpoint, dans un lot séparé

MLflow est un bon format de passage : Azure ML propose des mécanismes de déploiement batch et online pour ces modèles. Cela ne dispense pas de tester le format des requêtes, les dépendances, les permissions et la sémantique du prédicteur. [S3] [S8]

Pour Auto MPG, commencer éventuellement par le batch. Un mode online exige un nom d’endpoint, une configuration d’authentification, une taille de machine, des limites, une stratégie de trafic, un test d’invocation et une commande de nettoyage. Ces champs ne sont pas déduits d’une étude ML. Les YAML correspondants vivront sous aml/deployments/ quand cette option sera demandée.

Pour la classification, tester la sortie réelle du wrapper : un predict scikit-learn peut retourner une classe, alors qu’Hypotrail sélectionne un score puis une règle. La classe positive, le score et la convention >= seuil doivent être préservés. Une règle « choisir les meilleurs 10 % du lot » exige un lot complet et une politique d’ex æquo ; elle n’est pas une décision individuelle online. Les pondérations fractionnaires utilisées pour l’évaluation ne deviennent pas des actions réelles sans définition supplémentaire.

Écriture, versionnement et intégrité

  1. I-01 · Snapshot cohérent. Lire une version stable selon les mécanismes existants du moteur ; vérifier --expected-revision et les empreintes des dépendances. Une modification concurrente ne produit pas un mélange de deux états.
  2. I-02 · Étude préservée. L’export ne modifie ni décisions, ni résultats, ni appartenance, ni registre d’exposition. Il peut réutiliser la télémétrie de canal existante de l’export handoff, sans mutation scientifique. Le module actuel de handoff se décrit comme sans événements, mais son wrapper appelle record_channel : garder cette distinction lors des tests.
  3. I-03 · Destination contrôlée. Dossier neuf ou vide, hors fichiers internes, rapports et notebooks de l’étude. Refuser les chemins via symlink qui contournent cette règle. Une cible non vide n’est jamais écrasée par défaut.
  4. I-04 · Écriture atomique. Préparer dans un dossier temporaire frère, vérifier l’inventaire, puis publier par renommage. Échec ou conflit concurrent : pas de projet annoncé comme complet. Le chemin final est revérifié avant publication.
  5. I-05 · Reproductibilité du rendu. À snapshot, profil, template et versions identiques, mêmes fichiers textuels et mêmes copies d’artefacts. Exclure les horloges du rendu ; les données d’exécution vont dans outputs/. Ne pas promettre la sérialisation binaire identique d’un nouveau fit.
  6. I-06 · Régénération. Au MVP, créer un nouveau dossier/version, puis proposer un diff. Pas de fusion automatique avec du code modifié par un ingénieur. Une future mise à jour ne touchera que les fichiers possédés par le générateur et encore identiques à leur empreinte d’origine.
  7. I-07 · Template. Extraction à liste autorisée, rejet des traversées de chemins et symlinks, exclusion .git/macOS/caches/données d’exemple ; aucun hook ni script du ZIP exécuté à la génération.
  8. I-08 · Transfert. Contrôler l’inventaire réellement soumis à Azure et le contexte de build. Ne pas inclure credentials, configurations locales, labels finaux, modèles non choisis ou copie complète de l’étude.

Ces mesures répondent aux propriétés concrètes de l’archive et aux garanties déjà présentes dans le moteur. Elles ne constituent pas une nouvelle procédure d’approbation pour créer un dossier local.
