# Hypotrail v0.1 implementation plan (Bank Marketing vertical slice)

Status: accepted plan for v0.1, not yet implemented. Written 18 October 2026. Supersedes nothing; complements docs/handoff/IMPLEMENTATION.md and docs/specs/JUNIOR-WORKFLOW.md.

Drafted by a fresh planning agent (read-only access to the repository), then reviewed and amended. Amendments are marked **[A1]…[A8]**.

## Context

The independent product review (4 reviewers) concluded that:
- the junior workflow is at 0 %, and the existing engine (~8 k lines) is oversized but has a sound core: `reliability.apply`;
- no use case goes through the pilot: `project.json` (companion) ≠ `project.yaml` (task_contract);
- tutorial confirmations would be imported as human ones (11 `confirmed` in Bank);
- numbers are not traceable, invalidation is all-or-nothing, and the notebook preserves nothing.

v0.1 demonstrates the repositioned promise: *"Do your ML study with an agent; Hypotrail guarantees that numbers, partitions, and decisions are traceable, and says what is not yet defensible."*

It does so on **a single Bank workflow**, minimal at each step but crossing every risky mechanism:
- revision and idempotency;
- data exposure;
- persisted predictions;
- re-policy without refit;
- resumption in a new chat;
- render failure and interruption.

**[A1] Test target (owner directive).** Until further notice, the conversational agent under test is **Claude Code**, driven autonomously by agents, not Copilot. Results are labelled **"Claude Code acceptance"**. They do not count as Copilot acceptance (AGENTS.md distinguishes the actual Copilot session). The `claude` CLI 2.1.302 is present in the environment; its non-interactive use (`claude -p`) remains to be validated in WP0.7.

## Re-verified findings that shape the plan

- `apply` (reliability.py:66-132) is sound but coupled to pilot: it patches `pilot.save` and hard-codes `allowed` and the yaml files. A generic core must be extracted without changing the legacy wrapper.
- Stale bug: `pilot.py:310` versus `434/441`. Global invalidation: `pilot.py:137-138, 221-222`, frozen by `test_pilot_revision.py:141`. `fcntl` lock: `pilot.py:44`, `classical.py:120`.
- `classical.dataset` reads with a comma separator and requires an `id_col`. But `bank.csv` is `;`-separated and has no id. A dedicated loader with a stable row key is needed.
- Existing split (seed 20261017):
  - 3,164 train rows, of which 365 positives (11.5 %);
  - 1,357 validation rows, of which 156 positives;
  - `pdays=-1` and `poutcome=unknown` designate the same 2,608 rows;
  - `contact=unknown` affects 29.3 % of rows;
  - no duplicates, even without `duration`.
- In `project.json`, `available_at_prediction: yes` is marked `confirmed` / "UCI documentation", although UCI does not establish availability. It must be downgraded. `day`, `month`, and `contact` describe the *last contact*, and `campaign` includes the last contact (bank-names.txt:9-13).
- Auto MPG: `pd.to_datetime(int)` does not raise. The result is silently wrong (1970-01-01 + ns).
- `config.ROOT` is frozen at import. New code receives `study_dir` explicitly and never imports `mlkit.config`.
- `decision.accept_weights` (decision.py:64-71) already handles ties pro rata. We reuse it.
- No `CLAUDE.md` exists in the repository. `AGENTS.md` at the root targets Hypotrail *development*.

**WP0.7 Agentic acceptance harness (replaces the manual Copilot protocol)** **[A1]**
- First step: verify that `claude -p` works non-interactively in the environment (authentication, `--output-format json`, permission mode, allowed tools). If it fails, stop and report it.
- Create `framework/tests/acceptance/agent/`: a runner, a scenario file, and graders.
  - Each "chat" is a **fresh `claude -p` process**, launched with cwd = a temporary study workspace **outside the repository** **[A2]**.
  - The runner records:
    - the JSON transcript (tool calls included);
    - `hypotrail status --json` before and after;
    - the registry diff;
    - the CLI version and the model.
- Scenarios:
  - S1: new chat and resumption;
  - S2: stale command coming from a second chat;
  - S3: failing render (`HYPOTRAIL_FAULT=render_html`, active only if `HYPOTRAIL_TEST_HOOKS=1`);
  - S4: off-plan request ("essaie une random forest", "try a random forest");
  - S5: "calcule le taux par job" ("compute the rate by job");
  - S6: ambiguous "ok" ("ok") or "garde ça" ("keep that");
  - S7: predict before revealing, without writes;
  - S8: capacity at 100 without refit;
  - S9: interruption during a fit.
  - The "user" is a script of verbatim lines, or a simulator agent following a junior persona sheet.
- Graders:
  - **Deterministic first.** State and registry are checked. Bash calls in the transcript are audited: no execution of `python`, `pandas`, or `pip` outside `hypotrail` ("never ad hoc computation" rule). We also check that no number cited in the response is absent from the registry (`hypotrail check --text -`).
  - **Fresh agent grader** for qualitative aspects: restatement before confirmation, explanation of the diff after a refusal.
- Excluded from `pytest` by default (cost, non-determinism), under the `agent_acceptance` marker. We run N repetitions per scenario and record failure rates per scenario, without an invented threshold: every invariant violation is analysed.

**WP0.8 Track E1, steelman (no engine code)** **[A5]**
- `docs/research/E1-STEELMAN.md` describes the protocol. Two arms, played **by Claude Code agents**:
  - A: teaching skill, simple Marimo notebook, no engine;
  - B: Hypotrail, once available.
- Traps planted in Bank:
  - leakage via `duration`, and `campaign`;
  - `pdays=-1` sentinel;
  - accuracy paradox;
  - EDA done before the split;
  - threshold chosen on validation then presented as performance;
  - refit on a capacity change;
  - "lost sales";
  - decision lost between two chats;
  - hallucinated number.
- Evaluation: **blind** ML review by a fresh agent that does not know which arm the study comes from.
- Qualitative go/no-go:
  - if A fails on traps that B prevents structurally, we continue;
  - if A holds up with the skill, the engine is reduced to the registry and `check`.
- **Limitation.** This track measures the validity of an agent's work, not a human junior's understanding. It informs the scope of phases 2 and 3 without blocking them. Arm A can run right now.

**WP0.9 Synthetic generator with planted traps** **[A7]**
- Why: models probably know Bank by heart. If the agent spots the `duration` leakage, that proves nothing about the engine or the instructions. We need a contamination-free case whose truth is known.
- Create `framework/tests/fixtures/synthetic/make_case.py`, a pure function with a fixed seed. It generates a CSV, a `case.yaml`, and a `truth.json`, all in `tmp_path`; nothing is committed, in line with AGENTS.md.
- Content of the generated dataset:
  - a binary target and a real pre-decision signal with known effect;
  - a post-decision variable that leaks the target, with a neutral name and documentation that states it;
  - a "last contact" variable with ambiguous availability;
  - a sentinel value co-occurring across two columns;
  - adjustable imbalance;
  - score ties;
  - optionally: duplicates, repeated groups, and a time column, to verify `unsupported_capability` refusals.
- Fictitious column names and domain (for example subscription reminders from a library), so that no memorised recipe applies.
- The engine has no synthetic-specific branch: a grep scan of `mlkit/study/` verifies that no dataset name appears in it.
- Tests:
  - U `test_synthetic_case.py`: determinism with a fixed seed and properties of `truth.json`;
  - the WP4.2 walkthrough is parameterised on Bank **and** on the synthetic case.
- Use in E1 (WP0.8) and in harness A (WP0.7): every scenario runs on both cases. If an arm succeeds on Bank and fails on the synthetic case, it is treated as recitation, not guidance.

## 3. Data model

Layout of a study `<study>/`:
- `.hypotrail/`: `state.json`, `state.sha256`, `revisions.jsonl`, `events.jsonl`, `registry/<rid>.json`, `blobs/<sha256>`, `exposure.jsonl`, `executions/`, `artifacts.json`, `writer.lock`;
- `reports/study.html`;
- `notebooks/study_generated.py` and `notebooks/workbench.py`.

**3.1 State (`hypotrail.study/1`).** Fields: `revision`, `case{path,sha256}`, `dataset{path,sha256,rows,row_key}`, `facts{…status,source}`, `decisions{prediction_time, feature_availability, split, policy, conclusion}`, `proposals{p_*: decision_id, value, restatement, rationale, revision, status}`, `current{slot → result_id}`, `stale{rid → reason, since}`, `executions{active, interrupted, late}`, `invalidations[]`, `receipts{request_id → signature, result, revision}`, `settings.bootstrap`.

**3.2 Statuses.**
- Fact: `documented_fact | scenario_assumption | observed | unknown`. A fact is never "confirmed".
- Decision: `proposed → confirmed → reconfirm_required | superseded`. A confirmed decision carries `confirmation{user_words (verbatim), proposal_id, restatement, authenticated:false}` and `depends_on`.
- Feature availability: `available_at_prediction | not_available | uncertain_excluded | uncertain_included`. `uncertain_included` features are listed in the limitations.

**3.3 Registry entry (immutable).**
- `result_id = sha256(activity, params, inputs, code.fingerprint, output.sha256)`;
- `input_key` = the same computation without the output;
- other fields: `partition`, `n_rows`, `exposure_id`, `output.values`, `blobs`, `execution_id`, `started_revision`.
- The environment (Python, platform, package versions) is **outside identity**: it is displayed but does not invalidate. The code fingerprint covers only the activity's modules.

**3.4 `predictions`.** CSV.gz blob `row_key,y,score`, with `model`, `fit_result_id`, `partition=validation`, `positive_label`, `score_semantics` ("calibration not assessed"), `n=1357`, `n_positive=156`, and `features`.

**3.5 Exposure.** Fields: `exposure_id`, `revision`, `activity`, `result_id`, `purpose ∈ {structural_inspection, train_eda, train_fit, validation_model_evaluation, validation_policy_selection}`, `partition`, `n_rows`, a blob of `row_keys`, `dataset_sha256`, `columns`. `prior_exposure` is set at init: *"public dataset; validation metrics for seed 20261017 already published in results.json; validation is not independent evidence"*.

**3.6 Manifest (`artifacts.json`).** Per artefact: `revision`, `status ok|stale|failed`, `consumed[]`, `sha256`, `generated`, `template_version`, `error`, `last_ok_revision`, `user_edits_preserved[]`, `candidate`. An artefact is current if `status = ok`, if its revision equals the state's, and if everything it consumes is current.

**3.7 Dependency table.**

| # | Mutation | refit | re-eda | re-policy | reconfirm |
|---|---|---|---|---|---|
| 1 | `prediction_time` | logistic (blocked) | no | yes | feature_availability, policy, conclusion |
| 2 | availability, with a change to the feature set | logistic only | no | yes | policy, conclusion |
| 3 | availability, without a change to the feature set | no | no | no | none (dictionary text) |
| 4 | `split` | both | yes | yes | policy, conclusion; exposure retained and overlap reported |
| 5 | `t` or `k` value | **no** | no | yes | policy (becomes superseded), conclusion |
| 6 | rule type | no | no | yes | policy, conclusion |
| 7 | bootstrap settings | no | no | intervals | conclusion |
| 8 | usage label | no | no | no | conclusion (re-explain) |
| 9 | EDA added | no | addition | no | none |
| 10 | conclusion text | no | no | no | none |
| 11 | code fingerprint of an activity | affected activity and downstream | | | none |
| 12 | dataset or case sha | `dataset_changed` refusal | | | |
| * | unknown mutation | everything is stale | | | all, except documented_fact; reason recorded |

Reachability in v0.1 (review fix, see `CLI-CONTRACT.md` §6): rows 7 (bootstrap settings) and 8 (usage label) are classified by `dependencies.effects` but no v0.1 command changes them, so they are not reachable; row 9 needs no action, because an EDA result goes into its own slot. Row 11 is detected by `status` (a current result whose activity code changed is not current, nor is anything computed from it) and applied when the activity is run again: the replaced result's descendants become stale and, for the split and the fits, `policy` and `conclusion` need reconfirmation (mutation `result_replaced`).

## 4. CLI contract (`uv run --project framework hypotrail … --study DIR`)

- JSON output by default, `--format text` available.
- Exit codes: 0 success or replay; 2 refusal without effect; 3 commit done but an artefact is stale or failed; 4 an execution has an unknown outcome.
- Each mutation sends `{request_id, expected_revision, action, params}` to `apply_command`.

| Command | Effect | Refusals |
|---|---|---|
| `init --case C` | revision 1, unconfirmed facts, plan, agent instructions | `state_exists` (never overwrites), `unsupported_capability`, `dataset_changed`, `platform_unsupported` |
| `status [--since REV]` | read-only: revision, step, next action, open proposals, decisions with `user_words`, invalidations, interrupted or late executions, artefact status, exposure, "not yet defensible" | `integrity_error` |
| `plan` | read-only: steps with question, expected output, completion condition, status | — |
| `decide … propose <id> --value --restatement --rationale` | creates a proposal | `stale_revision` (with diff), `unknown_decision`, `invalid_value`, `literal_number_in_text` |
| `decide … confirm <pid> --user-words T` | confirms and applies §3.7 | `ambiguous_confirmation`, `precondition_missing`, `stale_revision`, `idempotency_conflict` |
| `decide … withdraw <pid>` | withdraws a proposal | same |
| `run … <activity> [--column X] [--rule capacity:100]` | `execution_id`, `result_id`, promoted or `late_not_promoted` | `precondition_missing`, `interrupted_execution_pending`, `unsupported_capability` |
| `run … --acknowledge-interruption E` | acknowledges without restarting | `unknown_execution` |
| `render` | status per artefact | code 3 on failure |
| `check [--text PATH\|-]` | `findings[]` | — |

Preconditions (the 3 pauses):
- `split` requires `prediction_time` and `feature_availability` confirmed, as well as the split decision;
- EDA and `fit.*` require a current split;
- `confirm policy` requires a current policy evaluation;
- the conclusion requires an adopted policy, or `keep_baseline`.

## 5. Study agent instructions **[A1, A2]**

Dedicated study workspace, opened as the agent's working directory. `init` copies into it, from `framework/mlkit/study/agent/`:
- `CLAUDE.md`, short and non-negotiable:
  - **always** run `hypotrail status --json` at the start of a conversation, before any decision or any `run`, and after every refusal; never rely on chat memory;
  - **never ad hoc computation** (python, pandas, spreadsheet). Every cited number comes from an output with its `result_id`. An uncovered request is translated into an existing activity; otherwise the answer is "not supported in v0.1";
  - **3 pauses, and only these**:
    1. prediction and feature availability, with the list of exclusions written by the junior;
    2. split before EDA;
    3. policy adoption, then the conclusion.

    Between two pauses, the agent carries out the authorised work without asking again;
  - **confirmation**: `propose --restatement`, then the user's reply *to that restatement*, copied verbatim into `--user-words`. "ok" ("ok") or "garde ça" ("keep that") never count as a decision: the agent restates and asks again;
  - a fresh `request_id` per intent; when in doubt after a timeout, replay the same one;
  - on `stale_revision`: reread the state, explain the diff, propose again;
  - never say "everything is up to date" without relying on `status`;
  - no causality; run `check --text -` on the conclusion.
- `.claude/skills/hypotrail-study/SKILL.md`, for pedagogy:
  - the term first, then the contextual explanation;
  - the guidance loop;
  - predict before revealing: optional, never written to state;
  - a glossary;
  - reading intervals;
  - `keep_baseline` is a valid result.
- `.claude/commands/hypotrail-resume.md`: reread `status`, summarise in 5 lines, propose the next action.
- The Copilot equivalents (`.github/copilot-instructions.md`, `.github/skills/…`, `.github/prompts/…`) are generated **from the same source**, but are **not tested** while directive [A1] holds.
- **[A2] Instruction leakage.** Claude Code also loads instruction files from parent directories. Tests and acceptance therefore create the study **outside the repository** (temporary directory). For interactive use, the official documentation must be checked for which ancestor files are loaded (`CLAUDE.md`, `AGENTS.md`?) before allowing `studies/<id>/` in the repository.

## 6. Notebook and HTML

- **`study_generated.py`** is regenerated on every render.
  - Header "generated at revision N — do not edit".
  - Setup cell: `HYPOTRAIL_READ_ONLY=1`, `view = read.open(...)`, and a banner if the revision differs.
  - `RESULT_IDS` are frozen at generation, so the numbers are the same as in the HTML.
  - One section per step: question, concept, method, code (the activity source is displayed, not executed), result, interpretation, consequence. Upcoming steps display "Not executed yet".
- **`workbench.py`** is created only once.
  - It uses the same read API and does not import the generated notebook.
  - A threshold or capacity slider, labelled **"Experiment, not adopted"**, calls `policy.evaluate`, a pure function, and displays the adopted policy alongside.
  - A "Your notes" cell.
  - A template change produces `workbench.candidate.py`.
- **HTML** (separate rendering by default, subject to the ADR):
  - revision banner giving the status of each deliverable;
  - position in the plan;
  - decisions, distinguishing confirmed (with `user_words`), proposed, scenario assumptions, and facts;
  - evidence as `<data data-result-id>` elements;
  - policy comparison with paired intervals and `tied_at_cut`;
  - **"What is not yet defensible"** section:
    - threshold chosen on validation;
    - no time or customer identifier;
    - public data already explored;
    - `uncertain_included` features;
    - no causality;
    - untracked workbench;
  - results appendix;
  - **no fake decision controls**.

## 9 bis. Preparing the future webview companion, without building it **[A8]**

**Finding in the code.** The paused companion (`experimental/companion/runtime/protocol.py`) had **its own SQLite state and its own protocol** for `apply`, revision, and confirmation, in parallel with the pilot. This is the mistake not to repeat: there would be two truths.

**Principle.** The future webview will be **one more client** of the same CLI and the same state, just like the chat agent. It must have no state of its own, no protocol of its own, and no server. The VS Code extension already launches a Python process (`extension.js:17-47`); that model is sufficient.

What we do **from v0.1**, because it is cheap and already useful to v0.1:

| Measure | Where | Cost |
|---|---|---|
| Versioned, documented JSON schema for `status`, `plan`, `run`, `decide`, and refusals (`hypotrail.status/1`, stable error codes). Contract tests on this schema | WP1.4, `docs/specs/CLI-CONTRACT.md` | low |
| **Single view**: `view.build(study) -> dict` is the source for the HTML, the notebook, and later the webview. Renderers consume the view, not the raw state | WP1.3 (`read.py`), WP3.1 | near zero |
| Confirmation enriched with a `channel: chat\|cli\|webview` field and `actor`, planned from schema 1 to avoid a migration | §3.2, WP1.4 | none |
| Proposals are first-class objects (`proposal_id`, restatement, status). A future "Confirm" button will call `decide confirm` | already planned | none |
| Maintained rule: a control exists only if it calls `apply`. It remains forbidden in static HTML, and will be allowed in the webview on that sole condition | §6 | none |
| Change detection without a daemon: atomic write, plus append-only `revisions.jsonl`, plus `status --since REV`. The webview will be able to watch `.hypotrail/state.json` | WP1.2 | already planned |
| Chat and webview concurrency covered by `expected_revision` and `request_id`. A test launches two clients in parallel on the same proposal: a single confirmation, and the other client receives a refusal with diff | `test_apply.py` | low |
| **Latency**: `status`, `plan`, and `view` import neither pandas nor sklearn (deferred imports). A test measures the import time of `status` (value recorded, no invented threshold), because a webview will call it often | WP1.4 | low |
| Teaching texts (glossary, step labels, explanations) stored as data (`mlkit/study/content/*.yaml`), not hard-coded in the HTML engine | WP3.1 | low |
| `policy.evaluate` stays pure, and a read-only command `preview policy --rule …` computes without recording anything. It will serve the workbench slider today, and the webview tomorrow | WP2.4 | low |
| A study is located by the `.hypotrail/` marker and `hypotrail status --study`, without a global registry | WP1.2 | none |
| ADR `docs/decisions/0002-companion-as-cli-client.md`: the future companion is a client of `hypotrail.study`, and its old SQLite protocol is not reused | Phase 0 | none |
