# Hypotrail v0.1: decisions taken during implementation

Status: record for the owner's end review. Written at the v0.1 closure (Phase 5), 18 October 2026, from the integrator's working log.

v0.1 was implemented autonomously by agents, following [the plan](V0.1-IMPLEMENTATION-PLAN.md). Wherever the plan left a choice open, or a finding forced a change, the integrator decided and wrote it down. This document groups those decisions by phase, with the reason for each.

**Review?** marks a decision the owner should confirm or overturn. It is a product, scope, cost, or contract choice that an agent should not settle alone. Decisions without the flag are engineering choices that follow from the plan or from a measured finding; they can still be revisited.

Phase names follow the plan. "D1–D12", "H1–H3, M1–M3, L1–L7", "R1–R7" and "F1–F6" are the defect ids of the [first acceptance run](../acceptance/runs/claude-code-2026-10-18.md), the fresh code review, the [rerun](../acceptance/runs/claude-code-2026-10-18-rerun.md), and the [final check](../acceptance/runs/claude-code-2026-10-18-final.md).

## Open questions for the owner

1. **Delegation.** Is recording "decided by delegation" (P5.1) acceptable for a teaching product, or should every decision need the junior's own words? Is the standing delegation's scope (P5.9) right?
2. **Confirmation words.** The bare-acknowledgement, negation, and content-token rules (P1.7, P5.5) are English and French heuristics. Keep them, narrow them, or replace them with an explicit confirmation gesture?
3. **Last-contact variables.** Bank tests treat `day`, `month`, `contact`, `campaign` either as available (P2.10) or as the walkthrough's choice (P4.7). Should the case supplement state a recommended default for them?
4. **Absolute paths** in `.hypotrail/agent.json` (P4.5): acceptable, or should a study be relocatable?
5. **Marimo internal API** (P0.4): accept the pin and the upgrade gate, or limit the notebook to what the public API supports?
6. **Two renderers** (P0.5): keep the stdlib HTML renderer, or revisit `marimo export` when it meets the seven criteria?
7. **Case supplement** (P0.6): the format for new cases?
8. **Evaluation model and budget** (E4, cost): keep Opus, add another model, and fund N repetitions per scenario? When does Copilot acceptance start (directive A1)?
9. **v0.2 scope**: float time columns, duplicates, regression (Auto MPG), groups, and a test partition are refused today. Which comes first?
10. **Licence** (plan §9 item 11): still open before any publication.

## M3: regression study (Auto MPG)

Taken during the M3 implementation (roadmap: the same junior workflow for regression), recorded for the owner's review.

| # | Decision | Rationale | Review? |
|---|---|---|---|
| M3.1 | A regression study has its own decision set: `model_choice` (`fit.linear` or `fit.baseline`) replaces `policy`; verdicts `adopt_model`, `keep_baseline`, `inconclusive`. `adopt_model` needs `model_choice = fit.linear`; `inconclusive` a confirmed model choice. | A decision rule on scores has no meaning for a numeric target; the third pause is a model choice on validation error. | **Review?** Decision names and verdicts are contract. |
| M3.2 | The study state carries an optional top-level `task`; a state without it is binary. The view gets an additive key `task`. Binary constants (`DECISION_IDS`, `STEPS`, `MUTATIONS`, verdicts) are unchanged; regression constants sit beside them. | Existing binary studies and the frozen binary contract stay valid. | |
| M3.3 | Evaluations recomputed from stored predictions keep the effect key `re_policy` in a regression study (`evaluate.regression` is listed there). | Avoids a new frozen effect key; documented in CLI-CONTRACT §6. | **Review?** Naming. |
| M3.4 | A declared time column of type `integer` is supported by `ordinal_cutoff` (rows `>= cutoff` are validation), and it is then the **only** split method; `random` is refused (`invalid_value`). A date or decimal time column is still refused at init. | "No silent fallback": a random split would mix periods. The Auto MPG random 70/30 counterexample is therefore not reproducible in a study. | **Review?** Whether a random counterexample should be allowed with a recorded warning. |
| M3.5 | A declared group column is **accepted** (no longer refused) with `grouped split (v0.2)` named in `case.limitations`, the split's `groups` overlap, and `not_yet_defensible.grouped_split_unsupported`. This also applies to binary cases (synthetic `groups=True`). | The task asks to report overlap rather than claim independence; refusing would block Auto MPG. | **Review?** Relaxes the v0.1 refusal of group columns. |
| M3.6 | A regression target must be `numeric` or `integer` with a declared `unit` (`invalid_case` otherwise). | Errors are reported in the target unit. | |
| M3.7 | The time column (role `time`) is never a model feature and is not in `feature_availability`; `eda.mean_by` accepts it. On Auto MPG the linear model is therefore fitted without the year and shows a positive bias on later years. | Roles are structural; using the ordering column as a feature would be extrapolation by construction. | **Review?** A junior may want the year as a feature. |
| M3.8 | `fit.linear` is `LinearRegression` placed in `mlkit.classical.pipeline` (its ridge model step replaced), so imputation, scaling, and one-hot encoding are the same machinery fitted on training rows. A `category` feature with numeric codes (`origin`) is cast to text before encoding (no effect on Bank or the binary synthetic case, whose categories are text). | Reuse of the pipeline; codes are labels. | |
| M3.9 | `evaluate.regression` records the exposure `validation_model_evaluation` (no new purpose); residuals are observed minus predicted; residuals by period use the declared time column only. | Existing purposes cover model selection on validation. | |
| M3.10 | A missing target value in a regression fit is refused (`missing target values (v0.2)`), never dropped or imputed. | Explicit refusal, as for duplicates. | |
| M3.11 | Agent templates use line-level task blocks (`<!-- hypotrail:task binary|regression -->` … `<!-- hypotrail:end -->`); the binary rendering is byte-identical to the previous templates (tested via `test_agent_files`, which now reads the binary rendering). A regression study gets a generated glossary without the binary-only terms. | One source; regression instructions free of threshold vocabulary. | **Review?** Templates now hold markers; the parallel template work may need a merge. |
| M3.12 | Texts are task-aware through overlays in the same content files (`regression_terms`, `binary_only`, `regression_steps`, `regression_activities`, `regression_metrics`, `report.regression`). | No new content files; binary texts unchanged. | |
| M3.13 | `preview policy` is refused in a regression study (`unsupported_capability`); a binary activity in a regression study (and the reverse) is `invalid_arguments`. | Named refusals. | |
| M3.14 | Synthetic `make_case(task="regression")` is a separate generator path with its own PCG64 streams (10–14); binary output is byte-identical for every seed and option (checked against the previous generator). | Keeps binary fixtures stable. | |
