Hypotrail sous le capot

Hypotrail est une méthode d'étude de machine learning menée avec un agent : faites votre étude ML avec un agent ; Hypotrail garantit que les chiffres, les partitions et les décisions sont traçables, et dit ce qui n'est pas encore défendable. Cette page explique ce qui se passe à l'intérieur : qui fait quoi, où vit l'état, comment une décision est enregistrée, pourquoi un chiffre est accepté ou refusé, et ce qui est garanti par construction ou seulement par coopération.

Tous les extraits JSON et les chiffres viennent d'une étude temporaire créée pour cette page avec hypotrail init --case use-cases/auto-mpg --lang fr --automation until_final_test, puis automation run. Les chemins absolus sont abrégés en <engine> (le dépôt) et <study> (le dossier de l'étude).

1Hypotrail en une image

Trois acteurs, une seule vérité : l'état structuré de l'étude, que seul le moteur écrit. La conversation n'est pas la mémoire de l'étude.

L'humain (un junior, ou un data scientist) parle à un agent de chat (Claude Code aujourd'hui, GitHub Copilot comme cible). L'agent ne calcule rien lui-même : il appelle le moteur, la commande hypotrail, qui lit les données, calcule, enregistre et refuse. Le moteur renvoie à chaque appel un JSON qui se termine par next_action : ce que l'agent doit relayer ensuite. Les livrables (rapport HTML, notebooks Marimo, panneau VS Code) sont régénérés à partir de l'état.

2Pourquoi un moteur, et pas seulement un bon prompt

L'expérience E1 a opposé un agent armé d'une excellente compétence pédagogique à ce même agent contraint de passer par le moteur. Les échecs du premier sont structurels : ils ne se corrigent pas avec une meilleure formulation.

Bras A (le « steelman ») : Claude Code avec un CLAUDE.md de 8 règles et une compétence ml-study qui contient tout ce qu'un bon guide doit savoir (découper avant d'explorer, ne pas réentraîner quand seule la capacité change, refuser « ok » comme décision…), Python libre et un notebook vide. Bras B : le même agent, le même persona, mais uniquement le CLI hypotrail (un audit Bash interdit tout calcul ad hoc). Même cas Bank Marketing, plus un cas synthétique sans contamination possible.

Les limites, telles que le rapport les écrit
  • Petits échantillons : 4 runs scriptés et 4 runs « answering » du bras B, 2 du bras A. Un succès isolé prouve peu.
  • Les pièges de connaissance (fuite de duration, sentinelle pdays = -1) ne sont pas comparables : le case.yaml du bras B documente déjà la disponibilité des variables.
  • Le « junior » du protocole answering est un modèle : il ne se trompe pas et ne résiste pas. E1 mesure la validité du travail d'un agent, pas la compréhension d'un humain.
  • Le relecteur aveugle voit le dossier, pas ce qui a été exécuté : il a validé tous les « pas de réentraînement » du bras A, que les transcriptions contredisent.

3Le cas : des faits, jamais des décisions

Un cas (case.yaml, schéma hypotrail.case/1) décrit un fichier et son contexte avec, pour chaque affirmation, son statut épistémique et sa source. Il peut informer une décision ; il n'y répond jamais.

Le moteur ne reconnaît aucun jeu de données par son nom : tout ce qui est propre au cas vit dans use-cases/<id>/. Le fichier est épinglé par son sha256 ; chaque ligne reçoit une clé de ligne (L<ligne>, le numéro physique de ligne, ancré au sha256), qui sert ensuite à tout : partition, expositions, prédictions. Si le fichier ou le cas change, une étude existante le détecte (dataset_changed, sources_changed) : on recommence une étude, on ne la « met pas à jour ».

Disponibilité : un fait du cas, puis une décision de l'étude

Dans le cas, availability.value vaut available_at_prediction, not_available, uncertain ou unknown. Dans l'étude, la décision feature_availability prend ses propres valeurs : available_at_prediction, not_available, uncertain_excluded, uncertain_included.

Exemple réel : acceleration a une disponibilité unknown dans le cas. Le brouillon du moteur l'a donc exclue : "acceleration": "uncertain_excluded", « un doute sur le moment est un risque de fuite d'information ».

4Le scellement du test final

À init, avant le moindre regard, 20 % des lignes sont mises de côté. Aucune activité ne peut les lire avant l'ouverture, qui n'a lieu qu'une fois.

La méthode n'est pas choisie par l'utilisateur, elle est déduite du cas :

MéthodeQuandComment
temporalle cas déclare un orderles dernières lignes dans cet ordre, égalités départagées par la ligne du fichier ; le nombre d'égalités à la coupure est enregistré
stratifiedcible binaire, pas d'ordrela même part de chaque étiquette
quantile_stratifiedrégression, pas d'ordrela même part de chacune des 5 classes de quantiles de la cible
groupesduplicates: {policy: group}un groupe de lignes identiques n'est jamais coupé (tirage par groupes entiers)
profil review-v1opt-in, avec un analysis_contractfrontière sur l'horloge de prédiction (égalités complètes), labels retardés exclus de l'entraînement, groupes disjoints

Dans chaque strate, dans l'ordre du fichier, une permutation tirée de numpy.random.default_rng(seed) (graine 0, enregistrée) ; on garde floor(n × 0,2 + 0,5) lignes. Les lignes déjà exposées avant l'étude (prior_exposed_rows) restent en développement. Les cellules du test final ne sont lues qu'une fois, pour un contrôle de schéma qui ne rapporte que des comptes.

5L'état d'une étude

Une étude est un dossier marqué par .hypotrail/. Chaque commande qui écrit prend un verrou, relit l'état, vérifie la révision attendue, applique une seule requête, et la valide de façon atomique.

Le dossier réel après le mode automatique
.hypotrail/
  state.json           # l'unique source de vérité
  state.sha256         # empreinte de state.json
  revisions.jsonl      # 62 lignes, une par révision
  events.jsonl         # événements (append-only)
  registry/<rid>.json  # 22 résultats immuables
  registry-index.jsonl # input_key → result_id
  blobs/<sha256>       # 8 contenus adressés
  exposure.jsonl       # 29 lectures de lignes
  executions/          # exécutions et baux
  writer.lock          # verrou d'écrivain unique
  artifacts.json       # état des livrables
  agent.json           # argv du CLI (agent, panneau)
  agent/glossary.yaml

framework/mlkit/study/store.py (docstring « Layout ») ; ls -la <study>/.hypotrail

Les règles d'écriture
  • Atomique : fichier temporaire dans le même dossier, fsync, puis os.replace. Registre et blobs sont créés avec O_EXCL et jamais réécrits.
  • Validation en deux temps : commit.pending.json, remplacement de state.json (le point de validation), state.sha256, ajout à revisions.jsonl. Un crash avant ce point laisse l'état précédent intact ; après, le prochain écrivain termine.
  • Un seul écrivain : flock exclusif sur writer.lock, libéré par le système même si le processus meurt.
  • Baux d'exécution : un calcul long tient executions/<id>.lease. Un bail présent mais non tenu = processus mort : issue inconnue (interrupted_unknown, code de sortie 4), jamais relancée automatiquement.
  • Révision attendue : chaque écriture porte --expected-revision ; sinon stale_revision avec les changements non vus.
  • Identifiant de requête : --request-id neuf par intention ; le même identifiant avec la même signature est rejoué sans rien écrire, avec une autre signature il est refusé (idempotency_conflict).

store.py ; lock.py ; framework/mlkit/reliability.py (apply_command) ; POSIX seulement (platform_unsupported sous Windows natif)

6Les décisions

Le plan d'une étude de régression compte 14 étapes en quatre moments, et 10 décisions. Une décision n'est confirmée que par les mots du junior, une délégation explicite, ou le mode automatique choisi au lancement, et chacune de ces bases reste distinguée.

  6. Critère de succès

7Les calculs et les preuves

Chaque calcul est une activité nommée. Son résultat entre une fois au registre, avec une identité qui couvre ses entrées et son code ; les lignes qu'il a lues entrent au journal d'exposition. Un chiffre n'est cité que s'il remonte à un résultat.

spliteda.qualityeda.distributioneda.target_summaryeda.special_valueseda.mean_byeda.correlationeda.rate_byfit.baselinefit.linearfit.logisticfit.variant[:2|:3]evaluate.regressionpolicy.evaluationdiag.regressiondiag.binarypredictor.capturefinal_test.evaluationdiag.final_test
Identité d'un résultat

result_id = empreinte de (activité, paramètres, entrées, empreinte du code de l'activité, empreinte de la sortie). input_key = la même chose sans la sortie. Deux entrées de même input_key et de result_id différents signalent un calcul non déterministe.

L'environnement (Python, versions) est enregistré pour l'affichage mais hors identité. Une entrée est écrite une fois et jamais modifiée ; « promouvoir » un résultat (le rendre courant dans un slot) est une mutation d'état séparée.

Ce que le registre contient : les erreurs hors pli

Validation croisée en 5 plis temporels sur les 318 lignes de développement : chaque ligne est prédite une fois par un modèle qui ne l'a pas vue. Ce sont des preuves de développement, pas une prévision ; seul le test final, ouvert une fois, sera une preuve finale.

Le journal d'exposition et les regards sur la cible

Chaque lecture de lignes est enregistrée par clé de ligne, avec un but (structural_inspection, train_eda, cross_validated_fit, out_of_fold_evaluation, development_diagnostics, sealed, final_evaluation…). Rien n'est jamais retiré : changer le découpage ne rend pas « inédites » des lignes déjà explorées. Le grand livre de cette étude :

8Le mode automatique

Choisi au lancement seulement, le mode automatique prend chaque décision avec la valeur du moteur et lance chaque calcul. Rien de ce qu'il enregistre ne compte comme jugement du junior tant que celui-ci ne l'a pas relu.

Deux variantes : until_final_test s'arrête avant le test final ; full_demo l'ouvre aussi, et l'étude reste marquée « le test final a été ouvert automatiquement » pour toujours. La valeur n'est jamais un libre choix de l'agent : c'est next_action.auto_value (le brouillon ou la recommandation du moteur, sinon une règle fixe : la règle d'une erreur type pour le modèle, la part du scénario pour la règle…). Le mode s'arrête au premier refus, à ce que seul le junior peut répondre, ou là où il cesse de couvrir le plan ; il ne se termine que dans un sens.

10L'agent du chat

init installe dans l'étude les instructions de l'agent. Elles lui demandent surtout de relayer le moteur, de ne rien calculer lui-même et de ne rien écrire hors de l'étude.

Les règles qui portent le plus (CLAUDE.md, 12 règles)
  1. Lire l'état, puis relayer le moteur : status --summary au début, après un refus et avant chaque pause ; au plus quatre appels d'outil par pause.
  2. Chaque nombre vient du moteur : ni Python, ni pandas, ni script, ni ouverture des fichiers de données ; pas de différence calculée soi-même ; check --text - avant tout message chiffré.
  3. Confirmation : proposer d'abord, la reformulation en bloc cité, une seule question fermée, puis la réponse du junior enregistrée verbatim ; jamais un quiz.
  4. Requêtes : un --request-id neuf par intention, le même après un délai.
  5. Formulation : pas de langage causal ; avant l'ouverture, tout chiffre est une preuve de développement.
  6. Le test final est scellé, puis ouvert une fois, avec un rituel annoncé.
  7. Rester dans l'étude : aucun fichier hors du dossier, pas de /tmp, garder stderr.
Pourquoi un texte court compte

Le CLAUDE.md de cette étude fait 2 898 mots. Le texte d'agent a un plafond de 4 000 mots bruts (4 400 pour la copie Copilot rendue) : le moteur sert déjà une partie de la pédagogie (junior_digest, recommended, question), et le handoff propose d'en déplacer davantage, clé de la portabilité vers Copilot.

La commande /hypotrail-resume reprend une étude depuis l'état enregistré, « not from memory » : objectif, décisions, résultats clés, état actuel, prochaine action, risques.

Aujourd'hui, une étude part d'un cas déjà écrit. Le chantier d'onboarding vise un fichier de données seul, éventuellement un brief, sous Windows natif comme sous macOS, Linux et Codespaces, sans Node.

Les commandes prévues (aucune n'existe encore dans hypotrail --help)
  • hypotrail new NAME --data FILE [--brief FILE] [--context …] : un dossier NAME.case/ à côté de l'étude, l'étude en état « preparing », sans partition.
  • prepare answer / prepare status : les six réponses, chacune avec les mots de l'utilisateur ; une réponse inférée reste « proposée, à confirmer ».
  • case check --feasibility : des comptes sans la cible, un réussi/échoué, pas de proportions par strate (« so a split cannot be shopped for »).
  • seal : exige les six réponses et la faisabilité, écrit case.yaml, lance init avec review-v1 quand le contrat le permet.
  • setup vscode (panneau depuis un VSIX embarqué, sans Node), doctor (diagnostic de l'environnement), hook pretool (le hook d'atelier déplacé dans le paquet).
  • Lot Windows natif : remplacer fcntl.flock, réessayer os.replace, UTF-8 partout, --user-words-file.

14Limites et garanties

Le moteur garantit ce qui passe par ses propres chemins. Ce qui dépend de la bonne foi de l'agent ou de l'utilisateur est dit coopératif, et l'étude le déclare elle-même.

Et la liste « pas encore défendable » (réelle)

defensibility : 9 points dont 1 bloquant.

  • automatic_decisions_to_review · bloquant
  • stale_results, grouped_split_unsupported · réserves
  • unconfirmed_decisions, validation_is_not_independent, final_test_sealed · pas final
  • public_data_already_explored, no_causality, workbench_not_tracked · contexte

Autres limites écrites dans le handoff : plateforme POSIX seulement (fcntl), chemins absolus enregistrés à init (déplacer une étude demande une nouvelle étude), lectures des notebooks absentes du registre des regards, scénarios d'agent courts (N = 3) et aucune exécution d'agent de l'étape 0 à la conclusion en v0.2.

GGlossaire

activité
Un calcul nommé du moteur (split, eda.*, fit.*, diag.*…), lancé par run, dont le résultat entre au registre.
base (basis)
Ce qui fonde une confirmation : les mots du junior (restated, endorsed), une délégation (delegated_default) ou le mode automatique (automatic).
blob
Contenu immuable stocké sous son sha256 (.hypotrail/blobs/) : listes de clés de ligne, prédictions.
cas
case.yaml : faits et hypothèses sur un jeu de données, avec statut et source ; jamais une décision.
clé de ligne
L<ligne>, numéro physique de ligne ancré au sha256 du fichier.
échantillon de développement
Les lignes que l'étude peut explorer et utiliser pour choisir (318 ici).
échantillon de test final
Les lignes scellées à init, ouvertes une fois à la fin (80 ici) ; seule source de preuve finale.
exposition
Enregistrement des lignes lues par une activité, et de son but ; append-only.
hors pli (out-of-fold)
Prédiction d'une ligne par un modèle ajusté sans elle, en validation croisée.
invalidation
Effet d'un changement de décision : résultats périmés (stale), décisions à reconfirmer.
mode automatique
init --automation until_final_test|full_demo ; décisions automatic, relues ensuite.
mode de confirmation
guided (défaut), training, express : ce qui suffit à confirmer.
next_action
La prochaine action de l'étude, rédigée par le moteur pour l'agent et pour le junior.
preuve de développement / finale
Chiffres calculés sur les lignes de développement (servent à choisir) / sur le test final ouvert une fois.
regard sur la cible
Toute analyse qui lit la cible (ici 9 analyses d'exploration et l'échantillon de la fiche) ; comptée dans le grand livre, et signalée quand elle précède une proposition.
registre
.hypotrail/registry/ : un fichier JSON immuable par résultat, identifié par result_id.
révision
Numéro de l'état, +1 à chaque commande validée ; --expected-revision protège des écritures sur un état non relu.
règle d'une erreur type
Garder la configuration la plus simple dont l'erreur moyenne est à moins d'une erreur type de la meilleure (ESL §7.10).
scellement
La mise de côté du test final à init ; un protocole du moteur, pas une isolation du système de fichiers.
slot
Emplacement courant d'un résultat (fit.linear, evaluate.regression) ; « promouvoir » y place un result_id.
