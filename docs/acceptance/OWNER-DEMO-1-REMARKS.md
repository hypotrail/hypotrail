# Owner demo 1 — remarks and validated decisions (2026-10-19)

## R1 — Confirmation too strict for juniors; need modes
- Observed: "oui je confirme cela" refused (`ambiguous_confirmation`, no shared token with the proposal value).
- Also found: the restatement is in English while the chat is in French, so a correct French paraphrase can fail the token match (bug, independent of modes).
- Proposal given: three modes, guided (default) / training / express. Under guided, an explicit endorsement bound to the open proposal is accepted and recorded with `basis=endorsed`; a hybrid rule requires one reason for policy and conclusion. The engine enforces the mode, and lowering it requires the user's words. Planned as ADR 0005.
- Status: VALIDATED by owner (three modes, guided default with the hybrid rule: one reason required for policy and conclusion). Includes the language fix (structured value + per-language label; concept matching in training).

## R2 — Junior sees variables before having seen the data
- Observed: at the feature_availability pause the agent lists features (duration, pdays, poutcome...) though the junior has never seen a row.
- Current engine: no data-preview capability. init records structural_inspection over all rows, so showing a few rows is already covered by the exposure ledger.
- Status: VALIDATED. `hypotrail data` read-only data card (observation unit, size, target labels; grouped column dictionary with availability/status/source, special values, missing, distinct, 3 examples; 5 fixed rows INCLUDING the target; no target rate/histograms pre-split). Step 0 "discover the data" (next_action show_data_card while no proposal exists, no confirmation). Same card in HTML, notebook, companion EDA tab. Optional `group` and `fr` labels in case-supplement (labels shared with R1 language fix).

## R3 — Agent corrects the junior's reason but records it anyway
- Observed: the junior confirmed features with "on écarte aussi contact, sa valeur peut être gonflée" (inflation applies to campaign, not contact). The agent confirmed first, then corrected the reasoning afterwards.
- Problem: a misconception is now the recorded justification in the report and notebook. The correction comes after the fact, so the junior cannot change their words.
- Status: VALIDATED. Agent checks reason before confirm (a reformulate / b confirm with new words / c keep); engine `--agent-concern` recorded and shown; mechanical contradiction check for feature_availability shipped as WARNING first; `decide note --on <decision>` for after-the-fact correction; behaviour by mode (training mandatory, guided one stop, express record only); agentic scenario S10.

## R4 — Notebooks: need "Open in editor" AND "Run with marimo"
- Observed: the Deliverables tab has a single "Open" button (showTextDocument on the .py) for workbench and the generated notebook.
- Wanted: a second button that launches `marimo edit` on the file.
- Constraints to check: AGENTS.md allows Marimo's own local editor server. This is not a study-state write (outside W1–W7), but it is a new panel action, so check the scope of ADR 0004 (possibly an amendment). `marimo edit` writes `__marimo__/` session files (already known). Use the study's uv environment and the pinned marimo 0.25.1. Launch in a VS Code terminal, never as a background process owned by the panel.
- Status: VALIDATED (with R7). Two buttons: generated notebook -> `marimo run` (read-only), workbench -> `marimo edit`; launched in a named VS Code terminal via uv run --project <engine>/framework with argument list (no shell); no process owned by the panel; ADR 0004 amendment "local launch" category + check_layout; available from stage v0.
- Owner confirmed: same two buttons for study_generated.py.
- Nuance: study_generated.py is regenerated by the engine, so edits made in `marimo edit` risk being overwritten (only annotations are preserved). Options: `marimo run` (read-only app) for the generated notebook and `marimo edit` for the workbench, or edit mode with a warning.
