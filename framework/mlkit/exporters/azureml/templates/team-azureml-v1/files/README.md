1. Create the environment (Python 3.13, exact versions from
   `aml/pipelines/training/requirements.lock`):
   ```bash
   conda env create -f environment.yml -n @@text:project_name@@
   conda activate @@text:project_name@@
   ```
   Then install the runtime distribution shipped with the model, when present:
   `pip install aml/pipelines/training/runtime/*.whl`.
2. Nothing modifies your shell: `make` and `cli-aliases.sh` only print commands.

## Quickstart

```bash
python -m src.pipeline.utils.project validate --offline     # local checks, no network
python -m src.pipeline.utils.project predict --input data/hypotrail/models/evaluated/@@text:parity_features_relpath@@ --output outputs/predictions.json
python -m src.pipeline.utils.project materialize --source <path to the original dataset file>
python -m src.pipeline.utils.project run-local --mode rebuild_final_candidate
python -m src.pipeline.utils.project preflight              # prints read-only az commands
python -m src.pipeline.utils.project submit                 # prints the az commands; --execute writes to Azure
```

`run-local` trains a **new candidate** (`rebuilt_candidate`) on the authorised development
rows. It does not inherit the study's verdict: only the evaluated model in
`data/hypotrail/models/evaluated/` is the object the study evaluated.

## Data Engineering Conventions

- `data/01_raw`: kept empty; the template's example tables were removed.
- `data/hypotrail/contracts`: the recipe, data contract, development plan, snapshot, export
  manifest and readiness (JSON, with their SHA-256 in `data/hypotrail/SHA256SUMS`).
- `data/hypotrail/development`: the development rows, materialised from the original file
  by `project.py materialize` (not versioned).
- `data/hypotrail/models/evaluated`: the evaluated model as captured by the study.

On Azure, `data/hypotrail` is one versioned data asset (`aml/pipelines/training/data.yml`);
the code upload (`code:`) excludes it (`.amlignore`).

## Project Structure and Modularity

Each step keeps its `main.py` with a `@hydra.main` entry point that does the I/O and a
separate function with the step's logic (`src/pipeline/utils/hypotrail/steps.py`):

1. `data_preparation`: reads the development rows and checks them against the data
   contract; no statistic is learnt and no row is dropped.
2. `data_splitting`: materialises the recorded partitions; it never draws a new split.
3. `training`: fits a new candidate with the recorded recipe through `hypotrail_runtime`.
4. `evaluation`: technical checks of that candidate (reload, MLflow parity); it never reads
   the study's final test.

### Hydra Configuration and Running Options

Hydra composes `src/conf/config.yaml` as in the team template. Before a step runs, the
configuration is resolved (a missing value is refused), checked against a closed set of
keys (`_target_` and unknown keys are refused), and its scientific projection is compared
with `hypotrail.expected_scientific_sha256`. Operational overrides (paths, logs, tracking)
are accepted; a scientific override (model, parameters, features, metrics, plan) is
refused with `scientific_config_changed`. Multirun is not part of this project: a new
exploration is a new study activity.

## Tracking with Azure MLflow

`mlflow_tracking: false` by default (`src/conf/base_config.yaml`). When true, the steps log
explicit parameters, identities and technical results; there is no autolog and no model
registration before the checks.
