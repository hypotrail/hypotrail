# Hypotrail development instructions

## Read first

1. `docs/START-HERE.md` — objective and reading order.
2. `docs/handoff/IMPLEMENTATION.md` — actual capabilities, gaps, first slice, and acceptance checks.
3. `docs/specs/JUNIOR-WORKFLOW.md` — consolidated target workflow.
4. `docs/architecture/REPOSITORY.md` — boundaries and paths.

Explicit specifications supplied by the user take precedence over this summary. Follow the current task; the presence of a specification does not authorize implementing it during an unrelated maintenance task.

## Product priority

Focus on junior guidance through normal Copilot chat, one evolving HTML report, and an explanatory, editable Marimo notebook. Introduce the statistical term first, then explain it with a contextual example. Make the plan and progress explicit, adapt to the use case, offer recommendations, and ask only useful questions. Start with Bank Marketing, then validate generality with Auto MPG.

The old companion (`experimental/companion/`) remains paused. Do not introduce a webview, application server, embedded chat, MCP integration, or multi-agent orchestration to implement the junior workflow. Marimo's own local editor server can still be used.

One exception, on the owner's explicit request: the study panel in `clients/vscode-companion/` ([ADR 0003](docs/decisions/0003-companion-webview-v0.md), staged by [ADR 0004](docs/decisions/0004-companion-advanced.md)). It sits behind a feature flag that is off by default, with the stage setting `hypotrail.companion.stage` at `v0` by default, and it is a client of the `hypotrail` CLI only ([ADR 0002](docs/decisions/0002-companion-as-cli-client.md)). It has no state, database, server, socket, or language-model integration. Its writes are exactly the whitelist W1–W7 of ADR 0004 and its spec (§7), each gated by stage: confirm or withdraw a proposal in the junior's typed words, propose an engine-drafted value the agent has evaluated, run an `eda.*` chart of the engine's catalog on training rows, regenerate the deliverables, acknowledge an interrupted execution in typed words, and export a handoff pack. It never delegates, records a note, fits, splits, or evaluates. The chat, HTML, and notebook workflow must stay complete without it. Widening its scope, for example with a new write command or delegation, or moving the default stage, needs a new explicit request and an ADR amendment.

## Source boundaries

- Reusable code belongs in `framework/`, including `framework/mlkit/`. Editing the engine is allowed when the assigned task concerns framework development.
- Business context, data, adapters, and study outputs belong in `use-cases/<id>/`. Do not copy the engine into each example.
- Current case `project.json` and `results.json` files are companion tutorial contracts, not the future junior study contract. Make migration explicit and never import tutorial choices as human decisions.
- `framework/tests/fixtures/legacy-project/` contains synthetic test fixtures, not an active study or confirmed human decisions.
- `clients/vscode-companion/` is the flagged study panel (plain JavaScript, no build step, no runtime dependency); `scripts/check_layout.py` checks that it stays default-off and CLI-only.
- `experimental/companion/` is outside the critical path. Extension `assets/` and `engine/` are generated by its packaging script; edit runtime sources instead.
- Keep maintained documentation, UI text, messages, comments, and examples in English. Preserve original third-party data, attributed quotations, and identifiers needed for compatibility.

## Preservation and validity

Do not reset existing `.pilot`, `.osml`, `.local`, or other study state to install an improvement. Test with temporary projects and databases. Historical sessions from the previous development folder are intentionally absent from this repository.

Structured persistent state is authoritative. A proposal, example, or quiz response is not a confirmed human decision. Retain valid confirmations, reread state before mutation, reject stale revisions and conflicting duplicate requests, and preserve notebook annotations.

Distinguish structural inspection, training-partition EDA, validation-based selection, and final evidence. Track exposed data. Changing a split does not make previously explored observations unseen. Do not access historical holdouts or reactivate suspended production certification. Temporary synthetic data created by tests is allowed.

## Execution and verification

Use uv and a dedicated environment for each executable project. Do not run `uv init` in an already configured project. Consult `CONTRIBUTING.md` and the handoff for test commands and current limitations.

Do not weaken assertions to obtain passing tests. Distinguish unit tests, simulated browser tests, and an actual Copilot acceptance session. Precomputed tutorial outputs do not establish that the new junior experience is implemented. Publishing, extension installation, and business model training require authorization appropriate to the task.
